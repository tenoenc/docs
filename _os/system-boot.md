### 시스템 부팅

컴퓨터의 전원을 켰을 때(Power on), 빈 껍데기인 하드웨어가 어떻게 운영체제를 찾아 실행하고 우리가 사용할 수 있는 상태가 되는지, 그 시작 과정을 다룬다.

#### 부트스트랩 프로그램 (Bootstrap Program)

컴퓨터에 전원이 들어오면 CPU는 미리 정의된 메모리 주소에서 명령을 읽기 시작한다. 하지만 RAM은 전원이 꺼지면 데이터가 날아가는 휘발성 메모리이므로 비어 있는 상태다. 따라서 컴퓨터는 전원이 끊겨도 데이터가 보존되는 **ROM(Read-Only Memory)**이나 **EEPROM**에 저장된 초기화 프로그램을 실행하는데, 이를 **부트스트랩 프로그램** 또는 펌웨어(Firmware)라고 한다.



- **하드웨어 초기화:** CPU 레지스터, 장치 컨트롤러, 메모리 등을 검사하고 초기화한다 (POST: Power-On Self-Test).
- **OS 로드:** 디스크의 특정 위치(부트 섹터)에 있는 운영체제 커널을 찾아서 메모리에 적재하고 실행한다.

#### 부트로더 (Boot Loader)

현대의 시스템은 부트스트랩 프로그램이 커널을 직접 로드하기보다는, 조금 더 복잡하고 유연한 **부트로더**라는 프로그램을 먼저 메모리에 올린다.

- **역할:** 디스크에 저장된 운영체제 커널을 찾아 메모리에 로드하고 제어권을 넘긴다.
- **GRUB (GRand Unified Bootloader):** 리눅스 시스템에서 가장 널리 쓰이는 부트로더다. 사용자가 부팅할 OS를 선택하거나(멀티 부팅), 커널 파라미터를 수정하여 부팅(안전 모드 등)할 수 있게 해준다.

#### 커널 로딩과 init 프로세스

부트로더에 의해 커널이 메모리에 로드되면, 커널은 시스템 제어권을 넘겨받아 하드웨어를 완전히 장악한다. 커널은 내부 자료구조를 초기화한 후, 시스템의 **첫 번째 프로세스**를 생성한다.

- **init 프로세스 (PID 1):** 모든 프로세스의 조상이다. 유닉스/리눅스 시스템에서는 `init` (최근에는 `systemd`) 프로세스가 PID 1번을 부여받는다.
- **시스템 초기화:** `init` 프로세스는 `/etc/inittab`이나 서비스 설정 파일들을 읽어 시스템에 필요한 데몬(Daemon) 프로세스들을 차례로 실행시키고, 최종적으로 사용자가 로그인할 수 있는 상태를 만든다.

#### [Practice] 컨테이너의 실체: PID 1의 주인은 누구인가?

Docker 컨테이너를 실행하면 마치 독립된 서버(VM)처럼 느껴지지만, 사실 운영체제 입장에서는 단순한 **'격리된 프로세스 군집'**일 뿐이다. 이를 증명하기 위해 일반 리눅스 환경과 Docker 컨테이너 내부의 프로세스 상태(PID 1)를 비교해 본다.

##### 검증 시나리오 (Shell Script)

일반적인 Linux OS에서는 시스템 전체를 관리하는 `systemd`가 PID 1번을 차지한다. 반면, Docker 컨테이너 내부에서는 우리가 실행한 애플리케이션 자체가 PID 1번을 부여받는다.

```bash
# 1. 호스트 OS(Linux)에서 PID 1번 확인
echo "=== [Host OS] PID 1 Information ==="
ps -p 1 -o comm=

# 2. Alpine Linux 컨테이너 실행 및 내부 PID 1번 확인
# 여기서는 컨테이너가 실행할 메인 프로세스로 'sleep 100'을 지정한다.
echo -e "\n=== [Docker Container] PID 1 Information ==="
docker run --rm alpine ps -ef | grep -v "ps -ef"

# 3. Java 애플리케이션을 담은 컨테이너 예시 (가상 시나리오)
# docker run --rm openjdk:17-slim ps -ef
```

##### 실행 결과 및 해석

```text
=== [Host OS] PID 1 Information ===
systemd

=== [Docker Container] PID 1 Information ===
PID   USER     TIME  COMMAND
    1 root      0:00  sleep 100  <-- 애플리케이션이 직접 1번을 차지함
```

-   **PID 1의 의미:** 유닉스 계열 운영체제에서 PID 1은 모든 프로세스의 조상인 **init 프로세스**를 의미한다.
-   **컨테이너의 경량성:** 컨테이너 내부에 `systemd` 같은 무거운 관리 프로세스가 뜨지 않고, 오직 '애플리케이션'만 1번으로 뜬다는 것은 컨테이너가 불필요한 오버헤드 없이 자원을 격리하고 있음을 시각적으로 보여준다.

> **백엔드 관점: Docker 컨테이너와 PID 1의 비밀**
>
> 이 부팅 과정은 **Docker 컨테이너**를 이해하는 데 결정적인 열쇠가 된다.
>
> 1. **컨테이너는 부팅되지 않는다:** Docker 컨테이너는 호스트 OS의 커널을 공유하므로, 부트스트랩이나 커널 로딩 과정이 없습니다. 단순히 격리된 공간에서 프로세스 하나를 띄우는 것이다.
> 2. **PID 1 문제 (Zombie Reaping & Signals):**
>     - 일반 리눅스에서 PID 1(`systemd`)은 **고아 프로세스(Orphan Process)**를 회수(Reaping)하고 종료 신호(SIGTERM)를 처리하는 중요한 역할을 한다.
>     - 하지만 컨테이너에서 `ENTRYPOINT ["java", "-jar", "app.jar"]`로 실행하면 Java 프로세스가 PID 1이 된다.
> 3. **Side Effect:**
>     - Java 애플리케이션은 기본적으로 PID 1의 역할(좀비 프로세스 청소 등)을 수행하도록 설계되지 않았습니다.
>     - 이로 인해 컨테이너 환경에서 좀비 프로세스가 쌓이거나, `docker stop` 명령을 보냈을 때 앱이 종료 신호를 받지 못해 **강제 종료(SIGKILL)**되는 문제가 발생할 수 있다.
>     - **해결책:** 이를 해결하기 위해 `tini` 같은 경량 init 프로세스를 사용하여 PID 1 역할을 위임하거나, Docker 실행 시 `--init` 옵션을 사용한다.
