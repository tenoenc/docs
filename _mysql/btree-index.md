## B-Tree 인덱스

### B-Tree 구조

B-Tree는 데이터의 정렬 상태를 유지하면서 삽입, 삭제, 검색 작업의 시간 복잡도를 $O(\log N)$으로 수렴시키는 자가 균형 트리 구조이다. 이 아키텍처는 하드웨어의 디스크 I/O 단위를 페이지(Page) 혹은 블록(Block)이라는 고정 크기 단위로 관리하는 현대 컴퓨팅 저장 시스템의 물리적 특성을 공학적으로 극대화하도록 설계되었다.

![](/docs/assets/img/2026-01-09-22-07-13.png)

#### 물리적 계층 아키텍처

B-Tree의 모든 데이터는 노드라고 불리는 물리적 페이지 단위에 저장된다. 이 페이지들은 트리 내에서 맡은 역할에 따라 세 가지 계층으로 구분된다. 최상위에는 단 하나의 루트 노드(Root Node)가 존재하여 탐색의 기점이 되며, 최하위에는 실제 데이터의 레코드 주소나 데이터 자체를 보관하는 리프 노드(Leaf Node)가 배치된다. 루트와 리프 사이에는 탐색 경로를 안내하는 브랜치 노드(Branch Node)가 위치한다. 

각 페이지 내부에는 키 값들이 오름차순으로 정렬되어 있으며, 브랜치 노드나 루트 노드의 키 사이사이에는 하위 자식 노드를 가리키는 포인터가 배치된다. 이 포인터들을 통해 엔진은 수조 건의 데이터 중에서도 단 몇 번의 페이지 이동만으로 목표 지점에 도달할 수 있는 수직적 탐색 가이드를 확보한다.

#### 트리 가용성 분석: B-Tree vs Binary Tree

B-Tree가 일반적인 이진 트리(Binary Tree)를 배제하고 데이터베이스 엔진의 핵심 알고리즘으로 채택된 이유는 디스크 I/O 최적화와 직결된다.

| 비교 속성 | 이진 트리 (Binary Tree) | B-Tree (Balanced Tree) |
| :--- | :--- | :--- |
| **자식 노드 수** | 최대 2개 (Low Fan-out) | 페이지 크기 허용 범위 내 수백 개 (High Fan-out) |
| **트리 높이** | 데이터 증가 시 급격히 높아짐 | 극도로 낮은 높이 유지 (보통 3~4단계) |
| **I/O 효율** | 탐색 시 많은 노드 방문 필요 | 한 번의 페이지 로드로 수많은 키 대조 가능 |
| **물리적 단위** | 메모리 포인터 기반 | 페이지(16KB 등) 기반의 디스크 최적화 |
| **정렬 유지** | 균형이 깨질 경우 $O(N)$으로 퇴화 | 삽입/삭제 시 자가 균형 메커니즘 작동 |

#### 논리적 임계점 분석

> **모든 경로의 균일성 (Uniform Path Length)**
> 
> B-Tree의 'B'는 Balanced를 의미하며, 이는 모든 리프 노드가 루트로부터 항상 동일한 깊이에 존재함을 보장한다. 만약 특정 리프 노드만 유독 깊은 곳에 위치한다면 검색 속도의 불확실성이 증가하겠지만, B-Tree는 삽입 과정에서 페이지를 분할하거나 병합하여 모든 데이터에 대한 접근 비용을 균일하게 유지한다. 이러한 결정론적 성능 보장은 대규모 시스템의 예측 가능성을 담보하는 핵심 기제이다.
{: .block-tip }

#### 물리적 공간 관리 및 페이지 디렉토리

하나의 페이지 내부는 단순한 데이터의 나열이 아니다. 페이지 헤더, 실제 레코드, 그리고 페이지 내에서 빠른 검색을 돕는 페이지 디렉토리 영역으로 구성된다. 특히 리프 노드들은 서로 양방향 연결 리스트(Doubly Linked List)로 결합되어 있는데, 이는 수직적 탐색 없이 인덱스 리프 노드만을 훑으며 데이터를 읽는 인덱스 스캔 작업을 가능케 한다.

> **Q: 왜 페이지 크기는 보통 16KB로 고정되는가?**
> 
> A: 이는 운영체제의 가상 메모리 관리 단위(Page)와 파일 시스템의 블록 크기 사이의 트레이드오프를 고려한 결과이다. 너무 작으면 I/O 횟수가 늘어나고, 너무 크면 작은 데이터를 읽을 때도 불필요하게 많은 양의 데이터를 메모리로 올려야 하는 오버헤드가 발생한다. 16KB는 수백 개의 인덱스 키를 한 번에 담아 트리의 높이를 효과적으로 낮추면서도 버퍼 풀의 메모리 효율을 유지할 수 있는 공학적 합의점이다.
{: .block-tip }

### 인덱스 키 추가 및 삭제

B-Tree 인덱스는 데이터의 정렬 상태를 물리적으로 강제하기 때문에, 새로운 키가 유입되거나 기존 키가 제거될 때 단순한 데이터 저장 이상의 구조적 재배치 과정을 수반한다. 이러한 과정은 스토리지 엔진의 리두 로그(Redo Log) 생성 부하와 버퍼 풀(Buffer Pool)의 메모리 관리 효율에 직접적인 영향을 미친다.

#### 페이지 분할 메커니즘 추적

새로운 키가 추가될 때, 인덱스 페이지에 가용 공간이 부족하면 트리의 균형을 유지하기 위한 **페이지 분할(Page Split)** 작업이 실행된다. 이 과정은 하드웨어적 I/O 비용이 발생하는 가장 무거운 지점이다.

1.  **대상 페이지 탐색**: 삽입될 키의 정렬 위치에 해당하는 리프 페이지를 수직 탐색을 통해 식별한다.
2.  **공간 포화 판정**: 해당 페이지의 슬롯이 가득 찼는지 확인한다. 여유 공간이 있다면 정렬 순서에 맞춰 레코드를 삽입하고 종료한다.
3.  **신규 페이지 할당**: 여유 공간이 없을 경우, 스토리지 엔진으로부터 새로운 물리 페이지를 할당받는다.
4.  **레코드 재배치**: 기존 페이지 레코드의 절반가량을 새로운 페이지로 이동시킨다.
5.  **부모 노드 갱신**: 새로운 페이지의 시작 키 값을 상위 브랜치 노드(Parent Node)에 등록한다. 만약 부모 노드 또한 가득 찼다면 이 과정은 루트 노드까지 재귀적으로 전파된다.

![](/docs/assets/img/2026-01-09-22-07-23.png)

#### 삭제 마킹과 물리적 정화

인덱스 키의 삭제는 성능 최적화와 동시성 제어를 위해 즉각적인 물리적 회수가 아닌 논리적 마킹 방식을 채택한다.

* **Delete Marking**: 삭제 쿼리가 실행되면 엔진은 인덱스 레코드 헤더의 `delete_flag`를 활성화한다. 해당 레코드는 인덱스 구조상에 물리적으로 남아 있으나, 이후의 검색 결과에서는 제외된다.
* **Purge Thread**: 시스템의 언두 로그(Undo Log)를 참조하는 가장 오래된 트랜잭션이 종료되어 해당 데이터가 더 이상 필요 없다고 판단되는 시점에, 백그라운드의 퍼지 스레드가 마킹된 레코드를 물리적으로 제거하고 페이지 공간을 재사용 가능 상태로 전환한다.

#### 업데이트 처리의 공학적 필연성

인덱스 키 값의 변경(Update)은 물리적으로 존재할 수 없는 명령이다. B-Tree는 키 값을 기준으로 데이터의 물리적 위치가 결정되는 구조이기 때문이다.

> **Update = Delete + Insert**
> 
> 특정 인덱스 칼럼의 값이 변경되면, 엔진은 기존 위치의 키를 삭제 마킹하고 새로운 값이 위치해야 할 정렬 지점으로 이동하여 삽입 작업을 수행합니다. 따라서 인덱스 칼럼에 대한 잦은 업데이트는 인덱스 크기를 빠르게 팽창시키고 페이지 밀도를 낮추는 주된 원인이 됩니다.
{: .block-warning }

#### 쓰기 부하의 임계점과 트레이드오프

인덱스의 추가/삭제 비용은 테이블의 전체 인덱스 개수에 비례하여 선형적으로 증가한다.

| 작업 유형 | 프라이머리 키 (Clustered) | 보조 인덱스 (Secondary) | 시스템 부하 요인 |
| :--- | :--- | :--- | :--- |
| **삽입 (Insert)** | 즉시 물리 재배치 발생 가능 | 체인지 버퍼를 통한 지연 쓰기 가능 | 페이지 분할 및 리두 로그 생성 |
| **삭제 (Delete)** | PK 순서 유지 필요 | 논리적 삭제 마킹 후 백그라운드 처리 | 언두 로그 및 퍼지 스레드 경합 |
| **수정 (Update)** | 데이터 이동 수반 (매우 고비용) | 삭제 및 삽입 연쇄 발생 | 인덱스 파편화 및 페이지 채우기 계수 저하 |

> **Q: 왜 체인지 버퍼는 보조 인덱스에만 적용되는가?**
> 
> A: 프라이머리 키는 데이터의 물리적 저장 위치를 결정하고 유니크 제약 조건을 즉시 검사해야 하므로 지연 처리가 불가능하다. 반면 보조 인덱스는 유니크 제약이 없는 경우, 변경 사항을 메모리에 모았다가 디스크 읽기가 발생할 때 한꺼번에 병합(Merge)함으로써 랜덤 I/O를 획기적으로 줄일 수 있다. 이는 일관성과 성능 사이의 정교한 설계적 절충안이다.
{: .block-tip }

```cpp
/**
 * B-Tree: Recursive Key Insertion and Page Splitting Logic
 * Explaining the cost of promotion up to the root.
 */

Status BTree::insert(Key key, Value val) {
    Page* leaf = find_leaf_node(key);
    
    // Attempt simple insertion
    if (leaf->has_space()) {
        leaf->insert_record(key, val);
        return SUCCESS;
    }

    // Trigger Page Split if full
    while (current_node->is_full()) {
        Page* new_page = allocate_new_block();
        Key split_key = current_node->split_to(new_page); // Redistribute 50/50

        if (current_node->is_root()) {
            createNewRoot(current_node, split_key, new_page);
            break; 
        } else {
            // Promote split_key to parent and repeat if parent is full
            current_node = current_node->parent;
            current_node->add_child_pointer(split_key, new_page);
        }
    }
    return SUCCESS;
}
```

### 인덱스 키 검색

B-Tree 인덱스를 통한 데이터 검색은 루트 노드에서 시작하여 하위 노드로 내려가는 **수직적 탐색**과, 목적지에 도달한 후 필요한 데이터를 순차적으로 읽는 **수평적 탐색**의 결합으로 완성된다. 이 메커니즘은 정렬된 키 값을 기반으로 탐색 범위를 이진 분할하여 디스크 I/O 횟수를 최소화하는 데 최적화되어 있다.

#### 수직적 탐색과 수평적 탐색의 물리적 경로

엔진이 특정 키를 검색할 때 거치는 물리적 단계는 다음과 같은 정밀한 추적 과정을 따른다.

1.  **루트 노드 진입**: 인덱스의 시작점인 루트 페이지를 메모리(버퍼 풀)로 로드하고 탐색할 키 값을 대조한다.
2.  **브랜치 노드 가이드**: 루트 노드의 키 사이사이에 배치된 자식 페이지 포인터를 따라 하위 브랜치 노드로 이동한다. 이 과정은 목표 키가 존재할 수 있는 유일한 경로를 확보하는 과정이다.
3.  **리프 노드 도달**: 수직적 탐색의 최종 목적지인 리프 페이지에 도달한다. 리프 페이지는 실제 레코드의 주소 또는 데이터를 담고 있는 물리적 블록이다.
4.  **페이지 내부 이진 탐색**: 리프 페이지 내부에 저장된 레코드들을 대상으로 이진 탐색을 수행하여 정확한 레코드 위치를 식별한다.
5.  **범위 스캔 실행**: 조건이 범위 검색(Range Scan)일 경우, 첫 번째 레코드를 찾은 시점부터 리프 노드의 양방향 연결 리스트(Doubly Linked List)를 따라 필요한 범위까지 옆으로 이동하며 데이터를 읽는다.

#### 검색 유형별 메커니즘 대조

검색의 목적에 따라 엔진이 인덱스를 활용하는 방식과 그에 따른 자원 소모량은 상이하게 나타난다.

| 비교 속성 | 점 검색 (Point Search) | 범위 검색 (Range Search) |
| :--- | :--- | :--- |
| **주요 연산자** | `=`, `IN` | `>`, `<`, `BETWEEN`, `LIKE 'abc%'` |
| **알고리즘** | 수직적 탐색 후 단일 레코드 추출 | 수직적 탐색 후 리프 노드 수평 스캔 |
| **I/O 발생량** | 트리의 높이($Depth$)에 비례 | $Depth$ + 스캔할 리프 페이지 수 |
| **연결 리스트 활용** | 미사용 | 필수적으로 양방향 링크 추적 |
| **시간 복잡도** | $O(\log N)$ | $O(\log N + M)$ ($M$은 스캔 대상 수) |

#### 내부 구조: 페이지 디렉토리와 슬롯 탐색

페이지 내부의 레코드는 물리적으로 항상 정렬된 상태로 저장되지 않을 수 있다. 삽입과 삭제가 반복되면서 물리적 순서가 뒤섞이기 때문이다. 이를 극복하기 위해 페이지 하단에는 **슬롯(Slot)** 또는 **페이지 디렉토리(Page Directory)**라고 불리는 정렬된 포인터 배열이 존재한다. 엔진은 페이지 내에서 레코드를 하나하나 전수 조사하지 않고, 이 디렉토리를 이용해 이진 탐색을 수행함으로써 페이지 내부 검색 속도를 $O(1)$에 가깝게 유지한다.

```cpp
/**
 * Pseudo-logic for Index Scan Type Selection
 * Demonstrating how the engine decides between Point and Range Scan.
 */

ScanPlan select_index_scan_type(Index index, Condition cond) {
    if (cond.operator == EQUAL && index.is_unique()) {
        // Only vertical traversal needed
        return IndexUniqueScan(index, cond.value);
    } 
    
    if (cond.is_range() && index.supports_range()) {
        // Vertical traversal to start_point, then horizontal scan
        Key start_key = cond.get_lower_bound();
        Key end_key = cond.get_upper_bound();
        
        float selectivity = index.estimate_selectivity(start_key, end_key);
        if (selectivity > 0.25) {
            return TableFullScan(); // Index usage cost is too high
        }
        return IndexRangeScan(index, start_key, end_key);
    }

    return TableFullScan();
}
```

#### 논리적 제약 조건 분석

> **왜 왼쪽 일치(Prefix Match)가 필수적인가?**
> 
> B-Tree는 키 값을 기준으로 물리적인 정렬이 이루어져 있다. 만약 쿼리 조건이 인덱스 칼럼의 중간이나 뒷부분을 검색(`LIKE '%abc'`)하도록 설계된다면, 루트 노드에서 어떤 자식 노드로 내려가야 할지 결정할 수 없게 된다. 이는 인덱스의 정체성인 '수직적 탐색 가이드'를 상실함을 의미하며, 결과적으로 엔진은 인덱스 전체를 다 읽거나 테이블 전체를 훑는 풀 스캔을 선택하게 된다.
{: .block-tip }

> **Q: 인덱스 검색이 테이블 풀 스캔보다 항상 유리한가?**
> 
> A: 그렇지 않다. 인덱스를 통해 레코드를 읽는 것은 인덱스 페이지와 데이터 페이지를 번갈아 참조하는 랜덤 I/O를 유발한다. 옵티마이저는 인덱스를 통해 읽어야 할 레코드 건수가 전체의 약 20~25%를 넘어서면, 인덱스를 타는 것보다 테이블 전체를 순차 I/O로 한 번에 읽는 것이 더 저렴하다고 판단한다. 인덱스는 만능 열쇠가 아니라, 선택도를 기반으로 한 비용 효율적 도구이다.
{: .block-warning }

### 멀티 칼럼 인덱스

멀티 칼럼 인덱스(Composite Index)는 두 개 이상의 칼럼을 결합하여 생성한 인덱스로, 데이터의 물리적 정렬 순서가 단일 칼럼 인덱스보다 복잡한 계층 구조를 형성한다. 이 구조에서 후행 칼럼의 정렬 상태는 반드시 선행 칼럼의 정렬 상태에 의존하며, 이러한 물리적 특성은 쿼리의 인덱스 가용성을 결정하는 근본적인 원인이 된다.

#### 다층적 정렬 메커니즘의 심층 분석

멀티 칼럼 인덱스 내에서 데이터는 마치 사전(Dictionary)의 단어 배열과 같은 방식으로 저장된다. 첫 번째 칼럼을 기준으로 우선 정렬이 수행되고, 첫 번째 칼럼의 값이 동일한 레코드들에 한해서만 두 번째 칼럼의 정렬이 유효해진다. 만약 세 번째 칼럼이 존재한다면, 이는 첫 번째와 두 번째 칼럼의 값이 모두 일치하는 구간에서만 정렬된 상태를 유지한다.

![](/docs/assets/img/2026-01-09-22-07-44.png)

이러한 정렬 의존성 때문에 멀티 칼럼 인덱스는 '선택도(Selectivity)'가 높은 칼럼을 앞에 두는 것이 유리하다는 통념이 존재하지만, 실제로는 **'검색 조건에서 사용되는 빈도'**와 **'동등 비교(=) 여부'**가 칼럼 순서 결정의 더 핵심적인 기준이 된다.

#### 칼럼 배치 전략에 따른 성능 대조

| 비교 지표 | (A, B) 인덱스 | (B, A) 인덱스 | 비고 |
| :--- | :--- | :--- | :--- |
| **WHERE A=1 AND B=10** | 최적 (두 칼럼 모두 작업 결정 조건) | 최적 (두 칼럼 모두 작업 결정 조건) | 순서 상관없음 |
| **WHERE A=1** | 효율적 (인덱스 활용 가능) | 비효율 (인덱스 활용 불가) | 선두 칼럼의 중요성 |
| **WHERE B=10** | 비효율 (Index Full Scan 혹은 Full Table Scan) | 효율적 (인덱스 활용 가능) | - |
| **WHERE A>1 AND B=10** | A만 작업 결정 조건, B는 필터링 조건 | B만 작업 결정 조건, A는 필터링 조건 | 범위 조건의 영향 |
| **ORDER BY A, B** | 정렬 처리 생략 가능 (Filesort 없음) | 별도 정렬 작업 필요 | 물리적 정렬 순서 활용 |

#### 인덱스 탐색의 단계별 추적

엔진이 `(City, Job, Age)`로 구성된 멀티 칼럼 인덱스를 사용하여 데이터를 탐색하는 물리적 과정은 다음과 같다.

1.  **선두 칼럼 필터링**: 루트 페이지에서 시작하여 `City`가 'Seoul'인 첫 번째 리프 페이지 구간을 수직 탐색한다.
2.  **중간 칼럼 정합**: 'Seoul' 구간 내부에서 `Job`이 'Engineer'인 레코드의 시작점을 찾는다. 선두 칼럼이 고정되었으므로 `Job` 칼럼은 완벽히 정렬된 상태이다.
3.  **최종 구간 스캔**: `Job`이 'Engineer'인 구간이 끝날 때까지 수평 스캔을 진행하며, `Age` 조건을 대조한다. 만약 `Job`이 범위 조건(`LIKE 'Eng%'`)이라면 그 뒤의 `Age`는 더 이상 정렬된 상태로 취급되지 않아 엔진은 단순 필터링만 수행한다.

> **작업 결정 조건과 필터링 조건의 분기점**
> 
> 멀티 칼럼 인덱스에서 각 칼럼의 조건이 검색 범위를 좁히는 데 기여하면 '작업 결정 조건(Access Condition)'이라 부르고, 단순히 읽어온 데이터를 거르기만 하면 '필터링 조건(Filtering Condition)'이라 한다. 중간 칼럼에서 범위 검색(`>`, `<`, `BETWEEN`, `LIKE 'abc%'`)이 사용되는 순간, 그 이후의 모든 칼럼은 작업 결정 조건으로서의 기능을 상실한다.
{: .block-warning }

```sql
/**
 * Composite Index Efficiency Analysis
 * Index Definition: (dept_no, salary)
 */

-- [Scenario 1] Best Case: Both columns act as Access Conditions
-- 수직 탐색으로 특정 부서의 특정 급여 지점까지 한 번에 도달
SELECT * FROM employees 
WHERE dept_no = 'd005' AND salary = 50000;

-- [Scenario 2] Range Condition Impact: Second column becomes a Filter
-- dept_no는 범위를 좁히지만, salary 조건은 단순히 50000보다 큰 값을 거르는 역할만 수행
-- 인덱스 내부 정렬 순서가 dept_no 기준으로 먼저 나열되기 때문
SELECT * FROM employees 
WHERE dept_no > 'd005' AND salary = 50000;

-- [Scenario 3] Leading Column Missing: Index cannot be used for traversal
-- 선두 칼럼인 dept_no가 없으므로 B-Tree의 수직 탐색 가이드라인 상실
-- Index Full Scan 혹은 Table Full Scan 발생
SELECT * FROM employees 
WHERE salary = 50000;
```

> **Q: 단일 칼럼 인덱스 여러 개를 생성하는 것과 멀티 칼럼 인덱스 하나를 생성하는 것 중 무엇이 더 나은가?**
> 
> A: MySQL 옵티마이저는 기본적으로 하나의 쿼리를 처리할 때 하나의 인덱스만 사용한다(Index Merge가 발생하는 특수한 상황 제외). 따라서 `WHERE A=1 AND B=2`와 같은 쿼리가 주력이라면, A 인덱스와 B 인덱스를 따로 두는 것보다 (A, B) 결합 인덱스를 생성하는 것이 압도적으로 효율적이다. 전자는 인덱스 하나를 탄 후 나머지 조건을 데이터 페이지에서 일일이 대조해야 하지만, 후자는 인덱스 레벨에서 정확한 지점으로 직행할 수 있기 때문이다.
{: .block-tip }

### 인덱스 스캔 방향

B-Tree 인덱스는 물리적으로 정렬된 구조를 갖추고 있으나, 이 정렬이 반드시 한 방향으로만 소비되는 것은 아니다. 최신 데이터베이스 엔진은 인덱스를 정순(Forward) 또는 역순(Backward)으로 읽을 수 있는 양방향 스캔 메커니즘을 지원하며, 이는 `ORDER BY` 절의 최적화와 밀접한 연산적 연관성을 가진다.

#### 페이지 내부의 물리적 비대칭성

인덱스 리프 노드 간에는 양방향 연결 리스트(Doubly Linked List)가 구축되어 있어 페이지 단위의 전후방 이동은 자유롭다. 그러나 실제 개별 레코드가 저장되는 페이지 내부 구조는 단방향 연결 리스트(Singly Linked List)에 가까운 형태로 레코드들이 엮여 있다. 이러한 물리적 설계의 비대칭성은 스캔 방향에 따른 성능 차이를 유발하는 근본 원인이 된다.

![](/docs/assets/img/2026-01-09-22-07-52.png)

#### 인덱스 역순 스캔의 단계별 추적

엔진이 오름차순으로 정렬된 인덱스를 역순(Descending)으로 읽을 때 발생하는 내부적인 처리 과정은 다음과 같다.

1.  **목표 지점 수직 탐색**: 검색 조건 혹은 정렬 조건의 최댓값(오른쪽 끝)이 위치한 리프 페이지를 찾기 위해 수직적 탐색을 수행한다.
2.  **페이지 커서 위치 설정**: 해당 페이지의 가장 마지막 레코드에 커서를 위치시킨다.
3.  **페이지 내 역방향 이동**: 페이지 내부 레코드들은 정방향으로만 링크되어 있으므로, 현재 레코드의 '이전 레코드'를 찾기 위해 페이지 하단의 페이지 디렉토리(Page Directory)를 참조하여 앞쪽 슬롯부터 재탐색을 수행한다.
4.  **페이지 경계 이동**: 현재 페이지의 모든 레코드를 읽으면, 리프 노드의 왼쪽 포인터(Previous Page Pointer)를 따라 이전 페이지로 점프한다.

#### 스캔 방향에 따른 성능 및 아키텍처 대조

| 비교 항목 | 정순 스캔 (Forward Scan) | 역순 스캔 (Backward Scan) |
| :--- | :--- | :--- |
| **물리적 방향** | 인덱스 리프 노드의 왼쪽에서 오른쪽 | 인덱스 리프 노드의 오른쪽에서 왼쪽 |
| **레코드 추적** | 정방향 포인터(Next Record) 단순 추적 | 페이지 디렉토리 반복 참조를 통한 역추적 |
| **CPU 소모량** | 상대적으로 낮음 | 상대적으로 높음 (약 20~30% 오버헤드) |
| **페이지 잠금** | 일반적인 인덱스 래치 구조 활용 | 데드락 방지를 위한 복잡한 잠금 획득 과정 필요 |
| **최적 활용** | ASC 정렬 및 범위 검색 | DESC 정렬 및 최신순 조회 |

#### 논리적 트레이드오프 분석

> **역순 스캔 오버헤드의 실체**
> 
> 많은 개발자가 "인덱스는 양방향이므로 ASC나 DESC나 성능이 같다"고 오해한다. 그러나 InnoDB 스토리지 엔진 관점에서 역순 스캔은 정순 스캔보다 느리다. 이는 페이지 내부에서 레코드 간의 정방향 포인터만 존재하기 때문에, 이전 레코드를 찾기 위해 매번 페이지 디렉토리를 통해 우회 탐색해야 하는 물리적 한계 때문이다. 빈번한 대량 역순 조회가 발생한다면, 인덱스 자체를 내림차순(Descending Index)으로 생성하여 정순 스캔을 유도하는 것이 공학적으로 타당하다.
{: .block-warning }

```sql
/**
 * Optimized Sorting with Descending and Mixed-Order Indexes
 */

-- [1] 오름차순 인덱스를 이용한 역순 스캔 (Backward Scan 유발)
CREATE INDEX idx_created_asc ON articles (created_at ASC);
-- 쿼리 실행 시 "Backward index scan" 메시지 확인 가능
SELECT * FROM articles ORDER BY created_at DESC LIMIT 10;

-- [2] 내림차순 인덱스 생성 (정순 스캔 유도)
CREATE INDEX idx_created_desc ON articles (created_at DESC);
-- 정순 스캔으로 처리되어 위 케이스보다 약 20% 이상 성능 우위 확보
SELECT * FROM articles ORDER BY created_at DESC LIMIT 10;

-- [3] 혼합 정렬 최적화 (Mixed-Order Index)
-- ASC와 DESC가 섞인 ORDER BY를 Filesort 없이 처리하기 위한 유일한 방법
CREATE INDEX idx_category_score ON rankings (category_id ASC, score DESC);

SELECT * FROM rankings 
WHERE category_id = 5 
ORDER BY score DESC; -- 최적화된 정순 탐색
```

> **Q: 단일 칼럼 인덱스에서 DESC 인덱스가 필요한가?**
> 
> A: 단순히 단일 칼럼을 역순으로 읽는 쿼리라면 기존 오름차순 인덱스의 역순 스캔으로도 충분히 대응 가능하다. 하지만 여러 칼럼이 혼합된 정렬(`ORDER BY A ASC, B DESC`)이 필요한 경우라면, 각 칼럼의 정렬 방향이 일치하는 혼합 인덱스(Mixed-Order Index) 없이는 인덱스만으로 정렬을 완결할 수 없으며 강제적인 `Filesort`가 발생하게 된다. 즉, DESC 인덱스의 진가는 멀티 칼럼의 복합 정렬 최적화에서 드러난다.
{: .block-tip }

### 가상 칼럼 인덱스

가상 칼럼 인덱스(Virtual Column Index)는 데이터의 물리적 저장과 논리적 표현을 분리하여, 연산 결과물에 B-Tree의 정렬 구조를 부여하는 고도화된 인덱싱 기술이다. 이는 조회 시점에 수행되던 고비용의 데이터 가공 작업을 데이터 삽입/수정 시점의 인덱스 관리 비용으로 전이시켜, 복잡한 비즈니스 로직이 포함된 쿼리의 응답 속도를 $O(\log N)$ 수준으로 고정한다.

#### 가상 칼럼의 실체화와 인덱스 버퍼링

가상 칼럼은 테이블 레코드에는 존재하지 않으나, 인덱스 생성 시 엔진의 표현식 평가기(Expression Evaluator)에 의해 계산된 결과값이 인덱스 페이지에 물리적으로 기록된다. 이 과정에서 가상 칼럼 인덱스는 단순한 포인터의 집합을 넘어, 가공된 데이터를 보관하는 '작은 요약 테이블'로서의 역할을 수행한다.

#### 데이터 삽입 시 인덱스 갱신 경로 추적

기반 칼럼(Base Column)에 데이터가 유입될 때, 해당 데이터가 가상 인덱스에 반영되는 물리적 흐름은 다음과 같은 인과관계를 갖는다.

* **원본 쓰기**: 기반 칼럼의 값이 데이터 페이지에 기록되고 리두 로그가 생성된다.
* **표현식 트리 가동**: 엔진은 가상 칼럼 정의에 포함된 표현식을 파싱 트리(Parsing Tree) 형태로 실행하여 결과값을 산출한다.
* **인덱스 위치 경합**: 산출된 결과값이 B-Tree의 정렬 순서상 어느 리프 페이지에 위치해야 하는지 수직 탐색을 수행한다.
* **물리적 쓰기 전이**: 결과값이 인덱스 리프 노드에 기록된다. 이때 가용 공간이 없다면 즉시 페이지 분할(Page Split)이 발생하며, 이는 기반 칼럼 하나를 수정했을 뿐인데 인덱스 레이어에서 막대한 I/O가 발생하는 원인이 된다.

#### 함수 기반 인덱스의 가용성 복원 메커니즘

전통적인 인덱스 환경에서 `WHERE FUNC(col) = 'val'` 쿼리가 인덱스를 타지 못하는 이유는 B-Tree가 `col` 자체를 키로 정렬되어 있기 때문이다. 가상 칼럼 인덱스는 이 정렬 기준을 `FUNC(col)`로 재설정함으로써 인덱스 가용성을 물리적으로 복원한다.

> **결정적 연산의 불변성 원칙**
> 
> 가상 칼럼 인덱스의 수식은 반드시 동일한 입력에 대해 항상 같은 결과(Deterministic)를 내놓아야 한다. 만약 시점이나 환경에 따라 결과가 달라지는 비결정적 함수가 포함된다면, 인덱스 리프 노드에 저장된 값이 실제 표현식의 결과와 일치하지 않는 '데이터 부정합' 상태에 빠지게 된다. 인덱스는 과거의 계산 결과를 신뢰하여 탐색을 수행하는 도구이므로, 이 불변성의 원칙이 깨지는 순간 B-Tree의 모든 논리적 근거는 상실된다.
{: .block-warning }

#### 비정형 데이터 필드 추출과 성능 임계점

JSON 칼럼과 같은 거대 비정형 데이터를 다룰 때, 가상 칼럼 인덱스는 전체 문서를 파싱하지 않고도 특정 속성에 직접 접근할 수 있는 '고속 통로'를 제공한다.

> **Q: 가상 칼럼 인덱스가 많아질 때 발생하는 시스템의 한계 비용은 무엇인가?**
> 
> A: 가상 칼럼 인덱스는 조회 성능을 위해 CPU 자원과 쓰기 대기 시간을 소모한다. 데이터가 삽입될 때마다 모든 가상 표현식을 CPU가 계산해야 하므로, 복잡한 수식이 포함된 가상 인덱스가 많을수록 데이터 쓰기 작업의 CPU 점유율이 급격히 상승한다. 또한, 인덱스 페이지의 크기가 커짐에 따라 InnoDB 버퍼 풀 내의 메모리 경합이 심화되어 시스템 전체의 처리량(Throughput)이 하락하는 임계점이 존재한다.
{: .block-tip }

```sql
/**
 * Functional Index for High-Performance JSON Querying
 */

-- [1] JSON 내부의 특정 필드를 정수로 추출하여 가상 인덱싱
-- 내부적으로 가상 칼럼 아키텍처를 사용하여 B-Tree 구축
CREATE INDEX idx_user_internal_id ON order_logs (
    (CAST(log_data->>'$.meta.user_id' AS UNSIGNED))
);

-- [2] 복합 연산 결과를 인덱싱하여 조회 시 연산 비용 제거
CREATE INDEX idx_discounted_price ON products (
    (price * (1 - discount_rate))
);

-- [3] 실행 계획 추적: 가공된 수식임에도 Index Range Scan 확인
EXPLAIN SELECT * FROM products 
WHERE (price * (1 - discount_rate)) > 50000;
```
