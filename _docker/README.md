## 컨테이너 기술의 기초와 가상화

현대 컴퓨팅 인프라의 변천사는 한정된 물리 자원을 얼마나 더 미세하게 쪼개고, 격리하며, 효율적으로 배분할 것인가에 대한 투쟁의 역사와 궤를 같이한다. 베어메탈(Bare-metal) 환경에서 단일 운영체제가 하드웨어의 모든 통제권을 소유하던 시대에서 벗어나, 논리적인 추상화 계층을 통해 자원의 이용률을 극대화하려는 시도는 가상화(Virtualization)라는 거대한 흐름을 만들어냈다. 컨테이너 기술은 이 가상화의 연대기에서 가장 진화된 형태의 자원 격리 메커니즘을 제안하며, 운영체제 수준의 추상화가 어떻게 애플리케이션의 배포와 실행 패러다임을 바꿀 수 있는지 증명한다.

### 가상화 모델의 이해

가상화의 본질은 물리적 하드웨어와 실행 환경 사이의 강한 결합을 해제(Decoupling)하는 데 있다. 이 계층 구조의 설계 방식에 따라 시스템의 성능, 격리 수준, 그리고 관리 복잡도가 결정된다. 가상화 모델은 크게 하드웨어를 모사하는 방식과 운영체제의 커널을 공유하며 프로세스를 격리하는 방식으로 나뉜다. 이들의 차이를 이해하는 것은 단순히 '가벼움'과 '무거움'의 차이를 넘어, 시스템 콜의 처리 경로와 메모리 매핑 아키텍처의 물리적 거리를 이해하는 과정이다.

#### 하드웨어 수준 가상화

하드웨어 수준 가상화는 물리 하드웨어 위에 하이퍼바이저(Hypervisor)라고 불리는 가상 머신 모니터(VMM)를 배치하여, 그 위에 복수의 독립적인 가상 머신(VM)을 구동하는 아키텍처다. 이 모델의 핵심은 하드웨어 자원을 논리적으로 분할하여 각 가상 머신에 할당함으로써, 각 머신이 마치 자신이 실제 물리 자원을 독점하고 있다고 믿게 만드는 속임수(Abstraction)에 있다.

> **하드웨어 수준 가상화의 물리적 한계**
> 
> 하드웨어 가상화는 CPU와 메모리를 완전히 분리된 상태로 모사하기 때문에, 게스트 운영체제에서 발생하는 모든 I/O 요청과 인터럽트가 하이퍼바이저를 거쳐야 하는 병목 구조를 필연적으로 동반한다.
{: .block-warning }

이 아키텍처를 이해하기 위해서는 x86 아키텍처의 CPU 권한 계층인 **Ring 구조**를 살펴봐야 한다. 일반적인 운영체제 환경에서 커널은 가장 높은 권한인 Ring 0에서 실행되며, 하드웨어에 직접 접근한다. 그러나 가상화 환경에서는 하이퍼바이저가 Ring 0(또는 하드웨어 지원 가상화 기술인 Intel VT-x 환경의 VMX Root mode)를 점유한다. 이로 인해 원래 Ring 0에서 실행되어야 할 게스트 운영체제의 커널은 Ring 1 또는 Non-root 모드로 밀려나게 된다.

여기서 **Trap-and-Emulate** 메커니즘이 작동한다. 게스트 운영체제가 하드웨어를 제어하기 위해 특권 명령(Privileged Instruction)을 수행하려고 하면, 하드웨어는 예외(Trap)를 발생시켜 제어권을 하이퍼바이저에게 넘긴다. 하이퍼바이저는 해당 명령을 분석한 뒤, 안전하다고 판단되면 물리 하드웨어에 대신 명령을 내리고 그 결과를 다시 게스트에게 전달한다. 이 과정에서 발생하는 컨텍스트 스위칭(Context Switching)은 시스템에 막대한 오버헤드를 유발하며, 이는 하드웨어 수준 가상화가 컨테이너에 비해 무거울 수밖에 없는 결정적인 하드웨어적 이유가 된다.

![](/docs/assets/img/2026-01-23-08-02-31.png)

메모리 관리 측면에서도 복잡성은 가중된다. 가상 머신은 실제 물리 메모리 주소(Host Physical Address)에 직접 접근할 수 없으므로, 게스트 내부의 가상 주소(Guest Virtual Address)를 게스트 물리 주소(Guest Physical Address)로 변환하고, 이를 다시 하이퍼바이저가 실제 물리 주소로 매핑하는 이중 매핑 구조를 갖는다. 이를 효율화하기 위해 **EPT(Extended Page Tables)**와 같은 하드웨어 가속 기술이 도입되었으나, 본질적인 추상화 계층의 존재는 여전히 메모리 레이턴시의 증가를 야기한다.

#### 하드웨어 수준 가상화

하드웨어 수준 가상화의 완성도를 결정짓는 또 다른 핵심 축은 **바이너리 변환(Binary Translation)**과 **하드웨어 가속(Hardware-Assisted Virtualization)**의 진화 과정에 있다. 초기 x86 가상화에서는 하드웨어가 가상화를 직접 지원하지 않았기 때문에, 하이퍼바이저는 게스트 운영체제가 실행하려는 민감한 명령어를 런타임에 가로채어 실행 가능한 안전한 명령어로 실시간 패치하는 방식을 사용했다. 이 방식은 소프트웨어적으로 모든 명령어를 검사하므로 코드 실행 효율이 극도로 저하되는 단점이 있었다.

이를 극복하기 위해 등장한 것이 Intel의 VT-x와 AMD의 AMD-V 기술이다. 이들 기술은 CPU 내부에 가상 머신 제어 구조인 **VMCS(Virtual Machine Control Structure)**를 도입하여, 하이퍼바이저가 게스트의 상태를 하드웨어 레벨에서 직접 관리할 수 있게 했다. 게스트 운영체제가 특권 명령을 실행할 때 발생하는 `VM Exit`와 다시 게스트 상태로 돌아가는 `VM Entry` 과정이 하드웨어 회로 수준에서 최적화되었음에도 불구하고, 여전히 이 전환 과정 자체는 CPU의 파이프라인을 비우고 캐시 로컬리티를 파괴하는 무거운 작업(Heavy-weight operation)으로 남는다.

또한, I/O 가상화의 경우 **Virtio**와 같은 반가상화(Para-virtualization) 드라이버를 통해 최적화를 꾀한다. 게스트가 하드웨어의 동작을 완벽히 모사하는 대신, 하이퍼바이저와 통신할 수 있는 전용 통로(Ring Buffer)를 통해 데이터를 주고받음으로써 에뮬레이션 오버헤드를 줄이는 전략이다. 하지만 이 역시 결국은 호스트와 게스트 간의 컨텍스트 전환을 전제로 하므로, 마이크로초(μs) 단위의 응답성이 중요한 저지연 서비스에서는 치명적인 한계점으로 작용한다.

#### OS 수준 가상화

OS 수준 가상화는 하드웨어를 추상화하는 대신, 호스트 운영체제의 커널을 직접 공유하며 프로세스 단에서 자원을 격리하는 방식이다. 이는 "가상 머신"이라는 거대한 물리적 모사체를 만드는 것이 아니라, "격리된 프로세스 그룹"을 만드는 것에 가깝다. 하드웨어 수준 가상화가 **HW -> Hypervisor -> Guest OS -> App**이라는 4단계 계층을 갖는다면, OS 수준 가상화는 **HW -> Host OS -> App(Container)**이라는 단일 운영체제 계층 구조를 유지한다.

이 모델의 가장 큰 특징은 **커널 공유(Kernel Sharing)**이다. 모든 컨테이너는 호스트 OS의 커널 엔진을 공통으로 사용하며, 단지 커널 내의 데이터 구조를 논리적으로 분리하여 서로 볼 수 없게 만든다. 이로 인해 컨테이너는 별도의 부팅 과정이 필요 없으며, 프로세스가 실행되는 속도와 거의 동일하게(Sub-second) 기동된다. 또한 게스트 운영체제를 위한 메모리 할당이 필요 없으므로 메모리 오버헤드가 거의 제로에 수렴한다.

> **커널 공유의 보안적 트레이드오프**
> 
> 모든 컨테이너가 동일한 커널을 공유한다는 것은 보안 측면에서 매우 취약한 구조를 가짐을 의미한다. 특정 컨테이너가 커널의 취약점을 공격하여 커널 패닉을 유발하거나 권한을 탈취할 경우, 동일한 호스트 내의 모든 컨테이너와 호스트 OS 전체가 위험에 노출된다. 이는 가상 머신이 하이퍼바이저라는 강력한 격리 벽을 갖는 것과 대조적인 부분이다.
{: .block-warning }

OS 수준 가상화는 시스템 콜(System Call) 처리 방식에서도 극적인 효율성을 보여준다. 가상 머신은 게스트 커널이 시스템 콜을 처리하기 위해 다시 하이퍼바이저를 호출하는 이중 구조를 갖지만, 컨테이너 환경의 프로세스는 호스트 커널에 직접 시스템 콜을 던진다. 커널 입장에서는 이것이 일반 프로세스의 요청인지 컨테이너 내부의 요청인지 구분할 필요 없이, 단지 해당 프로세스가 속한 네임스페이스(Namespace)와 제어 그룹(Cgroups)의 제약 사항만을 체크하여 실행한다.

![](/docs/assets/img/2026-01-23-08-04-00.png)

이러한 효율성에도 불구하고 OS 수준 가상화는 **커널 종속성**이라는 명확한 한계를 지닌다. 호스트 운영체제가 리눅스라면 그 위에서 실행되는 컨테이너 역시 리눅스 커널을 사용해야 하며, 특정 버전 이상의 커널 기능을 요구하는 애플리케이션은 해당 기능을 지원하지 않는 구버전 호스트에서 실행될 수 없다. 이는 이식성(Portability) 면에서는 강력하지만, 이종 운영체제 간의 혼합 실행 환경을 구축하는 데에는 가상 머신보다 불리한 요소가 된다.

#### 하이퍼바이저 (Hypervisor)

하이퍼바이저(Hypervisor)는 물리적 하드웨어와 가상 머신(VM) 사이의 중재자로서, 하드웨어 자원을 논리적으로 추상화하고 이를 여러 가상 머신에 분배하여 관리하는 '가상 머신 모니터(VMM)' 역할을 수행한다. 이 소프트웨어 계층은 단순히 자원을 나누는 것을 넘어, 각 가상 머신이 서로의 존재를 인지하지 못한 채 완벽히 격리된 독립적인 하드웨어 위에서 구동되고 있다는 환상을 유지시키는 것이 핵심이다.

하이퍼바이저는 구동 위치와 방식에 따라 크게 두 가지 유형으로 분류된다.

1.  **Type 1 (Bare-metal) 하이퍼바이저**: 하드웨어 바로 위에서 직접 실행되는 방식이다. 호스트 운영체제가 존재하지 않으며 하이퍼바이저 자체가 커널과 같은 권한을 갖는다. Xen, VMware ESXi, Microsoft Hyper-V가 대표적이다. 하드웨어 접근 경로가 짧아 성능 효율이 높고, 호스트 운영체제의 취약점으로부터 자유롭다는 보안적 강점이 있다.
2.  **Type 2 (Hosted) 하이퍼바이저**: 기존의 호스트 운영체제 위에서 일반 애플리케이션처럼 실행되는 방식이다. Oracle VirtualBox, VMware Workstation 등이 이에 속한다. 설치와 관리가 용이하지만, 모든 I/O 요청이 호스트 OS의 드라이버 스택을 한 번 더 거쳐야 하므로 성능 오버헤드가 크다.

> **KVM(Kernel-based Virtual Machine)의 독특한 위치**
> 
> 리눅스 커널의 일부로 통합된 KVM은 흔히 Type 1과 Type 2의 경계에 있는 것으로 평가받는다. 리눅스 커널 자체를 하이퍼바이저로 전환시켜 하드웨어 자원을 직접 제어하면서도, 리눅스의 프로세스 스케줄러와 메모리 관리 기능을 그대로 활용하는 영리한 설계를 취한다.
{: .block-tip }

하이퍼바이저의 가장 복잡한 임무는 **vCPU(Virtual CPU) 스케줄링**이다. 하이퍼바이저는 물리 CPU(pCPU)의 타임 슬라이스를 쪼개어 가상 머신의 vCPU에 할당한다. 이때 발생하는 치명적인 문제 중 하나가 'L1TF(L1 Terminal Fault)'와 같은 CPU 부채널 공격(Side-channel attack)에 노출될 수 있다는 점이다. 하이퍼바이저는 서로 다른 신뢰 수준을 가진 가상 머신들이 동일한 CPU 코어의 하이퍼스레딩(Hyper-threading) 자원을 공유하지 못하도록 강제하는 '코어 스케줄링' 등의 복잡한 방어 기제를 커널 수준에서 구현해야 한다.

또한, **I/O 가상화**를 처리하기 위해 하이퍼바이저는 **IOMMU(Input-Output Memory Management Unit)** 기술을 활용한다. 이는 가상 머신이 장치에 직접 접근(Direct Assignment/Pass-through)할 때, 가상 메모리 주소가 아닌 실제 물리 메모리 주소로 안전하게 변환되도록 보장한다. 만약 이 중재 과정에서 하이퍼바이저의 소프트웨어 로직이 개입하면(Emulation), 수만 번의 시스템 콜이 발생할 때마다 CPU는 Context Switching을 반복하며 막대한 자원을 소모하게 된다.

#### 게스트 운영체제 (Guest OS)

게스트 운영체제(Guest OS)는 하이퍼바이저가 제공하는 가상 하드웨어 위에서 실행되는 독립적인 운영체제 인스턴스이다. 컨테이너 기술과 비교했을 때 가상 머신의 '무거움'을 상징하는 핵심 요소가 바로 이 게스트 운영체제의 존재다. 가상 머신 내에서 애플리케이션 하나를 실행하기 위해서는 커널, 장치 드라이버, 시스템 라이브러리, 그리고 각종 백그라운드 서비스가 포함된 수백 MB에서 수 GB에 이르는 운영체제 전체가 메모리에 로드되어야 한다.

게스트 운영체제의 도입은 **자원 중복(Resource Duplication)**이라는 비효율을 초래한다. 예를 들어, 동일한 리눅스 배포판을 사용하는 10개의 가상 머신이 실행 중이라면, 동일한 커널 코드와 공유 라이브러리가 메모리 상에 10번이나 중복되어 적재된다. 하이퍼바이저는 이를 최적화하기 위해 **KSM(Kernel Same-page Merging)**과 같은 기술을 사용하여 동일한 내용의 메모리 페이지를 하나로 통합하려 시도하지만, 이는 다시 CPU 연산량을 증가시키는 트레이드오프를 발생시킨다.

> **메모리 벌루닝(Memory Ballooning) 메커니즘**
> 
> 하이퍼바이저는 호스트의 메모리가 부족해지면 게스트 운영체제 내부의 '벌루닝 드라이버'를 팽창시킨다. 게스트 운영체제는 이 드라이버를 일반 프로세스로 인식하여 메모리를 할당해주고, 하이퍼바이저는 이렇게 확보된 메모리를 회수하여 다른 가상 머신에 재배분한다. 이는 게스트 입장에서는 예기치 못한 메모리 압박(Memory Pressure)으로 작용하여 성능 저하를 유발할 수 있다.
{: .block-warning }

![](/docs/assets/img/2026-01-23-08-04-08.png)

성능적 측면에서 게스트 운영체제의 가장 큰 병목은 **이중 스케줄링(Double Scheduling)**이다. 게스트 운영체제 내부의 스케줄러가 특정 프로세스에 CPU 시간을 할당하더라도, 정작 하이퍼바이저가 해당 가상 머신 전체에 CPU 시간을 할당하지 않으면 프로세스는 실행되지 못한다. 이러한 시간 불일치(Time Drift) 문제는 고정밀 타이머가 필요한 실시간 시스템이나 대규모 데이터베이스 환경에서 데이터 정합성 및 성능 예측 가능성을 떨어뜨리는 주요 원인이 된다.

결국 게스트 운영체제는 완벽한 격리와 이종 OS 실행이라는 강력한 자유를 선사하는 대신, 하드웨어 자원의 상당 부분을 운영체제 유지 자체에 소모하는 '세금'을 지불하게 만드는 구조적 특성을 지닌다. 컨테이너는 바로 이 게스트 운영체제라는 거대한 오버헤드를 제거하고 커널을 공유함으로써 효율성의 극대화를 꾀하는 전략을 취하게 된다.

### 리눅스 커널 격리 (Namespace)

리눅스 커널의 네임스페이스(Namespace)는 시스템의 전역 자원(Global Resources)을 추상화하여, 특정 프로세스 그룹에게는 해당 자원이 자신들만의 독립된 인스턴스인 것처럼 보여주는 커널의 핵심 격리 메커니즘이다. 이는 "자원의 가상화"를 구현하는 로우 레벨 기술로, 컨테이너가 호스트 운영체제 위에서 독립된 시스템처럼 동작할 수 있게 만드는 논리적 토대 역할을 수행한다.

커널 내부적으로 네임스페이스는 `task_struct`(리눅스의 프로세스 서술자) 내부에 `nsproxy`라는 구조체 포인터로 관리된다.

> **struct nsproxy의 내부 구조**
> 
> ```c
> struct nsproxy {
>     atomic_t count;
>     struct mnt_namespace  *mnt_ns;
>     struct uts_namespace  *uts_ns;
>     struct ipc_namespace  *ipc_ns;
>     struct pid_namespace  *pid_ns_for_children;
>     struct net            *net_ns;
>     struct cgroup_namespace *cgroup_ns;
>     struct time_namespace *time_ns;
> };
> ```
> `nsproxy`는 프로세스가 속한 각 네임스페이스의 참조를 모아놓은 프록시 객체다. 새로운 네임스페이스가 생성될 때마다 커널은 이 구조체를 새로 생성하거나 기존 것을 공유하며 자원의 가시 범위를 결정한다.
{: .block-tip }

네임스페이스의 제어는 주로 `clone()`, `unshare()`, `setns()`라는 세 가지 시스템 콜을 통해 이루어진다. `clone()`은 새로운 프로세스를 생성함과 동시에 새로운 네임스페이스를 할당하고, `unshare()`는 현재 실행 중인 프로세스를 기존 네임스페이스에서 분리하여 새로운 공간으로 이동시킨다. `setns()`는 이미 존재하는 다른 프로세스의 네임스페이스로 현재 프로세스를 진입시키는 데 사용된다. 이러한 메커니즘을 통해 컨테이너 엔진은 프로세스가 실행되는 "공간"의 벽을 세우고 허문다.

#### mnt 네임스페이스 (파일시스템 격리)

mnt(Mount) 네임스페이스는 리눅스 커널 2.4.19 버전에 가장 먼저 도입된 네임스페이스로, 프로세스가 바라보는 마운트 지점(Mount Points)의 목록을 격리한다. 이 네임스페이스를 통해 프로세스는 호스트 시스템의 전체 파일시스템 계층 구조 중 자신이 허용된 부분만을 보거나, 자신만의 독자적인 마운트 레이아웃을 구성할 수 있다.

![](/docs/assets/img/2026-01-23-08-04-15.png)

**1. 격리의 시작: CLONE_NEWNS**
새로운 mnt 네임스페이스를 생성할 때 사용되는 플래그는 `CLONE_NEWNS`이다. 이 플래그와 함께 `clone()`이나 `unshare()`가 호출되면, 커널은 `copy_mnt_ns()` 함수를 호출하여 호출자(부모)의 마운트 목록을 복사한 새로운 마운트 네임스페이스를 생성한다. 중요한 점은 생성 직후에는 부모와 자식의 마운트 목록이 동일하지만, 이후 어느 한쪽에서 발생하는 `mount()`나 `umount()` 동작은 서로에게 영향을 주지 않는다는 점이다.

**2. 마운트 전파(Mount Propagation)와 피어 그룹(Peer Group)**
단순히 마운트 목록을 복사하는 것만으로는 실제 운영 환경의 복잡한 요구사항을 충족하기 어렵다. 예를 들어, 호스트에 새로 삽입된 USB 메모리가 모든 컨테이너 내부에서도 자동으로 보이게 하거나, 반대로 컨테이너 내부의 마운트가 호스트로 절대 유출되지 않게 해야 할 때가 있다. 이를 제어하기 위해 커널은 **Shared Subtree** 기능을 제공하며, 마운트 지점마다 전파 속성을 정의한다.

* **Shared (MS_SHARED)**: 마운트 이벤트가 피어 그룹 내의 다른 마운트 지점으로 양방향 전파된다. 호스트에서 마운트하면 컨테이너에서도 보이고, 그 반대도 성립한다.
* **Private (MS_PRIVATE)**: 전파가 완전히 차단된다. 해당 네임스페이스 내부에서의 변경은 오직 그 안에서만 유효하며 외부로 나가지도, 외부로부터 받지도 않는다. 컨테이너의 독립적인 루트 파일시스템을 구성할 때 기본적으로 활용되는 속성이다.
* **Slave (MS_SLAVE)**: 단방향 전파만 허용된다. 마스터(Master)인 호스트의 마운트 변경은 슬레이브(Slave)인 컨테이너에 반영되지만, 컨테이너 내부에서의 변경은 호스트에 영향을 주지 않는다.
* **Unbindable (MS_UNBINDABLE)**: Private과 유사하게 전파를 차단하지만, 추가적으로 해당 마운트 지점을 다른 곳으로 바인드 마운트(Bind Mount)하는 것조차 금지한다.

이러한 전파 속성은 `/proc/[pid]/mountinfo` 파일을 통해 확인할 수 있으며, `shared:N` 또는 `master:M`과 같은 태그를 통해 커널이 관리하는 피어 그룹의 ID를 명시한다.

> **mnt 네임스페이스의 한계와 pivot_root의 필요성**
> 
> mnt 네임스페이스는 마운트 '목록'을 격리할 뿐, 실제 루트 디렉토리(`/`)의 경로 자체를 강제로 바꾸지는 않는다. 네임스페이스가 생성된 직후 프로세스는 여전히 호스트의 루트 파일시스템을 보고 있다. 따라서 진정한 의미의 컨테이너 환경을 구축하기 위해서는 mnt 네임스페이스 격리 후 반드시 `pivot_root` 시스템 콜을 사용하여 프로세스의 루트를 컨테이너 전용 이미지 경로로 전환해야 한다.
{: .block-warning }

#### pid 네임스페이스 (프로세스 격리)

pid(Process ID) 네임스페이스는 리눅스 커널 내에서 프로세스 식별 번호를 격리하여, 컨테이너가 자신만의 독립적인 프로세스 트리 구조를 가질 수 있게 만든다. 이 네임스페이스의 가장 핵심적인 특징은 **계층 구조(Hierarchy)**와 **PID 1의 가상화**에 있다.

새로운 pid 네임스페이스를 생성(`CLONE_NEWPID`)하면, 해당 공간에서 처음으로 생성된 프로세스는 PID 1을 할당받는다. 리눅스 시스템에서 PID 1은 전통적으로 `init` 프로세스의 역할을 수행하며, 시스템의 부팅부터 좀비 프로세스(Zombie Process) 회수(Reaping)에 이르기까지 중추적인 책임을 진다. 컨테이너 내부의 프로세스가 종료되어 자식 프로세스들이 고아가 되었을 때, 이 PID 1 프로세스가 이를 입양하여 자원을 정리하지 않으면 시스템의 프로세스 테이블이 가득 차는 문제가 발생한다.

**1. 프로세스 ID의 다중 매핑 메커니즘**
커널 수준에서 프로세스는 단 하나의 유일한 존재이지만, pid 네임스페이스를 통해 여러 개의 ID를 가질 수 있다. 이는 커널의 `struct pid` 구조체가 내부적으로 각 네임스페이스 레벨에서의 PID 값을 담은 `struct upid` 배열을 관리하기 때문에 가능하다.

> **프로세스 식별자의 커널 내부 레이아웃**
> 
> ```c
> struct pid {
>     refcount_t count;
>     unsigned int level;
>     struct upid numbers[1]; // 가변 길이 배열, 각 네임스페이스의 PID 저장
> };
> ```
> 호스트에서 PID 1234인 프로세스가 컨테이너 내부에서는 PID 5로 보일 수 있는 이유는, `numbers[0]`(호스트 레벨)에는 1234가, `numbers[1]`(컨테이너 레벨)에는 5가 기록되어 있기 때문이다.
{: .block-tip }

**2. 계층적 가시성과 신호(Signal) 전달**
pid 네임스페이스는 중첩될 수 있으며, 상위 네임스페이스(조상)는 하위 네임스페이스(자손)의 프로세스를 볼 수 있고 조작할 수 있다. 반면, 하위 네임스페이스의 프로세스는 상위 네임스페이스의 존재를 전혀 알 수 없다. 이 일방향성 격리는 보안의 핵심이다. 하지만 신호 전달에 있어서는 엄격한 규칙이 적용된다. 상위 네임스페이스에서 하위 네임스페이스의 PID 1 프로세스에게 `SIGKILL`이나 `SIGSTOP`을 보내는 것은 가능하지만, 컨테이너 내부의 프로세스가 자신의 PID 1에게 신호를 보내는 것은 커널에 의해 제한된다.

![](/docs/assets/img/2026-01-23-08-04-23.png)

#### net 네임스페이스 (네트워크 격리)

net 네임스페이스는 리눅스 네트워크 스택 전체를 격리하는 가장 방대하고 복잡한 격리 단위다. 여기에는 루프백 인터페이스(`lo`)를 포함한 모든 네트워크 장치, IPv4/IPv6 프로토콜 스택, 라우팅 테이블, 방화벽(iptables/nftables) 규칙, 그리고 소켓 바인딩을 위한 포트 번호 대역이 포함된다.

**1. 네트워크 스택의 완전한 복제**
새로운 net 네임스페이스가 생성(`CLONE_NEWNET`)되면, 해당 프로세스는 전역 네트워크 자원으로부터 완전히 단절된다. 초기 상태의 net 네임스페이스는 물리 인터페이스가 전혀 없는 진공 상태와 같으며, 심지어 루프백 장치조차 `DOWN` 상태로 생성된다. 따라서 컨테이너가 외부와 통신하기 위해서는 가상 네트워크 장치를 생성하여 호스트의 네트워크 스택과 물리적/논리적으로 연결해주는 추가적인 작업이 필수적이다.

**2. veth pair와 가상 브리지의 역할**
컨테이너 네트워크 구성에서 가장 보편적으로 사용되는 도구는 가상 이더넷 쌍인 **veth (virtual ethernet) pair**이다. veth pair는 마치 양방향이 뚫린 파이프와 같아서, 한쪽 인터페이스로 들어온 패킷은 즉시 반대쪽 인터페이스로 전달된다.

* 한쪽 끝(`veth_host`)은 호스트의 기본 네임스페이스나 가상 브리지(`docker0` 등)에 배치한다.
* 다른 쪽 끝(`veth_container`)은 컨테이너의 net 네임스페이스 내부로 밀어 넣고 이름(예: `eth0`)을 변경한다.

이 구조를 통해 컨테이너 내부의 애플리케이션이 `eth0`로 패킷을 보내면, 이는 커널의 네트워크 레이어를 타고 호스트의 `veth_host`로 흘러나와 호스트의 라우팅 규칙에 따라 물리 망으로 전달된다.

![](/docs/assets/img/2026-01-23-08-04-32.png)

#### ipc 네임스페이스 (통신 자원 격리)

ipc(Inter-Process Communication) 네임스페이스는 시스템 V(System V) IPC 오브젝트와 POSIX 메시지 큐를 격리한다. 구체적으로는 공유 메모리(Shared Memory), 세마포어(Semaphores), 그리고 메시지 큐(Message Queues)가 그 대상이다.

리눅스 시스템에서 IPC 자원은 전역적인 식별자(ID)와 키(Key)를 통해 관리되는데, 네임스페이스가 적용되지 않으면 서로 다른 컨테이너의 프로세스들이 동일한 공유 메모리 키를 사용하여 데이터를 가로채거나 손상시킬 위험이 있다. ipc 네임스페이스는 각 컨테이너가 자신만의 독립적인 IPC 식별자 공간을 갖게 함으로써 프로세스 간 통신을 컨테이너 내부로 한정시킨다.

#### uts 네임스페이스 (호스트 네임 격리)

uts(UNIX Timesharing System) 네임스페이스는 시스템의 호스트 네임(`nodename`)과 도메인 네임(`domainname`)을 격리하는 가장 단순한 형태의 네임스페이스다.

`CLONE_NEWUTS` 플래그를 통해 격리된 프로세스는 호스트의 이름과 무관하게 자신만의 이름을 설정할 수 있다. 이는 네트워크 서비스 구축 시 매우 중요한데, 많은 애플리케이션과 프로토콜이 호스트 네임을 식별자로 사용하거나 로그 기록의 기준으로 삼기 때문이다. 만약 이 격리가 없다면 모든 컨테이너는 호스트의 이름을 공유해야 하며, 이는 서비스 식별 및 클러스터 구성에 큰 혼란을 야기한다.

#### user 네임스페이스 (사용자 권한 격리)

user 네임스페이스는 보안적 관점에서 가장 강력하면서도 구현이 까다로운 격리 기술이다. 이 네임스페이스는 프로세스의 사용자(UID)와 그룹(GID) ID 공간을 격리하여, **"컨테이너 내부의 루트(root)가 호스트에서는 일반 사용자"**가 될 수 있도록 만든다.

**1. ID 매핑(Mapping) 메커니즘**
user 네임스페이스의 핵심은 `/proc/[pid]/uid_map`과 `/proc/[pid]/gid_map` 파일을 통한 매핑이다. 이 파일은 컨테이너 내부의 ID 범위를 호스트의 특정 ID 범위와 연결한다.

> **UID 매핑 예시**
> 
> 만약 매핑 설정이 `0 1000 1` 이라면:
> * 컨테이너 내부의 UID 0(Root)은 호스트의 UID 1000(일반 사용자)에 매핑된다.
> * 컨테이너 내부에서 루트 권한으로 파일을 생성하더라도, 호스트 커널은 이를 UID 1000의 소유물로 기록한다.
{: .block-tip }

이 기술은 컨테이너 탈출(Container Escape) 공격에 대한 최후의 방어선 역할을 한다. 만약 공격자가 컨테이너 내부에서 루트 권한을 획득하여 호스트 운영체제로 탈출하더라도, 호스트 입장에서는 권한이 없는 일반 사용자(UID 1000)로 인식되기 때문에 물리적인 시스템 전체를 장악하는 것을 방어할 수 있다.

### 리눅스 자원 제어 (Cgroups)

네임스페이스가 프로세스가 바라보는 '가시 범위'를 격리하여 각 컨테이너를 논리적으로 분리한다면, 제어 그룹(Control Groups, 이하 Cgroups)은 해당 프로세스가 소비할 수 있는 '물리 자원의 양'을 엄격히 제한하고 감시한다. Cgroups는 리눅스 커널의 스케줄러와 메모리 관리 시스템에 직접 개입하여, 특정 프로세스 그룹이 호스트 전체의 자원을 독점(Starvation)하는 것을 방지하고 서비스의 품질(QoS)을 보장하는 핵심 엔진이다.

Cgroups는 커널 내부에서 계층적 구조로 관리되며, 사용자 공간에서는 `/sys/fs/cgroup` 디렉토리에 마운트된 가상 파일 시스템(VFS)을 통해 인터페이스를 제공한다. 운영체제의 관점에서 컨테이너의 자원 제한은 이 가상 파일 시스템 내의 특정 파일에 수치를 기록하는 것만으로 즉시 하드웨어 스케줄링에 반영되는 구조를 가진다. 현재는 Cgroups v1의 복잡성을 해결하고 단일 계층 구조로 통합된 Cgroups v2가 표준으로 자리 잡고 있다.

#### CPU 자원 할당 제어

리눅스 커널은 CPU 자원을 관리하기 위해 **CFS(Completely Fair Scheduler)**를 사용한다. Cgroups의 CPU 컨트롤러는 이 CFS 스케줄러의 동작 파라미터를 조정하여 프로세스에 할당되는 CPU 시간을 제어한다. 도커 및 컨테이너 런타임에서 제공하는 CPU 제한은 크게 '비중(Weight)' 방식과 '제한(Hard Limit)' 방식으로 나뉜다.

**1. CPU Shares (상대적 비중 제어)**
`cpu.shares` 파일에 설정되는 값은 시스템의 CPU 자원이 경합 상태일 때 각 프로세스 그룹이 가질 수 있는 CPU 시간의 상대적 비율을 결정한다. 기본값은 1024이며, 만약 컨테이너 A가 1024, 컨테이너 B가 512를 가지고 있다면, CPU가 풀 로드(Full Load)일 때 A는 B보다 두 배 많은 실행 시간을 보장받는다. 중요하게 짚고 넘어갈 점은, 경합이 없는 상태에서는 `cpu.shares` 설정과 관계없이 프로세스가 유휴 CPU 자원을 모두 사용할 수 있다는 것이다. 이는 자원의 활용률을 극대화하는 엔지니어링적 선택이다.

**2. CFS Quota & Period (절대적 시간 제한)**
상대적 비중과 달리, 특정 주기 동안 프로세스가 사용할 수 있는 CPU 시간을 절대적인 마이크로초(μs) 단위로 제한하는 방식이다.
* **cpu.cfs_period_us**: 스케줄링의 주기(기본 100ms)를 정의한다.
* **cpu.cfs_quota_us**: 정의된 주기 내에서 해당 그룹이 최대로 사용할 수 있는 CPU 시간을 정의한다.

> **CFS 스로틀링(Throttling) 메커니즘**
> 
> 만약 100ms(Period) 중 50ms(Quota)를 사용하도록 설정된 컨테이너가 50ms를 모두 소진하면, 커널은 해당 프로세스를 강제로 대기 상태로 전환시킨다. 이를 '스로틀링'이라 하며, 다음 주기가 시작될 때까지 프로세스는 CPU를 할당받지 못해 레이턴시가 급증하게 된다. 이는 CPU 사용률(Usage)이 낮더라도 순간적인 피크(Burst)로 인해 발생할 수 있는 현상이다.
{: .block-warning }

#### 메모리 자원 제한

메모리는 CPU와 달리 압축 불가능한(Non-compressible) 자원이다. CPU는 할당 시간을 줄여서 대응할 수 있지만, 메모리는 부족할 경우 시스템의 안정성을 위해 프로세스를 강제로 종료해야 하는 극단적인 선택을 강요한다. Cgroups의 메모리 컨트롤러는 프로세스의 익명 메모리(Anonymous Memory), 페이지 캐시(Page Cache), 스왑(Swap) 사용량을 트래킹한다.

**1. 하드 리밋(Hard Limit)과 소프트 리밋(Soft Limit)**
* **memory.limit_in_bytes**: 해당 그룹이 절대 넘을 수 없는 메모리의 최대치다. 이 한계에 도달하면 커널은 메모리 회수(Reclaim)를 시도하고, 실패할 경우 즉시 OOM(Out of Memory) Killer를 호출한다.
* **memory.soft_limit_in_bytes**: 시스템 전체의 메모리가 부족할 때만 적용되는 느슨한 제한이다. 평소에는 이를 초과해서 사용할 수 있지만, 호스트의 가용 메모리가 위험 수준에 도달하면 커널은 소프트 리밋을 초과한 그룹부터 메모리를 강제로 회수한다.

**2. OOM Killer와 점수화(Scoring)**
커널은 메모리 고갈 시 어떤 프로세스를 죽일지 결정하기 위해 `oom_score`를 계산한다. Cgroups 내의 프로세스들은 그룹 전체의 메모리 사용량에 비례하여 높은 점수를 부여받는다. 특히 컨테이너 환경에서는 특정 컨테이너가 설정된 `limit`을 초과하려고 할 때, 시스템 전체의 OOM Killer가 작동하기 전에 Cgroup 자체의 OOM Killer가 해당 컨테이너 내부의 프로세스 중 가장 '죄질이 나쁜(메모리를 많이 점유한)' 프로세스를 찾아 `SIGKILL`을 날린다.

> **메모리와 스왑(Swap)의 관계**
> 
> 메모리 제한만 설정하고 스왑 제한(`memory.memsw.limit_in_bytes`)을 설정하지 않으면, 컨테이너는 물리 메모리 한계를 넘어서는 데이터를 호스트의 디스크 스왑 영역으로 보낸다. 이는 애플리케이션이 죽지는 않게 하지만, 디스크 I/O 발생으로 인해 시스템 성능이 비약적으로 저하되는 '스래싱(Thrashing)' 현상을 유발한다.
{: .block-tip }

#### I/O 대역폭 제한

Cgroups의 `blkio` 컨트롤러는 특정 프로세스 그룹이 블록 장치(Disk, SSD)에 대해 수행하는 입출력(I/O) 성능을 제어한다. 이는 CPU나 메모리와 달리 물리적 매체의 헤드 이동 속도나 대역폭이라는 물리적 한계가 명확한 자원을 다룬다. 컨테이너 환경에서 특정 애플리케이션이 과도한 디스크 읽기/쓰기를 수행하여 전체 시스템의 응답성을 마비시키는 'Noisy Neighbor' 문제를 해결하기 위해 사용된다.

제어 방식은 크게 두 가지로 나뉜다.

**1. 대역폭 및 IOPS 제한 (Throttling)**
가장 직관적인 방법으로, 초당 전송량(Bytes Per Second)이나 초당 작업 수(I/O Operations Per Second)에 대한 상한선을 설정한다.
* **blkio.throttle.read_bps_device / write_bps_device**: 특정 장치에 대한 초당 읽기/쓰기 바이트 수를 제한한다.
* **blkio.throttle.read_iops_device / write_iops_device**: 초당 I/O 요청 횟수를 제한한다.

**2. 가중치 기반 제어 (Proportional Weight)**
CPU Shares와 유사하게 자원 경합 시 각 그룹이 가질 수 있는 I/O 비중을 설정한다. `blkio.weight` 파일을 통해 100에서 1000 사이의 값을 부여하며, 이는 CFQ(Completely Fair Queuing) I/O 스케줄러가 활성화되어 있을 때만 유효하다. 최근의 NVMe 장치나 멀티 큐(Multi-queue) 환경에서는 CFQ 대신 `bfq` 스케줄러를 활성화해야 이 비중 제어가 정상 작동한다.

> **커널 버퍼드 I/O(Buffered I/O)의 복병**
> 
> `blkio` 컨트롤러의 치명적인 한계는 커널의 페이지 캐시를 거치는 '버퍼드 쓰기'를 완벽히 제어하지 못한다는 점이다. 애플리케이션이 `write()` 시스템 콜을 호출하면 데이터는 즉시 디스크로 가지 않고 커널 메모리(Page Cache)에 머문다. 이후 커널의 `pdflush` 스레드가 백그라운드에서 데이터를 디스크로 밀어낼 때, 이 작업은 컨테이너의 프로세스가 아닌 커널 스레드의 작업으로 간주되어 Cgroups 제한을 회피하게 된다. 이를 해결하기 위해 최근 커널에서는 `cgroup v2`를 통해 메모리 컨트롤러와 블록 I/O 컨트롤러를 유기적으로 결합하여 더 정밀한 제어를 시도하고 있다.
{: .block-warning }

#### 프로세스 개수 제한 (PIDs)

PIDs 컨트롤러는 특정 Cgroup 내에서 생성할 수 있는 총 프로세스(및 스레드)의 개수를 제한한다. 리눅스 커널은 시스템 전체에서 관리할 수 있는 최대 프로세스 수(`/proc/sys/kernel/pid_max`)가 정해져 있는데, 만약 특정 컨테이너에서 악의적인 코드나 버그로 인해 프로세스가 무한히 복제되는 **포크 폭탄(Fork Bomb)**이 발생하면 호스트 전체의 프로세스 테이블이 가득 차 시스템이 중단된다.

`pids.max` 파일에 정수 값을 기록함으로써 이 한도를 설정할 수 있다. 프로세스가 `fork()`나 `clone()` 시스템 콜을 호출하여 새로운 프로세스를 생성하려고 할 때, 커널은 해당 그룹의 현재 프로세스 수(`pids.current`)를 확인한다. 만약 `pids.max`를 초과한다면 커널은 `-EAGAIN` 에러를 반환하며 프로세스 생성을 거부한다. 이는 단순히 시스템 보호를 넘어, 마이크로서비스 환경에서 각 서비스 인스턴스가 설계된 범위를 벗어난 리소스를 점유하지 못하도록 강제하는 안전장치가 된다.

### 파일시스템 추상화

컨테이너가 '이식성(Portability)'을 갖는 이유는 애플리케이션 실행에 필요한 모든 바이너리, 라이브러리, 설정 파일을 하나의 논리적 단위로 묶어 관리하기 때문이다. 이 마법은 리눅스의 파일시스템 추상화 기술을 통해 가능해진다. 호스트의 루트 파일시스템과 컨테이너의 루트 파일시스템을 분리하고, 여러 개의 읽기 전용 레이어를 겹쳐서 하나의 완성된 디렉토리 구조를 만들어내는 과정은 컨테이너 기술의 정수 중 하나다.

#### 루트 디렉토리 격리 (chroot)

`chroot`(Change Root)는 1979년 Unix V7에 처음 도입된 유구한 역사를 가진 시스템 콜로, 특정 프로세스가 바라보는 루트 디렉토리(`/`)의 위치를 변경한다. 이를 통해 프로세스는 지정된 디렉토리 외부의 파일에 접근할 수 없게 되며, 이를 흔히 **'chroot 감옥(Jail)'**이라고 부른다.

작동 원리는 단순하면서도 강력하다. 리눅스 커널의 프로세스 서술자(`task_struct`)에는 파일시스템 정보를 담는 `fs_struct` 구조체가 있으며, 여기에 해당 프로세스의 루트 디렉토리(`root`)와 현재 작업 디렉토리(`pwd`) 정보가 `struct path` 형태로 저장된다. `chroot(path)`가 호출되면 커널은 프로세스의 `root` 경로를 인자로 받은 새로운 경로로 업데이트한다.

> **chroot의 보안적 한계와 탈옥(Escape)**
> 
> `chroot`는 환경을 '격리'하기 위한 용도였을 뿐, 완벽한 보안 경계를 구축하기 위해 설계된 것은 아니다. 예를 들어, 루트 권한을 가진 프로세스는 `chroot` 내부에서 또 다른 `chroot`를 실행하고 특정 트릭(예: 현재 디렉토리를 루트 밖으로 이동시킨 후 상대 경로 사용)을 통해 감옥을 빠져나올 수 있다. 또한 네트워크 장치, 프로세스 리스트, IPC 등 파일시스템 이외의 자원은 전혀 격리하지 못한다는 결정적인 약점이 있다.
{: .block-warning }

![](/docs/assets/img/2026-01-23-08-04-59.png)

컨테이너 기술에서 `chroot`는 격리의 시발점이 되었으나, 현대의 도커는 단순히 경로를 속이는 것을 넘어 파일시스템 마운트 자체를 물리적으로 격리하는 `pivot_root`와 네임스페이스 기술을 조합하여 훨씬 견고한 격리 수준을 달성한다.

#### 피벗 루트 (pivot_root)

`chroot`가 프로세스의 루트 경로라는 소프트웨어적 변수만을 수정한다면, `pivot_root`는 마운트 네임스페이스 내의 마운트 지점(Mount Point) 자체를 물리적으로 교체하는 보다 근본적인 시스템 콜이다. `pivot_root(new_root, put_old)` 호출은 현재 프로세스가 속한 네임스페이스의 루트 마운트를 `new_root`로 바꾸고, 기존의 루트 마운트는 `put_old` 디렉토리 하위로 이동시킨다.

이 메커니즘이 `chroot`보다 보안적으로 월등한 이유는 '이전 루트와의 완전한 단절'이 가능하기 때문이다. `chroot` 환경에서는 프로세스가 루트 바깥의 파일 서술자(File Descriptor)를 가지고 있거나 특정 트릭을 쓰면 감옥을 나갈 여지가 있지만, `pivot_root` 이후에 `umount -l` 명령을 통해 `put_old`에 마운트된 이전 호스트의 루트 파일시스템을 완전히 언마운트(Unmount)해버리면, 컨테이너 내부 프로세스는 물리적으로 호스트 파일시스템에 접근할 경로가 완전히 사라지게 된다.

> **pivot_root 호출의 엄격한 전제 조건**
> 
> 1. `new_root`와 `put_old`는 반드시 디렉토리여야 한다.
> 2. `new_root`와 `put_old`는 현재 루트와 동일한 파일시스템 내에 있어서는 안 된다. (즉, `new_root`는 별도의 파일시스템이 마운트된 지점이어야 한다.)
> 3. `put_old`는 반드시 `new_root` 하위에 존재해야 한다.
> 4. 현재 프로세스의 루트 마운트가 `MS_SHARED` 상태여서는 안 된다. 반드시 `MS_PRIVATE`으로 변경한 후 호출해야 전파로 인한 호스트 시스템의 오동작을 막을 수 있다.
{: .block-warning }

![](/docs/assets/img/2026-01-23-16-55-46.png)

커널 내부적으로 `pivot_root`는 `fs/namespace.c`에 정의되어 있으며, VFS(Virtual File System) 계층에서 마운트 객체(`struct mount`)의 연결 리스트 구조를 재배치하는 작업을 수행한다. 이는 컨테이너가 단순히 격리된 공간에서 실행되는 것을 넘어, 호스트와는 완전히 독립된 파일시스템 생태계를 가질 수 있게 만드는 물리적 확신을 제공한다.

#### 유니온 파일 시스템 (UnionFS)

컨테이너가 기가바이트 단위의 운영체제 이미지를 사용함에도 불구하고 수초 내에 생성될 수 있는 비결은 유니온 파일 시스템(Union File System) 기술에 있다. UnionFS는 여러 개의 디렉토리를 하나의 디렉토리처럼 보이게 합치는(Merge) 가상 파일시스템이다.

이 기술의 핵심 철학은 **'레이어(Layer)의 적층'**이다. 도커 이미지는 여러 개의 읽기 전용(Read-Only) 레이어로 구성되며, 컨테이너가 실행될 때 이 레이어들 위에 단 하나의 쓰기 가능(Writable) 레이어를 얹는다. 사용자가 파일시스템을 조회할 때, UnionFS는 상단 레이어부터 하단 레이어까지 순차적으로 검색하여 가장 먼저 발견된 파일을 사용자에게 보여준다.

* **브랜치(Branch)**: UnionFS에서 합쳐지는 개별 디렉토리를 의미한다.
* **우선순위(Priority)**: 상위에 있는 브랜치가 하위에 있는 동일한 이름의 파일을 가린다(Shadowing).
* **쓰기 전략**: 하위 레이어는 읽기 전용이므로, 수정이 필요할 경우 해당 파일을 상위 쓰기 레이어로 복사한 뒤 수정한다. 이를 **Copy-on-Write (CoW)** 메커니즘이라 부른다.

![](/docs/assets/img/2026-01-23-16-55-55.png)

UnionFS는 저장 공간의 효율성을 극대화한다. 동일한 베이스 이미지(예: Ubuntu 22.04)를 사용하는 100개의 컨테이너가 있더라도, 물리 디스크에는 베이스 이미지 레이어가 단 한 번만 저장된다. 각 컨테이너는 자신만의 얇은 쓰기 레이어만을 가질 뿐이며, 이는 현대 클라우드 인프라에서 스토리지 비용을 혁신적으로 절감하는 엔지니어링적 기반이 된다.

#### OverlayFS 구조

OverlayFS는 UnionFS의 개념을 현대적으로 계승하여 리눅스 커널 3.18부터 메인라인에 포함된 파일시스템 아키텍처다. 기존의 AUFS(Advanced Multi-Layered Unification Filesystem)보다 구조가 단순하고 성능이 뛰어나 현재 도커의 기본 스토리지 드라이버로 채택되어 있다. OverlayFS는 시스템을 크게 네 가지 추상화된 디렉토리로 구분하여 관리한다.

**1. LowerDir (읽기 전용 레이어)**
도커 이미지의 구성 요소들이다. 하단에 위치하며 여러 개를 가질 수 있다. 커널은 이 레이어들에 대해 변경을 허용하지 않으며, 오직 데이터의 원본 소스로만 참조한다.

**2. UpperDir (쓰기 가능 레이어)**
컨테이너 실행 중에 발생하는 모든 변경 사항(파일 생성, 수정, 삭제)이 실제로 저장되는 물리적 공간이다. 컨테이너가 삭제되면 이 디렉토리의 내용도 휘발된다.

**3. MergedDir (통합 뷰)**
사용자와 애플리케이션이 실제로 마운트하여 사용하는 디렉토리다. 커널은 `LowerDir`과 `UpperDir`을 유기적으로 결합하여 이곳에 가상의 파일 트리를 렌더링한다.

**4. WorkDir (커널 내부 작업 영역)**
파일 이동이나 원자적(Atomic) 연산을 수행하기 위해 커널이 임시로 사용하는 빈 디렉토리다. 사용자는 이 공간에 직접 접근할 수 없다.

> **OverlayFS에서의 파일 삭제: 화이트아웃(Whiteout)**
> 
> 읽기 전용인 `LowerDir`에 존재하는 파일을 삭제하려면 어떻게 해야 할까? OverlayFS는 `UpperDir`에 삭제하려는 파일과 동일한 이름의 **'화이트아웃'** 장치 파일(Character device with 0/0 device number)을 생성한다. `MergedDir`을 렌더링할 때 커널이 이 화이트아웃 파일을 발견하면, 하위 레이어에 실제 파일이 존재하더라도 사용자에게는 해당 파일이 없는 것으로 표시한다.
{: .block-tip }

OverlayFS는 디렉토리의 가시성을 결정할 때 `dentry`(Directory Entry) 캐시를 효율적으로 활용하므로, 복잡한 레이어 구조에서도 파일 탐색 속도가 매우 빠르다. 하지만 수많은 작은 파일을 빈번하게 생성하고 삭제하는 워크로드에서는 `UpperDir`과 `LowerDir` 사이의 메타데이터 동기화 및 CoW 오버헤드로 인해 네이티브 파일시스템(ext4, xfs) 대비 성능 저하가 발생할 수 있다는 트레이드오프가 존재한다.

## Docker 아키텍처 및 런타임

도커의 초창기 설계는 모든 기능을 하나의 거대한 바이너리에 통합한 모놀리식(Monolithic) 구조였다. 그러나 컨테이너 생태계가 확장되고 표준화에 대한 요구가 거세짐에 따라, 도커는 기능을 잘게 쪼개어 유연하고 확장 가능한 마이크로서비스 아키텍처로 진화했다. 현재의 도커 엔진은 단순한 실행 도구를 넘어, 컨테이너의 생애주기를 관리하는 오케스트레이션 엔진과 표준화된 런타임 인터페이스가 유기적으로 결합된 복합 시스템이다.

### 도커 엔진 구조

도커 엔진은 클라이언트-서버 모델을 따르는 애플리케이션으로, 크게 세 가지 구성 요소가 상호작용하며 구동된다. 사용자의 명령을 받는 CLI, 실제 작업을 수행하는 백그라운드 프로세스인 데몬, 그리고 이 둘 사이를 잇는 통신 규격인 REST API가 그것이다.

#### 도커 데몬 (dockerd)

`dockerd`는 호스트 운영체제에서 지속적으로 실행되며 도커 API 요청을 수신하고 처리하는 핵심 프로세스다. 데몬은 이미지 빌드, 컨테이너 생성 및 실행, 네트워크 구성, 볼륨 관리 등 모든 중량급 작업을 총괄한다.

과거의 `dockerd`는 컨테이너 실행 로직까지 직접 담당했으나, 현재는 컨테이너 실행 및 관리를 하위 계층인 `containerd`에 위임하고 자신은 고수준의 오케스트레이션과 사용자 편의 기능에 집중한다. 데몬이 수행하는 주요 로직 흐름은 다음과 같다.

1.  **API 수신 및 인증**: 유닉스 소켓 또는 TCP를 통해 들어오는 요청을 검증하고 권한을 확인한다.
2.  **이미지 관리**: 요청받은 이미지가 로컬에 있는지 확인하고, 없으면 레지스트리에서 풀(Pull)하여 레이어별로 저장한다.
3.  **리소스 할당**: 컨테이너 실행 시 필요한 네임스페이스와 Cgroups 설정을 구성한다.
4.  **런타임 호출**: 설정 정보를 담은 OCI 번들(Bundle)을 생성하여 `containerd`에게 실행을 요청한다.

> **데몬 프로세스의 장애 격리 (Live Restore)**
> 
> 기본적으로 도커 데몬이 중단되면 실행 중인 모든 컨테이너도 함께 종료되거나 통제 불능 상태가 된다. 이를 방지하기 위해 도커는 `live-restore` 옵션을 제공한다. 이 옵션을 활성화하면 데몬이 업데이트되거나 비정상 종료되더라도, 실행 중인 컨테이너는 하위 런타임(containerd-shim)의 보호 아래 중단 없이 서비스를 유지할 수 있다.
{: .block-tip }

#### 도커 클라이언트 (CLI)

도커 클라이언트(`docker` 커맨드)는 사용자가 도커와 상호작용하는 기본 수단이다. 클라이언트는 실제 연산을 수행하지 않는 '얇은 계층'이며, 오직 사용자의 입력을 해석하여 도커 데몬에게 보낼 API 요청으로 변환하는 역할만 수행한다.

클라이언트는 데몬과 동일한 호스트에 존재할 수도 있고, 네트워크를 통해 원격에 있는 데몬을 제어할 수도 있다. 사용자가 `docker run` 명령을 입력하면, 클라이언트는 해당 명령의 옵션들을 JSON 형태로 직렬화하여 HTTP POST 요청을 생성하고 이를 도커 소켓(`/var/run/docker.sock`)으로 전송한다.

![](/docs/assets/img/2026-01-23-16-56-03.png)

#### 도커 API (REST API)

도커 API는 클라이언트와 데몬 사이의 공용 언어다. 표준 HTTP 프로토콜을 기반으로 설계된 RESTful API이며, 이를 통해 도커 엔진은 플랫폼에 독립적인 확장성을 확보한다. 도커 API는 버전 관리(Versioning)가 엄격하게 이루어져, 클라이언트와 데몬의 버전이 다르더라도 하위 호환성을 유지할 수 있도록 설계되었다.

* **엔드포인트 구조**: `/v1.41/containers/create`와 같이 버전 정보와 리소스 경로가 결합된 형태를 취한다.
* **통신 프로토콜**: 보안 강화를 위해 로컬에서는 유닉스 도메인 소켓(Unix Domain Socket)을 기본으로 사용하며, 원격 제어가 필요한 경우 TLS 인증이 적용된 TCP 포트(기본 2376)를 사용한다.

도커 API의 공개된 규격 덕분에, 공식 CLI뿐만 아니라 Portainer 같은 GUI 관리 도구, Kubernetes의 이전 방식인 DockerShim, 그리고 다양한 언어의 SDK(Go, Python, Java)들이 도커 데몬을 직접 제어할 수 있게 되었다.

### 컨테이너 런타임 계층

도커 엔진이 현대적인 아키텍처로 탈바꿈하면서 가장 큰 변화를 맞이한 부분은 컨테이너의 실행 기능을 계층화된 런타임 구조로 분리한 것이다. 과거에는 도커 데몬이 컨테이너의 생명 주기 전반을 직접 통제했으나, 현재는 고수준 런타임(High-level Runtime)과 저수준 런타임(Low-level Runtime)으로 역할을 분담하여 운영 안정성과 이식성을 동시에 확보한다. 이 구조는 컨테이너 산업의 표준인 OCI(Open Container Initiative) 규격을 준수하며, 다양한 런타임 기술이 플러그인 형태로 결합될 수 있는 유연한 생태계를 형성한다.

#### containerd (컨테이너 관리)

`containerd`는 도커에서 분리되어 CNCF(Cloud Native Computing Foundation)의 졸업 프로젝트로 안착한 산업 표준 고수준 컨테이너 런타임이다. 도커 데몬의 하부에서 실행되며, 이미지 전송, 스토리지 관리, 컨테이너 실행 명령 전달, 네트워크 인터페이스 관리 등 실제 컨테이너 구동에 필요한 중량급 로직을 담당한다.

`containerd`의 아키텍처는 내부 시스템이 gRPC를 통해 통신하는 서비스 지향적 구조를 가진다. 주요 내부 구성 요소로는 이미지 배포를 담당하는 Content Service, 레이어 스냅샷을 관리하는 Snapshot Service, 그리고 컨테이너의 상태를 추적하는 Runtime Service 등이 존재한다. `containerd`는 스스로를 '단순하고 견고하며 확장 가능한' 런타임으로 정의하며, 쿠버네티스의 CRI(Container Runtime Interface)를 직접 지원함으로써 도커 데몬 없이도 독자적인 오케스트레이션의 핵심 엔진으로 기능할 수 있다.

> **Snapshorter의 레이어 관리 전략**
> 
> `containerd`는 OverlayFS와 같은 스토리지 드라이버를 '스냅샷터(Snapshotter)'라는 인터페이스로 추상화한다. 이는 파일시스템의 변경 사항을 증분(Incremental) 방식으로 캡처하여 저장 공간의 중복을 제거하고, 새로운 컨테이너가 생성될 때 기존 이미지 레이어를 빠르게 마운트하여 기동 시간을 단축하는 핵심 로직이다.
{: .block-tip }

#### runC (OCI 런타임)

`runC`는 OCI 규격을 준수하는 공식 저수준 런타임으로, 실제 리눅스 커널의 네임스페이스와 Cgroups를 설정하고 프로세스를 실행하는 '실무자' 역할을 수행한다. 도커가 자사의 컨테이너 기술인 `libcontainer`를 기증하여 만들어진 이 도구는 독립적인 바이너리로 존재하며, 오직 컨테이너를 '생성'하고 '실행'하는 데만 집중한다.

`runC`의 동작 방식은 매우 단기적이다. 고수준 런타임으로부터 OCI 번들(설정 파일인 `config.json`과 루트 파일시스템)을 전달받으면, `runC`는 해당 설정을 기반으로 격리된 환경을 구축한 뒤 컨테이너 내부의 프로세스를 기동(exec)한다. 프로세스가 성공적으로 실행되어 제어권이 컨테이너 내부로 넘어가면, `runC` 프로세스는 즉시 종료된다. 이러한 설계는 런타임 자체가 시스템 자원을 상주하며 소비하는 것을 방지하여 극도의 효율성을 제공한다.

![](/docs/assets/img/2026-01-23-16-56-09.png)

#### containerd-shim

`runC`가 프로세스를 실행하고 사라진다면, 실행된 컨테이너 프로세스의 관리(Standard I/O 유지, 종료 상태 보고 등)는 누가 담당할 것인가? 이 공백을 메우는 것이 바로 `containerd-shim`이다. 컨테이너가 생성될 때마다 각 컨테이너당 하나의 `shim` 프로세스가 함께 생성된다.

`containerd-shim`의 존재 이유는 세 가지 기술적 필연성에서 기인한다.
1.  **데몬과의 결합 해제**: 도커 데몬이나 `containerd`가 재시작되더라도, 컨테이너 프로세스의 부모 프로세스 역할을 `shim`이 수행하고 있으므로 컨테이너는 중단 없이 실행을 유지할 수 있다.
2.  **파일 서술자(FD) 유지**: 컨테이너의 표준 입력/출력(stdin/stdout) 스트림을 열어두어 로그 수집 및 대화형 쉘 연결을 가능하게 한다.
3.  **상태 보고**: 컨테이너 내부의 PID 1 프로세스가 종료되면 그 종료 코드(Exit Code)를 수거하여 `containerd`에게 보고하는 '장례식' 절차를 수행한다.

> **Shim의 물리적 존재 가치**
> 
> 만약 `shim`이 없다면 `containerd`가 모든 컨테이너의 파일 서술자를 직접 들고 있어야 한다. 이는 `containerd` 업그레이드 시 모든 컨테이너의 연결이 끊어지는 대참사로 이어진다. `shim`은 컨테이너와 데몬 사이의 '완충지대'로서 시스템의 고가용성을 보장하는 핵심 설계이다.
{: .block-warning }

![](/docs/assets/img/2026-01-23-16-56-15.png)

#### gVisor (샌드박스 런타임)

전통적인 컨테이너는 호스트 운영체제의 커널을 직접 공유하며, 시스템 콜(System Call) 인터페이스를 통해 하드웨어 자원을 요청한다. 이러한 구조는 성능 면에서는 유리하지만, 커널의 광대한 공격 표면(Attack Surface)을 그대로 노출시킨다는 보안적 취약점을 안고 있다. Google에서 개발한 **gVisor**는 이러한 한계를 극복하기 위해 사용자 공간(User-space)에서 동작하는 별도의 독립적인 커널인 **Sentry**를 도입한 샌드박스 런타임이다.

gVisor의 핵심 아키텍처는 애플리케이션과 호스트 커널 사이에 거대한 필터링 계층을 배치하는 것이다. 애플리케이션이 시스템 콜을 호출하면, 호스트 커널이 이를 처리하기 전에 gVisor의 Sentry가 이를 가로챈다. Sentry는 리눅스 커널의 상당 부분을 Go 언어로 재구현한 소프트웨어로, 대부분의 시스템 콜을 호스트 커널로 전달하지 않고 사용자 공간에서 직접 처리(Emulation)한다.

> **Sentry와 Gofer의 협업 모델**
> 
> gVisor는 보안을 위해 파일 시스템 접근조차 직접 수행하지 않는다. Sentry는 네트워크와 연산만을 담당하며, 파일 I/O가 필요할 경우 **Gofer**라고 불리는 별도의 프로세스를 통해 제한된 9P 프로토콜 통신으로만 데이터를 주고받는다. 이는 Sentry가 탈취당하더라도 공격자가 호스트의 파일 시스템에 직접 접근하는 것을 원천 차단하기 위한 다중 방어(Defense in Depth) 전략이다.
{: .block-tip }

gVisor는 시스템 콜을 가로채는 방식에 따라 두 가지 플랫폼 모드를 지원한다.
* **Ptrace 플랫폼**: 표준 리눅스 `ptrace` 기능을 사용하여 시스템 콜을 인터셉트한다. 별도의 특수 권한이 필요 없어 어디서든 실행 가능하지만, 모든 시스템 콜마다 컨텍스트 스위칭이 발생하여 성능 저하가 극심하다.
* **KVM 플랫폼**: 호스트의 KVM(Kernel-based Virtual Machine) 기능을 활용한다. Sentry가 가상 머신 모니터(VMM)처럼 동작하여 하드웨어 가속을 통해 시스템 콜 가로채기 성능을 최적화한다.

gVisor의 도입은 필연적으로 **성능과 보안의 트레이드오프**를 발생시킨다. 시스템 콜 처리가 호스트 커널에서 직접 이루어지는 것이 아니라 Go 언어로 작성된 에뮬레이션 레이어를 거치기 때문에, I/O 집약적인 애플리케이션에서는 일반 컨테이너 대비 상당한 레이턴시 증가가 발생한다. 그러나 다중 테넌트(Multi-tenant) 클라우드 환경에서 신뢰할 수 없는 코드를 실행해야 하는 경우, gVisor는 가상 머신 수준의 격리 안정성을 제공하면서도 컨테이너의 가벼운 운영 모델을 유지할 수 있는 최적의 대안이 된다.

![](/docs/assets/img/2026-01-23-16-56-20.png)

#### Kata Containers (VM 기반 런타임)

gVisor가 소프트웨어적으로 시스템 콜을 흉내 낸다면, **Kata Containers**는 하드웨어 수준의 가상화 기술을 컨테이너 생태계에 직접 이식한 기술이다. Kata Containers의 본질은 "컨테이너처럼 동작하는 극도로 가벼운 가상 머신(Micro-VM)"이다. 각 컨테이너는 독립된 전용 커널을 가진 마이크로 VM 내부에서 실행되며, 이를 통해 가상 머신이 제공하는 물리적 수준의 격리와 컨테이너가 제공하는 신속한 배포 경험을 결합한다.

Kata Containers의 구동 원리는 다음과 같은 로우 레벨 메커니즘을 기반으로 한다.
1.  **하이퍼바이저 최적화**: QEMU, Firecracker, 또는 Cloud Hypervisor와 같은 가벼운 VMM을 사용하여 VM 부팅 오버헤드를 수백 밀리초 단위로 단축한다.
2.  **공유 커널 및 에이전트**: VM 내부에는 최소한의 기능만 남긴 전용 리눅스 커널이 로드되며, `kata-agent`가 상주하며 호스트의 지시를 받아 컨테이너 프로세스를 관리한다.
3.  **리소스 브릿징**: 호스트와 VM 사이의 통신은 `virtio-fs`를 통한 파일 시스템 공유와 `vhost-net`을 통한 네트워크 가속을 사용하여 VM 기반 가상화의 고질적인 I/O 병목을 최소화한다.

> **Kata Containers의 하드웨어 요구사항**
> 
> Kata Containers는 Intel VT-x 또는 AMD-V와 같은 하드웨어 가상화 기술을 필수로 요구한다. 따라서 클라우드 환경에서 Kata Containers를 구동하려면 호스트 자체가 가상화 중첩(Nested Virtualization)을 지원해야 하며, 이는 인프라 비용 상승의 요인이 될 수 있다.
{: .block-warning }

Kata Containers는 격리 수준이 가장 높기 때문에 금융권 시스템, 고도의 보안이 요구되는 데이터 처리 워크로드, 또는 서로 다른 팀의 코드가 동일한 물리 서버에서 실행되는 환경에서 강력한 힘을 발휘한다. 일반 컨테이너(`runC`)와 비교했을 때 메모리 점유율이 높고 기동 속도가 미세하게 느리지만, 보안 경계가 커널 레벨에서 명확히 분리된다는 점은 엔지니어링 측면에서 대체 불가능한 가치를 제공한다.

![](/docs/assets/img/2026-01-23-16-56-25.png)

### 실행 표준 및 통신

도커가 세상을 바꾼 것은 단순히 기술의 우수성 때문이 아니라, 컨테이너를 어떻게 만들고 실행할지에 대한 '약속'을 표준화했기 때문이다. 이 표준화는 특정 벤더에 종속되지 않는 거대한 에코시스템을 탄생시켰으며, 서로 다른 런타임과 도구들이 마치 레고 블록처럼 맞물려 돌아갈 수 있는 기반이 되었다.

#### OCI (Open Container Initiative) 규격

OCI는 리눅스 재단의 프로젝트로, 컨테이너 산업의 파편화를 막기 위해 설립된 표준화 기구다. OCI는 크게 두 가지 핵심 규격을 정의한다.

**1. 런타임 규격 (Runtime Spec)**
컨테이너의 '상태'와 '실행'에 관한 표준이다. 컨테이너를 생성하기 위해 필요한 설정 파일(`config.json`)의 형식과 컨테이너의 생애주기(create, start, stop, delete)를 제어하는 시스템 콜 명령어를 규정한다. `runC`는 이 규격을 구현한 표준 참조 모델이다.

**2. 이미지 규격 (Image Spec)**
컨테이너 이미지가 어떤 구조로 아카이브되어야 하는지에 대한 표준이다. 레이어들의 파일 시스템 구조, 설정 파일(JSON), 그리고 이들을 묶어주는 매니페스트(Manifest)의 형식을 정의한다. 이를 통해 도커에서 빌드한 이미지를 쿠버네티스나 다른 OCI 준수 런타임에서도 수정 없이 그대로 실행할 수 있게 된다.

#### 도커 소켓 (docker.sock)

도커 소켓(`/var/run/docker.sock`)은 도커 데몬이 API 요청을 대기하는 유닉스 도메인 소켓(Unix Domain Socket) 파일이다. 이는 동일한 호스트 내에서 실행되는 클라이언트와 서버 간의 IPC(Inter-Process Communication)를 위한 엔드포인트로, TCP/IP 스택을 거치지 않고 커널 내부의 메모리 복사를 통해 통신하므로 오버헤드가 극도로 적다.

**1. 유닉스 도메인 소켓의 보안 모델**
`docker.sock`은 파일 시스템의 권한 체계를 통해 접근을 제어한다. 기본적으로 이 소켓 파일은 `root` 사용자와 `docker` 그룹에 속한 사용자에게만 읽기/쓰기 권한을 부여한다. 사용자가 `docker ps`와 같은 명령을 내릴 때, 클라이언트는 `AF_UNIX` 주소 체계를 사용하여 이 소켓에 접속하며, 커널은 `SO_PEERCRED` 옵션을 통해 요청을 보낸 프로세스의 UID/GID를 검증한다.

**2. 도커 내부의 도커 (Docker-in-Docker, DinD)와 소켓 마운트**
개발 환경이나 CI/CD 파이프라인에서 컨테이너 내부에서 도커 명령을 실행해야 하는 경우가 빈번하다. 이때 가장 흔히 사용되는 방식이 호스트의 `docker.sock`을 컨테이너 내부로 바인드 마운트(Bind Mount)하는 것이다.

> **소켓 마운트의 치명적 위험성**
> 
> 컨테이너 내부에 `docker.sock`을 노출하는 것은 해당 컨테이너에게 호스트 운영체제의 **루트(root) 권한을 통째로 넘겨주는 것**과 다름없다. 컨테이너 내부의 프로세스는 도커 API를 통해 호스트의 파일 시스템을 마운트한 새로운 특권 컨테이너(Privileged Container)를 생성할 수 있으며, 이를 통해 호스트 커널을 장악하거나 데이터를 탈취하는 '컨테이너 탈출' 공격이 매우 용이해진다.
{: .block-warning }

![](/docs/assets/img/2026-01-23-16-56-33.png)

#### CRI (Container Runtime Interface)

CRI는 쿠버네티스(Kubernetes)가 다양한 컨테이너 런타임을 지원하기 위해 정의한 gRPC 기반의 통신 규격이다. 과거 쿠버네티스는 도커만을 지원하기 위해 내부에 `DockerShim`이라는 전용 코드를 유지했으나, 런타임 생태계가 다변화되면서 이를 표준화된 인터페이스로 분리하게 되었다.

**1. CRI 아키텍처의 계층 구조**
CRI는 크게 두 가지 서비스 인터페이스로 구성된다.
* **RuntimeService**: 컨테이너의 생명 주기 관리(생성, 시작, 중단, 삭제)와 샌드박스(Pod) 구성을 담당한다.
* **ImageService**: 이미지 풀링, 조회, 삭제 등 이미지 관련 작업을 처리한다.

쿠버네티스의 에이전트인 `kubelet`은 gRPC 클라이언트로서 동작하며, 호스트에 상주하는 CRI 런타임(예: containerd, CRI-O)의 gRPC 서버에 요청을 보낸다. 런타임은 이 요청을 받아 실제 OCI 런타임(`runC`)을 호출하여 컨테이너를 구동한다.

**2. 도커의 CRI 대응 (DockerShim의 퇴장)**
도커는 원래 CRI 규격을 직접 구현하지 않았다. 이로 인해 쿠버네티스는 도커를 사용하기 위해 `kubelet` 내부에 별도의 어댑터 계층을 두어야 했으나, 이는 유지보수의 비효율을 초래했다. 결국 쿠버네티스 1.24 버전부터 `DockerShim`이 완전히 제거되었으며, 현재는 도커 엔진 대신 그 하부 런타임인 `containerd`를 직접 CRI 엔드포인트로 연결하는 방식이 표준으로 자리 잡았다.

## 이미지 빌드 및 레이어 관리

도커 이미지는 컨테이너 실행에 필요한 모든 파일과 메타데이터를 포함하는 정적인 읽기 전용 템플릿이다. 이미지는 단순히 파일들의 묶음이 아니라, 효율적인 저장과 배포를 위해 논리적으로 분리된 '레이어'들이 유기적으로 결합된 불변(Immutable)의 데이터 구조체이다. 이 계층 구조는 컨테이너 기술의 핵심인 '재사용성'과 '속도'를 지탱하는 물리적 기반이 된다.

### 이미지 추상화

이미지의 추상화는 복잡한 파일 시스템의 상태를 스냅샷 형태로 캡처하고, 이를 고유한 식별자를 가진 전송 가능한 단위로 변환하는 과정이다.

#### 도커 이미지 (Image)

도커 이미지는 애플리케이션을 구동하기 위한 '실행 환경의 박제'이다. 여기에는 코드, 런타임, 시스템 라이브러리, 환경 변수, 설정 파일 등이 포함된다. 이미지는 상태를 가지지 않으며(Stateless), 한 번 빌드되면 절대 변경되지 않는 불변성을 가진다.

이미지의 정체성은 **이미지 ID**에 의해 결정된다. 이는 이미지의 구성 요소와 설정 정보를 담은 JSON 설정 파일의 해시값(SHA256)이다. 만약 이미지 내의 파일 하나가 바뀌거나 환경 변수 설정 하나가 변경되면, 전체 해시값이 달라지므로 완전히 새로운 이미지로 취급된다. 이러한 설계는 배포 시 데이터 정합성을 보장하고, '내 로컬에서는 되는데 서버에서는 안 된다'는 고전적인 문제를 원천적으로 봉쇄한다.

#### 이미지 레이어 (ReadOnly Layer)

도커 이미지는 `Dockerfile`의 각 명령어(`FROM`, `RUN`, `COPY` 등)가 실행될 때마다 생성되는 여러 개의 읽기 전용 레이어로 구성된다. 각 레이어는 이전 레이어와의 '차이점(Diff)'만을 저장한다.

예를 들어, 베이스 이미지 위에 패키지를 설치하는 `RUN apt-get update` 명령은 새로운 레이어를 생성하며, 이 레이어에는 업데이트된 패키지 리스트와 관련 메타데이터만이 저장된다. 이 레이어들은 호스트의 스토리지 드라이버에 의해 관리되며, 여러 이미지 사이에서 동일한 레이어가 존재할 경우 이를 공유하여 디스크 공간을 절약한다.

> **레이어의 원자성과 무결성**
> 
> 각 레이어는 자신만의 `ChainID`를 가지는데, 이는 해당 레이어 자체의 해시값과 하위 레이어의 `ChainID`를 결합하여 산출된다. 따라서 중간의 레이어 하나를 임의로 교체하는 것은 불가능하며, 전체 레이어 체인의 무결성이 하드웨어 레벨의 암호화 검증을 통해 보장된다.
{: .block-tip }

#### 컨테이너 레이어 (Writable Layer)

이미지가 정적인 '박제'라면, 컨테이너 레이어는 그 박제 위에 씌워지는 얇고 투명한 '메모장'과 같다. 도커 엔진은 이미지를 기반으로 컨테이너를 생성할 때, 하단의 읽기 전용 레이어들(ReadOnly Layers) 위에 단 하나의 쓰기 가능한 계층(Writable Layer)을 추가한다. 컨테이너 내부에서 발생하는 모든 파일 생성, 수정, 삭제 작업은 오직 이 최상단 레이어에만 기록된다.

이 메커니즘의 핵심은 **Copy-on-Write (CoW)** 전략이다. 만약 컨테이너 내부의 프로세스가 하위 이미지 레이어에 존재하는 파일을 수정하려고 시도하면, 스토리지 드라이버는 즉시 해당 파일을 상위 컨테이너 레이어로 복사(Copy)한 뒤 수정 작업을 수행한다. 이 과정은 사용자나 애플리케이션 입장에서는 완전히 투명(Transparent)하게 이루어지지만, 하부 구조에서는 다음과 같은 물리적 비용이 발생한다.

> **CoW의 입출력 페널티**
> 
> 대용량 파일에 대한 첫 번째 쓰기 작업은 파일 전체를 하위 레이어에서 상위 레이어로 복사하는 과정을 수반하므로, 상당한 I/O 레이턴시를 유발한다. 따라서 데이터베이스의 로그 파일이나 대규모 데이터 세트와 같이 쓰기 작업이 빈번하고 성능이 중요한 데이터는 컨테이너 레이어가 아닌 **볼륨(Volumes)**이나 **바인드 마운트(Bind Mounts)**를 통해 호스트의 네이티브 파일 시스템에 직접 기록하는 것이 엔지니어링 측면에서 타당하다.
{: .block-warning }

컨테이너가 삭제되면 이 쓰기 레이어에 기록된 모든 데이터도 함께 소멸하며, 하단의 이미지 레이어는 본래의 무결성을 유지한 채 다른 컨테이너에 의해 재사용된다. 이는 동일한 이미지를 기반으로 수백 개의 컨테이너를 동시에 띄우더라도, 물리적인 디스크 공간은 이미지 용량에 각 컨테이너의 미세한 변경분(Diff)만이 추가되는 수준으로 억제되는 이유다.

![](/docs/assets/img/2026-01-23-16-56-45.png)

#### 이미지 매니페스트 (Manifest)

이미지 매니페스트는 도커 이미지를 구성하는 모든 컴포넌트를 정의하고 유기적으로 연결하는 '설계 명세서'이다. 매니페스트는 JSON 형식의 텍스트 파일로, 이미지의 메타데이터, 지원하는 아키텍처, 그리고 실제 데이터가 담긴 레이어들의 해시값(Digest) 목록을 포함한다.

매니페스트는 컨테이너 레지스트리(Registry)에서 이미지를 풀(Pull)할 때 가장 먼저 다운로드되는 파일이다. 도커 엔진은 이 매니페스트를 분석하여 어떤 레이어들을 내려받아야 하는지, 그리고 각 레이어의 무결성을 어떻게 검증할지 결정한다.

**1. 매니페스트의 구성 요소**
* **Schema Version**: 매니페스트 파일의 형식을 정의한다. (현재 v2가 표준)
* **Media Type**: 각 데이터의 유형을 식별한다. (예: `application/vnd.docker.image.rootfs.diff.tar.gzip`)
* **Config**: 이미지의 실행 환경 설정(환경 변수, 노출 포트, 엔트리포인트 등)을 담은 별도의 JSON 파일에 대한 식별자다.
* **Layers**: 이미지의 각 파일 시스템 레이어에 대한 해시값과 크기 정보를 담은 리스트다.

**2. 멀티 아키텍처 지원 (Manifest List)**
현대적인 클라우드 환경에서는 x86_64뿐만 아니라 ARM64 등 다양한 CPU 아키텍처가 혼재한다. 도커는 이를 지원하기 위해 **매니페스트 리스트(Manifest List)** 또는 **OCI Index**라 불리는 상위 개념을 사용한다. 하나의 태그(예: `ubuntu:latest`) 아래에 각 아키텍처별 매니페스트 정보를 묶어두면, 도커 클라이언트는 현재 호스트의 아키텍처에 맞는 최적의 매니페스트를 자동으로 선택하여 내려받는다.

![](/docs//assets/img/2026-01-25-00-00-15.png)

매니페스트의 존재는 이미지를 '내용 중심 주소 지정(Content-addressable)' 방식으로 관리할 수 있게 한다. 매니페스트 파일 자체의 해시값이 곧 이미지의 고유 식별자가 되며, 이를 통해 데이터의 위변조를 원천적으로 방지하고 효율적인 캐싱 아키텍처를 구축할 수 있다.

### 저장 및 효율화 매커니즘

이미지 시스템의 진정한 가치는 단순히 파일을 묶어두는 것이 아니라, 이를 어떻게 최소한의 자원으로 관리하느냐에 달려 있다. 도커는 파일 시스템의 중복을 제거하고 네트워크 전송량을 최적화하기 위해 정교한 엔지니어링 기법들을 동원한다.

#### Copy-on-Write (CoW)

앞서 컨테이너 레이어에서 언급된 CoW는 도커의 전체 스토리지 아키텍처를 관통하는 핵심 철학이다. 리눅스 커널의 파일 시스템 기능을 활용하는 CoW는 '수정이 발생하기 전까지는 데이터를 복사하지 않는다'는 원칙을 고수한다.

**1. 레이어 공유와 성능**
도커의 모든 레이어는 고유한 ID를 가지며, 동일한 내용의 레이어는 시스템 내에서 단 한 번만 저장된다. 이는 `docker pull` 명령 시 "Already exists"라는 메시지로 나타난다. 하지만 CoW는 레이어가 깊어질수록 성능 문제를 유발할 수 있다. 하위 10번째 레이어에 있는 파일을 수정하려고 하면, 커널은 해당 파일을 찾기 위해 상위 레이어들로부터 아래로 차례대로 검색(Lookup)해야 하며, 발견 즉시 10단계를 거슬러 올라가 최상단 레이어로 복사해야 한다.

**2. 스토리지 드라이버별 구현 차이**
CoW의 구체적인 동작 방식은 사용하는 스토리지 드라이버에 따라 다르다.
* **OverlayFS**: 디렉토리 수준에서 CoW를 수행한다. 파일 수정 시 전체 파일을 복사하므로 구현이 단순하고 속도가 빠르다.
* **Btrfs / ZFS**: 블록(Block) 수준에서 CoW를 수행한다. 파일의 일부만 수정할 경우 바뀐 블록만을 새로 할당하므로 대용량 파일 수정 시 효율적이다.
* **Devicemapper**: 가상 블록 장치를 생성하여 세밀하게 제어하지만, 설정이 복잡하고 오버헤드가 커 현재는 거의 사용되지 않는다.

#### 콘텐츠 주소 지정 (CAS)

콘텐츠 주소 지정(Content-Addressable Storage, CAS)은 데이터를 저장된 물리적 위치가 아닌, 데이터 그 자체의 내용(Content)을 나타내는 해시값으로 식별하고 접근하는 저장 아키텍처다. 도커는 이 기술을 통해 이미지 레이어와 메타데이터의 무결성을 보장하며, 시스템 전체에서 중복된 데이터를 획기적으로 제거한다.

**1. 해시 식별자 (Digest) 생성 메커니즘**
도커의 모든 레이어와 설정 파일은 SHA256 알고리즘을 거쳐 고유한 체크섬(Checksum)인 **디제스트(Digest)**를 부여받는다. 예를 들어, 특정 레이어의 파일 시스템 바이너리 데이터를 해싱하여 `sha256:a3ed...`와 같은 식별자가 생성되면, 이 값은 해당 데이터의 지문(Fingerprint)이 된다. 만약 레이어 내부의 파일 비트 하나라도 변경되면 해시값은 완전히 달라지며, 이는 곧 다른 데이터로 취급된다.

**2. 레이어 ID와 DiffID의 분리**
엔지니어링 수준에서 도커는 두 종류의 해시를 관리한다.
* **DiffID**: 레이어가 압축되지 않은 상태(Tarball)의 데이터 해시값이다. 이미지 매니페스트와 설정 파일에서 레이어의 논리적 구성을 정의할 때 사용된다.
* **ChainID**: 특정 레이어가 하위 레이어들에 종속되어 있음을 나타내는 고유 식별자다. `ChainID(n) = SHA256(ChainID(n-1) + DiffID(n))` 공식을 통해 계산되며, 이를 통해 이미지 레이어의 적층 순서가 변조되지 않았음을 수학적으로 증명한다.

> **CAS의 부작용: CPU 오버헤드**
> 
> 모든 데이터를 해싱하는 과정은 빌드와 푸시(Push)/풀(Pull) 시 CPU 자원을 소모한다. 특히 대용량 레이어를 처리할 때 입출력 속도보다 해싱 연산 속도가 병목이 될 수 있다. 하지만 이를 통해 얻는 데이터 신뢰성과 저장 효율(De-duplication)의 가치가 비용보다 월등히 높기 때문에 현대의 모든 컨테이너 런타임은 이 아키텍처를 채택하고 있다.
{: .block-warning }

![](/docs//assets/img/2026-01-25-00-00-24.png)

#### 가비지 컬렉션 (Image GC)

도커 이미지는 불변(Immutable) 레이어의 집합이므로, 이미지 빌드와 삭제가 반복될수록 호스트의 디스크에는 어떤 이미지에도 속하지 않는 유령 레이어들이 쌓이게 된다. 가비지 컬렉션(GC)은 이러한 불필요한 자원을 추적하여 물리적으로 제거하는 청소 메커니즘이다.

**1. Dangling Image와 참조 카운팅**
태그가 지정되지 않은(None:None) 이미지를 **댕글링(Dangling) 이미지**라 부른다. 이는 보통 동일한 이름으로 새 이미지를 빌드했을 때 기존 이미지가 밀려나면서 발생한다. 도커 데몬은 각 레이어에 대해 참조 카운트(Reference Count)를 관리하며, 어떤 태그나 컨테이너에서도 참조하지 않는 레이어를 삭제 대상으로 분류한다.

**2. 삭제 알고리즘의 안전성**
도커의 GC는 매우 보수적으로 작동한다. 단순히 사용되지 않는 레이어라고 즉시 삭제하는 것이 아니라, 실행 중인(또는 정지된) 컨테이너가 해당 레이어를 사용하고 있는지 전수 조사한다. 만약 단 하나의 컨테이너라도 특정 레이어를 참조하고 있다면, 그 레이어와 연결된 하위 레이어 체인 전체가 보존된다.

* **docker image prune**: 댕글링 이미지만을 삭제한다.
* **docker system prune -a**: 사용되지 않는 모든 이미지, 컨테이너, 네트워크를 일괄 삭제하여 가용 공간을 최대화한다.

#### 레이어 캐싱 (Layer Caching)

레이어 캐싱은 `Dockerfile` 빌드 속도를 극대화하는 도커의 가장 강력한 최적화 기술이다. 도커는 이미 빌드된 레이어를 재사용함으로써 중복된 연산과 네트워크 전송을 회피한다.

**1. 캐시 히트(Cache Hit) 판정 로직**
도커 빌더(BuildKit)는 각 명령어를 실행하기 전 다음 세 가지 조건을 검사한다.
* **명령어의 일치**: `RUN apt-get install`과 `RUN apt-get update`는 서로 다른 명령어로 간주되어 캐시가 깨진다.
* **부모 레이어의 일치**: 이전 단계의 레이어가 캐시 히트여야만 현재 단계의 캐시를 검토한다.
* **빌드 컨텍스트의 변경**: `COPY`나 `ADD` 명령의 경우, 복사하려는 실제 파일의 해시값을 비교하여 파일 내용이 조금이라도 바뀌었다면 캐시를 무효화(Invalidate)한다.

**2. 캐시 체인 무효화 (Cache Invalidation Flow)**
캐싱 전략에서 가장 주의해야 할 점은 **순차적 무효화**다. `Dockerfile`의 중간 단계에서 캐시가 깨지면, 그 이후의 모든 명령어는 캐시 히트 여부와 관계없이 새로 실행되어 레이어를 생성한다.

> **전략적 Dockerfile 작성법**
> 
> 변경이 잦은 소스 코드 복사(`COPY . .`) 명령은 `Dockerfile`의 최하단에 배치하고, 변경이 드문 패키지 설치(`RUN apt-get ...`)나 환경 설정 명령은 상단에 배치하는 것이 캐시 효율을 극대화하는 엔지니어링의 정석이다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-00-32.png)

### 이미지 배포 아키텍처

이미지가 로컬 빌드 단계를 넘어서 협업과 운영 환경으로 전달되기 위해서는 신뢰할 수 있는 중앙 저장소와 효율적인 전송 규격이 필요하다. 도커의 배포 아키텍처는 전 세계 어디서든 동일한 이미지를 빠르게 내려받을 수 있도록 설계된 분산형 저장 체계를 지향한다.

#### 도커 레지스트리 (Registry)

도커 레지스트리는 컨테이너 이미지를 저장하고 배포하는 서버 측 애플리케이션이다. 레지스트리는 이미지의 실제 데이터인 **Blob(Binary Large Object)**과 이미지의 구조를 설명하는 **Manifest**를 분리하여 관리한다.

* **저장 구조**: 레지스트리는 CAS 원칙에 따라 레이어 데이터를 저장한다. 서로 다른 이미지가 동일한 레이어를 포함하고 있다면, 레지스트리 내부적으로는 해당 레이어를 한 번만 저장하여 스토리지 공간을 최적화한다.
* **Push/Pull 프로토콜**: 도커 클라이언트는 HTTP API를 통해 레지스트리와 통신한다. `push` 시에는 로컬 레이어의 해시를 레지스트리에 먼저 쿼리하고, 이미 존재하는 레이어라면 전송을 생략하는 '레이어 스킵' 기술을 사용한다.

#### 도커 허브 (Docker Hub)

도커 허브는 전 세계에서 가장 거대한 컨테이너 이미지 SaaS(Software as a Service) 레지스트리이자, 도커 생태계의 중앙 집중식 허브다. 도커 엔진을 설치한 후 별도의 설정을 하지 않고 `docker pull` 명령을 내리면, 데몬은 기본적으로 `index.docker.io`라는 도커 허브의 엔드포인트를 향한다.

도커 허브는 단순히 이미지를 보관하는 창고를 넘어, 다음과 같은 고도화된 배포 서비스를 제공한다.
* **공식 이미지 (Official Images)**: 도커와 소프트웨어 벤더가 협력하여 보안 취약점을 관리하고 최적화한 검증된 이미지 세트다. 이 이미지들은 최소한의 설치 기반(Alpine, Slim 등)을 제공하며, 명확한 문서화와 보안 패치 주기를 보장받는다.
* **자동 빌드 (Automated Builds)**: GitHub나 GitLab 같은 소스 코드 저장소와 연동하여 코드 푸시 발생 시 레지스트리 측에서 직접 이미지를 빌드하는 파이프라인 기능을 제공한다.
* **보안 스캐닝**: Snyk과 같은 보안 솔루션과 통합되어 레이어 내부의 라이브러리 취약점(CVE)을 자동으로 분석하고 보고한다.

> **Rate Limiting (전송량 제한) 정책의 도입**
> 
> 도커 허브는 익명 사용자와 무료 사용자에 대해 특정 시간당 풀(Pull) 횟수를 제한하는 정책을 시행하고 있다. 이는 무분별한 이미지 요청으로 인한 대역폭 낭비를 막기 위한 엔지니어링적 제동 장치다. 대규모 프로덕션 환경에서는 이 제한이 서비스 중단으로 이어질 수 있으므로, 내부 프라이빗 레지스트리에 이미지를 미러링(Mirroring)하거나 유료 플랜을 통해 쿼터를 확보하는 것이 필수적이다.
{: .block-warning }

#### 프라이빗 레지스트리

기업 보안 정책이나 네트워크 성능상의 이유로 도커 허브를 사용할 수 없는 경우, 자체적인 프라이빗 레지스트리를 구축한다. 이는 폐쇄망 환경에서 이미지 유출을 방지하고, 내부 대역폭을 활용하여 기가바이트 단위의 이미지를 초고속으로 전송하기 위한 선택이다.

**1. Docker Distribution (Registry v2)**
도커가 오픈소스로 공개한 `registry:2` 이미지는 프라이빗 레지스트리의 참조 모델이다. Go 언어로 작성되었으며, HTTP API v2 규격을 구현한다. 이 시스템은 무상태(Stateless) 아키텍처로 설계되어 확장이 용이하며, 실제 데이터 저장소(Storage Backend)로 로컬 파일 시스템뿐만 아니라 S3, Azure Blob, GCS 등 클라우드 스토리지를 추상화하여 연결할 수 있다.

**2. 엔터프라이즈급 관리 도구 (Harbor)**
단순한 저장소 기능을 넘어, 기업용 환경을 위해 CNCF 프로젝트인 **Harbor**가 널리 사용된다. Harbor는 기본 레지스트리 위에 다음과 같은 강력한 관리 계층을 추가한다.
* **RBAC (역할 기반 접근 제어)**: 프로젝트 단위로 이미지 접근 권한을 세밀하게 통제한다.
* **복제 (Replication)**: 서로 다른 지역(Region)의 레지스트리 간에 이미지를 자동으로 동기화하여 가용성을 높인다.
* **이미지 서명 (Notary/Cosign)**: 이미지가 신뢰할 수 있는 빌드 시스템에서 생성되었음을 증명하는 디지털 서명을 관리하여 공급망 공격(Supply Chain Attack)을 방어한다.

![](/docs//assets/img/2026-01-25-00-00-39.png)

프라이빗 레지스트리 운영 시 가장 큰 기술적 도전 과제는 **스토리지 가비지 컬렉션**이다. 이미지를 수시로 업로드하고 삭제하더라도 실제 물리 데이터(Blob)는 레지스트리에 남아 있는 경우가 많다. 관리자는 주기적으로 레지스트리를 읽기 전용 모드로 전환한 뒤 GC 작업을 수행하여 불필요한 레이어를 정리해야 하며, 이 과정에서의 다운타임을 최소화하는 것이 운영 노하우의 핵심이다.

## 컨테이너 실행 및 제어

이미지가 정적인 설계도라면, 컨테이너는 그 설계도가 메모리에 로드되어 CPU 연산을 수행하기 시작한 '동적인 인스턴스'이다. 컨테이너의 실행과 제어는 리눅스 커널의 프로세스 관리 모델과 도커 엔진의 상태 머신이 유기적으로 결합하여 완성된다. 개발자는 컨테이너의 생애주기를 정교하게 통제함으로써 애플리케이션의 고가용성과 자원 효율성을 달성한다.

### 컨테이너 생명 주기 (Lifecycle)

컨테이너는 생성부터 소멸까지 명확한 상태 전이 모델을 따른다. 각 상태는 도커 데몬이 관리하는 메타데이터에 기록되며, 특정 명령어나 시스템 이벤트에 의해 트리거된다.

#### 컨테이너 상태 (Status)

도커 컨테이너는 크게 다음과 같은 상태를 가진다.
* **Created**: 파일 시스템 격리와 네임스페이스 준비는 완료되었으나, 내부의 프로세스가 아직 실행되지 않은 상태다.
* **Running**: 컨테이너 내부의 PID 1 프로세스가 구동 중이며, CPU와 메모리 자원을 실제로 소비하는 상태다.
* **Paused**: 프로세스 실행이 일시 중단된 상태다. 커널의 `freezer` cgroup을 사용하여 프로세스의 스케줄링을 중단시키며, 메모리 정보는 그대로 유지된다.
* **Exited (Stopped)**: 내부 프로세스가 종료된 상태다. 격리된 환경과 쓰기 가능한 레이어 데이터는 보존되지만, CPU 자원은 반납한다.
* **Restarting**: 설정된 재시작 정책에 의해 컨테이너가 다시 실행을 시도하는 과도기적 상태다.

![](/docs//assets/img/2026-01-25-00-00-46.png)

#### 생성 (create)

`docker create` 명령은 컨테이너의 '뼈대'를 잡는 작업이다. 이 단계에서 도커 데몬은 다음과 같은 작업을 수행한다.
1. 이미지 레이어 위에 쓰기 가능한(Writable) 레이어를 생성한다.
2. 지정된 네트워크와 볼륨 설정을 파싱하여 메타데이터에 기록한다.
3. 호스트 파일 시스템의 특정 위치에 컨테이너 고유의 설정 파일을 생성한다.

실제 프로세스가 포크(fork)되지 않으므로 시스템 부하가 거의 없으며, 대량의 컨테이너를 미리 준비해두었다가 순차적으로 실행해야 하는 워크로드에서 유용하다.

#### 실행 (start/run)

`docker start`는 `create` 단계를 통해 준비된 컨테이너 격리 환경 내에서 실제 프로세스를 깨우는 작업이다. 반면 `docker run`은 `pull`, `create`, `start`를 한 번에 수행하는 복합 명령이다. 이 과정의 핵심은 저수준 런타임인 `runC`가 커널의 `clone()` 시스템 콜을 호출하여 네임스페이스가 적용된 프로세스를 생성하고, 이미지에 정의된 엔트리포인트(ENTRYPOINT)를 실행하는 데 있다.

실행 단계에서 도커 데몬은 `containerd-shim` 프로세스를 생성하여 컨테이너 프로세스의 부모 역할을 맡긴다. 이때 컨테이너 내부의 프로세스는 PID 1을 할당받으며, 호스트의 자원을 소모하기 시작한다. 만약 `-it` 옵션을 사용했다면, 이 시점에 호스트의 터미널(TTY)과 컨테이너의 표준 입출력 스트림이 유닉스 소켓을 통해 연결되어 인터랙티브한 제어가 가능해진다.

#### 일시 정지 (pause)

`docker pause`는 실행 중인 컨테이너의 모든 프로세스를 일시적으로 멈춘다. 이 기능의 내부 메커니즘은 리눅스 커널의 **cgroup freezer** 서브시스템을 활용한다. 이는 프로세스에게 `SIGSTOP` 신호를 보내는 방식과는 근본적으로 다르다.

`SIGSTOP`은 프로세스가 신호를 수신하여 스스로 멈추는 방식이기에 프로세스가 이를 인지할 수 있고, 일부 시스템 콜 상태에서는 즉시 멈추지 않을 수 있다. 반면 `cgroup freezer`는 커널 스케줄러 레벨에서 해당 프로세스 그룹의 상태를 'FROZEN'으로 변경하여 CPU 할당을 완전히 차단한다. 프로세스는 자신이 멈췄다는 사실조차 모른 채 메모리 상에 그대로 유지되며, `unpause` 시 즉시 이전의 CPU 레지스터 상태와 메모리 컨텍스트를 복구하여 실행을 재개한다.

#### 종료 (stop)

`docker stop`은 컨테이너를 우아하게 종료(Graceful Shutdown)시키는 절차를 밟는다. 이 과정은 하드웨어와 소프트웨어 간의 신호 전달 체계인 시그널(Signal)을 기반으로 동작한다.

1.  **SIGTERM 전달**: 도커 데몬은 먼저 컨테이너의 PID 1 프로세스에게 `SIGTERM`(15) 신호를 보낸다. 이는 "정상적으로 종료를 준비하라"는 통보이다. 애플리케이션은 이 신호를 받으면 진행 중인 트랜잭션을 마무리하고, 데이터베이스 연결을 닫으며, 임시 파일을 정리하는 등의 클린업 작업을 수행한다.
2.  **Grace Period 대기**: 기본적으로 도커는 10초의 대기 시간을 준다. 이 시간 동안 PID 1 프로세스가 종료되기를 기다린다.
3.  **SIGKILL 강제 종료**: 만약 10초가 지나도 프로세스가 종료되지 않으면, 커널은 `SIGKILL`(9) 신호를 즉시 보낸다. 이는 프로세스가 가로챌 수 없는 강제 종료 신호이며, 커널이 즉시 해당 프로세스의 모든 자원을 회수한다.

![](/docs//assets/img/2026-01-25-00-00-55.png)

#### 재시작 (restart)

`docker restart`는 내부적으로 `stop`과 `start`를 순차적으로 실행한다. 여기서 중요한 엔지니어링 포인트는 **재시작 정책(Restart Policy)**이다. `--restart` 옵션에 따라 컨테이너가 예기치 않게 종료되었을 때(`on-failure`), 혹은 데몬이 재시작되었을 때(`always`) 커널 상태를 확인하여 컨테이너를 자동으로 복구한다. 이는 수동 개입 없이 시스템의 가용성을 유지하는 오토-힐링(Auto-healing)의 기초적인 형태이다.

#### 강제 종료 (kill)

`docker kill`은 `stop`의 우아한 절차를 생략하고 즉시 커널 레벨에서 프로세스를 제거한다. 기본값으로 `SIGKILL`을 보내지만, 사용자가 임의의 시그널(예: `SIGHUP`)을 지정하여 보낼 수도 있다. 이 명령은 애플리케이션이 응답 불능 상태(Deadlock)에 빠졌을 때나, 즉각적인 자원 회수가 필요한 긴급 상황에서 사용된다. 데이터 무결성이 손상될 위험이 크므로 일반적인 상황에서는 권장되지 않는다.

#### 삭제 (rm)

`docker rm`은 정지된 컨테이너의 모든 흔적을 시스템에서 지우는 최종 단계다. 
* 컨테이너를 위해 생성되었던 쓰기 가능한(Writable) 레이어를 물리적으로 삭제한다. 
* 도커 데몬이 관리하던 해당 컨테이너의 메타데이터(ID, 상태, 로그, 네트워크 설정 등)를 데이터베이스에서 제거한다. 
* 단, 컨테이너와 연결되었던 외부 볼륨(Volumes) 데이터는 이 명령으로 삭제되지 않으며 명시적인 볼륨 삭제 명령을 따로 수행해야 한다.

### 프로세스 관리 및 모니터링

컨테이너 환경에서 프로세스는 고립된 섬과 같다. 외부에서 이 섬의 상태를 파악하고 제어하기 위해서는 커널이 제공하는 표준 스트림과 리소스 추적 기능을 도커 엔진이 어떻게 추상화하여 제공하는지 이해해야 한다.

#### 전경 프로세스 (Foreground)

전경 모드는 컨테이너의 표준 입력, 출력, 에러 스트림을 현재 사용자의 터미널 세션에 직접 연결하는 방식이다. `docker run` 시 `-d` 옵션을 주지 않았을 때의 기본 동작이다. 이 모드에서 사용자가 `Ctrl+C`를 누르면 `SIGINT`가 컨테이너로 전달되어 프로세스가 종료된다. 주로 개발 환경에서 로그를 실시간으로 확인하거나 초기 디버깅을 수행할 때 활용된다.

#### 배경 프로세스 (Detached)

`-d` 옵션을 통해 실행되는 배경 모드는 컨테이너를 백그라운드에서 구동한다. 프로세스는 실행되지만 터미널 세션과의 연결은 끊어진다. 이 상태에서 컨테이너의 생사는 오직 도커 데몬만이 관리하며, 사용자는 `docker ps`를 통해 상태를 조회해야 한다. 실제 운영 환경의 서비스(웹 서버, 데이터베이스 등)는 대부분 이 모드로 실행된다.

#### 인터랙티브 쉘 (Interactive)

컨테이너를 단순한 바이너리 실행기가 아닌, 사용자와 실시간으로 상호작용하는 쉘 환경으로 전환하기 위해서는 `-i` (interactive)와 `-t` (tty)라는 두 가지 독립적인 메커니즘의 결합이 필요하다. 이 두 옵션은 리눅스 커널의 터미널 서브시스템과 파일 서브시스템을 각각 제어하며, 컨테이너 내부의 프로세스가 사용자의 키보드 입력을 받아들이고 화면에 출력할 수 있는 물리적 통로를 개설한다.

* **-i (Keep STDIN open)**: 컨테이너 내부 프로세스의 표준 입력(stdin)을 닫지 않고 호스트의 입력 스트림에 연결된 상태로 유지한다. 이 옵션이 없으면 프로세스는 입력을 기다리지 않고 즉시 종료되거나 입력을 무시한다.
* **-t (Allocate a pseudo-TTY)**: 컨테이너 내부에 **가상 터미널(Pseudo-TTY, PTY)** 장치를 할당한다. 리눅스 커널은 이를 통해 프로세스에게 "당신은 현재 인터랙티브한 터미널 환경에서 실행 중이다"라는 신호를 보낸다. PTY가 할당되면 쉘 프롬프트가 나타나고, `ls` 명령 시 색상이 구분되는 등 터미널 전용 기능들이 활성화된다.

> **PTY와 커널 드라이버의 인터랙션**
> 
> `-t` 옵션이 실행되면 도커 데몬은 커널의 `/dev/pts/ptmx` 장치를 호출하여 새로운 PTY 마스터/슬레이브 쌍을 생성한다. 컨테이너 내부의 프로세스는 이 슬레이브 장치에 연결되며, 사용자가 입력하는 데이터는 마스터 장치를 거쳐 프로세스로 전달된다. 이 과정에서 커널의 TTY 라인 디시플린(Line Discipline)이 개입하여 특수 문자(Ctrl+C 등)의 처리와 에코(Echo) 기능을 수행한다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-01-01.png)

#### 표준 스트림 (stdout/stderr)

도커는 컨테이너 내부 프로세스에서 발생하는 모든 출력을 가로채어 관리한다. 리눅스의 표준 관례에 따라 프로세스는 **표준 출력(stdout, FD 1)**과 **표준 에러(stderr, FD 2)**라는 두 개의 출력 스트림을 가지는데, 도커 엔진은 이 스트림들을 파일 시스템이나 네트워크, 혹은 외부 로깅 시스템으로 리다이렉션하는 중계기 역할을 수행한다.

이 메커니즘의 핵심은 `containerd-shim`이 컨테이너 프로세스의 파일 서술자를 소유하고 있다는 점이다. 프로세스가 `write()` 시스템 콜을 호출하여 데이터를 출력하면, 이 데이터는 유닉스 파이프(Pipe)를 타고 `shim`으로 전달된다. 도커 데몬은 이 데이터를 수집하여 설정된 **로깅 드라이버(Logging Driver)**에 따라 직렬화(Serialization)한다.

특히 표준 출력과 표준 에러를 명확히 분리하여 관리하는 것은 마이크로서비스 운영에서 매우 중요하다. 일반적인 서비스 로그는 `stdout`으로 보내고, 치명적인 오류나 예외 상황은 `stderr`로 보내도록 설계하면, 로그 수집기(Fluentd, Logstash 등)에서 필터를 통해 에러 로그만을 별도로 추출하여 알람을 발생시키는 등의 자동화된 운영 체계를 구축할 수 있다.

#### 컨테이너 로그 (logs)

`docker logs` 명령은 컨테이너가 실행되는 동안 발생한 모든 표준 스트림 데이터를 조회하는 창구다. 도커는 기본적으로 `json-file` 로깅 드라이버를 사용하며, 컨테이너 내부에서 발생한 출력을 호스트의 특정 경로(`/var/lib/docker/containers/<id>/<id>-json.log`)에 JSON 형태로 기록한다.

**1. 로그 데이터의 직렬화 구조**
JSON 로깅 드라이버는 단순히 텍스트만 저장하는 것이 아니라, 각 로그 라인에 대해 다음과 같은 메타데이터를 함께 기록한다.
* `log`: 실제 출력된 메시지 내용
* `stream`: 데이터가 온 소스 (`stdout` 또는 `stderr`)
* `time`: 로그가 기록된 정확한 타임스탬프 (RFC3339)

**2. 로그 드라이버 아키텍처**
도커는 플러그인 아키텍처를 통해 다양한 로깅 드라이버를 지원한다.
* **journald**: 리눅스 시스템의 전역 저널링 시스템에 로그를 통합한다.
* **syslog**: 전통적인 유닉스 로그 서버로 데이터를 전송한다.
* **fluentd / gelf / splunk**: 외부 중앙 집중식 로그 분석 플랫폼으로 직접 데이터를 스트리밍한다.
* **none**: 로그를 전혀 기록하지 않는다. I/O 성능이 극도로 중요하고 로그 보존이 필요 없는 경우에 사용한다.

> **로그 비대화와 디스크 고갈 (Disk Exhaustion)**
> 
> 기본 설정인 `json-file` 드라이버는 로그 파일의 크기를 제한하지 않는다. 컨테이너가 대량의 로그를 무한히 생성할 경우, 호스트의 디스크 공간이 가득 차 전체 시스템이 중단되는 대참사가 발생할 수 있다. 따라서 운영 환경에서는 반드시 도커 데몬 설정(`daemon.json`)이나 컨테이너 실행 옵션을 통해 `max-size`와 `max-file`(로그 로테이션) 설정을 강제해야 한다.
{: .block-warning }

![](/docs//assets/img/2026-01-25-00-01-10.png)

#### 리소스 통계 (stats)

`docker stats`는 실행 중인 컨테이너의 CPU, 메모리, 네트워크 I/O, 블록 I/O 사용량을 실시간 스트림으로 제공하는 가상 계층의 모니터링 도구이다. 이 명령이 반환하는 수치는 도커 데몬이 직접 계산하는 것이 아니라, 리눅스 커널의 **Cgroups(Control Groups)** 가상 파일 시스템에서 수집한 로우 레벨 데이터를 가공한 결과물이다.

**1. 데이터 수집 메커니즘**
도커 데몬은 주기적으로 `/sys/fs/cgroup/` 하위의 각 컨트롤러 디렉토리를 탐색한다.
* **CPU**: `cpuacct.usage` 파일에서 나노초 단위의 누적 CPU 사용 시간을 읽어온다.
* **메모리**: `memory.usage_in_bytes`에서 현재 점유 중인 메모리 양을, `memory.limit_in_bytes`에서 할당된 한계치를 읽어온다.
* **I/O**: `blkio.throttle.io_service_bytes`에서 장치별 입출력 바이트를 집계한다.

**2. CPU 사용률 계산 공식**
도커가 표시하는 CPU 백분율은 '시스템 전체의 가용한 CPU 시간 대비 컨테이너가 사용한 시간'을 의미한다. 이를 산출하기 위해 커널 수준의 델타(Delta) 값을 사용한다.

$$CPU\% = \frac{container\_usage\_delta}{system\_usage\_delta} \times number\_of\_cpus \times 100.0$$

여기서 `container_usage_delta`는 두 샘플링 시점 사이의 컨테이너 누적 CPU 사용량 차이이며, `system_usage_delta`는 동일 시간 동안 호스트 시스템 전체에서 발생한 CPU 틱(Tick)의 총합이다. 이 수치는 멀티코어 환경에서 100%를 초과할 수 있는데, 예를 들어 4코어 시스템에서 컨테이너가 2개의 코어를 완전히 점유한다면 200%로 표기된다.

> **메모리 통계의 함정: RSS vs Cache**
> 
> `docker stats`에서 보여주는 메모리 사용량은 단순히 `memory.usage_in_bytes` 값이 아니다. 커널은 성능 최적화를 위해 파일 I/O 데이터를 메모리에 캐싱(Page Cache)하는데, 이는 시스템이 필요할 때 즉시 해제될 수 있는 자원이다. 따라서 도커는 사용자에게 실질적인 압박을 주는 **RSS(Resident Set Size)**와 **Mapped File** 사용량만을 계산하여 보여주고, 캐시 영역은 통계에서 제외함으로써 실제 애플리케이션의 메모리 사용량을 보다 정확하게 투영한다.
{: .block-tip }

### 실행 환경 제어

컨테이너 내에서 애플리케이션이 어떻게 시작되고 어떤 파라미터를 인자로 받을지는 이미지 빌드 단계에서 정의된다. 이는 단순히 실행 명령을 적는 것을 넘어, 유닉스 프로세스 모델의 실행 계층을 설계하는 과정이다.

#### 엔트리포인트 (ENTRYPOINT)

`ENTRYPOINT`는 컨테이너가 실행될 때 **'반드시 실행되어야 할 주 프로세스'**를 정의한다. 컨테이너를 마치 하나의 독립적인 실행 파일(Executable)처럼 취급하게 만드는 핵심 설정이다.

**1. Exec Form vs Shell Form**
* **Exec Form (`["executable", "param1"]`)**: 도커가 권장하는 방식이다. 프로세스를 `/bin/sh`를 거치지 않고 직접 실행한다. 이 경우 애플리케이션이 컨테이너 내에서 **PID 1**을 점유하게 되어, 호스트로부터 전달되는 `SIGTERM`과 같은 종료 시그널을 직접 수신하고 처리할 수 있다.
* **Shell Form (`executable param1`)**: 커널은 내부적으로 `/bin/sh -c`를 사용하여 명령을 실행한다. 이 경우 `/bin/sh`가 PID 1이 되고 실제 애플리케이션은 그 자식 프로세스가 된다. 쉘은 시그널을 자식에게 전달하지 않는 특성이 있어, `docker stop` 명령 시 애플리케이션이 우아하게 종료되지 못하고 강제 종료(SIGKILL)되는 문제를 유발한다.

#### 실행 명령 (CMD)

`CMD`는 엔트리포인트에 전달될 **'기본 인자(Default Arguments)'**를 정의하거나, 엔트리포인트가 없을 경우 실행될 기본 명령을 설정한다. `ENTRYPOINT`와의 결정적인 차이는 가변성에 있다. `docker run` 명령 뒤에 추가 인자를 입력하면, 이미지에 정의된 `CMD` 값은 무시되고 사용자의 입력값으로 완전히 대체된다.

> **ENTRYPOINT와 CMD의 결합 논리**
> 
> 최종 실행 명령 = `ENTRYPOINT` + `CMD` (또는 사용자 인자)
> 만약 `ENTRYPOINT`가 `["python", "app.py"]`이고 `CMD`가 `["--port", "80"]`이라면, 컨테이너는 `python app.py --port 80`으로 실행된다. 사용자가 `docker run myimg --port 90`을 입력하면 `CMD`가 대체되어 `python app.py --port 90`이 실행된다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-01-24.png)

#### 환경 변수 (ENV)

`ENV`는 프로세스 실행 환경의 쉘 변수를 설정한다. 이는 빌드 시점뿐만 아니라 실행 시점에도 유지되며, 애플리케이션 소스 코드 수정 없이 설정을 변경할 수 있는 가장 유연한 도구이다.

도커 엔진은 컨테이너 구동 시 `ENV`에 정의된 키-값 쌍을 프로세스의 환경 블록(Environment Block)에 주입한다. 애플리케이션은 언어별 표준 라이브러리(예: Python의 `os.environ`, Node.js의 `process.env`)를 통해 이 값에 접근한다. 하지만 보안 측면에서 `ENV`는 주의가 필요하다. `docker inspect` 명령을 통해 누구나 평문으로 변수를 확인할 수 있기 때문에, 데이터베이스 비밀번호나 API 키와 같은 민감 정보는 `ENV`가 아닌 도커 시크릿(Secrets)이나 볼륨 마운트를 통한 파일 주입 방식을 사용해야 한다.

#### 작업 디렉토리 (WORKDIR)

`WORKDIR` 명령어는 컨테이너 내부에서 후속 명령어(`RUN`, `CMD`, `ENTRYPOINT`, `COPY`, `ADD`)가 실행될 물리적 작업 경로를 설정한다. 이는 리눅스 쉘의 `cd` 명령과 유사한 역할을 수행하지만, 도커 빌드 시스템의 레이어 아키텍처에 최적화된 방식으로 동작한다.

**1. 경로 자동 생성 및 절대 경로 지향**
`WORKDIR`의 가장 큰 특징은 지정된 경로가 이미지 내에 존재하지 않을 경우, 도커가 이를 자동으로 생성(`mkdir -p`)한다는 점이다. 또한, `WORKDIR`은 누적된 설정값을 따른다. 예를 들어 `WORKDIR /app` 실행 후 `WORKDIR dev`를 실행하면 최종 경로는 `/app/dev`가 된다. 그러나 이러한 상대 경로의 연쇄는 설정 오류를 유발할 가능성이 크므로, 엔지니어링 실무에서는 항상 `/usr/src/app`과 같은 절대 경로를 명시하는 것이 권장된다.

**2. 커널 수준의 PWD 관리**
프로세스가 실행될 때 리눅스 커널은 프로세스 제어 블록(`task_struct`) 내의 `fs_struct` 구조체에 현재 작업 디렉토리(`pwd`) 정보를 담는다. 도커 엔진은 컨테이너 구동 시 이 구조체의 포인터를 `WORKDIR`에서 정의한 경로로 매핑한다. 이는 컨테이너 내부 프로세스가 상대 경로를 통해 자원에 접근할 때의 기준점이 되며, 잘못된 `WORKDIR` 설정은 라이브러리 참조 오류나 실행 파일 로드 실패를 유발하는 주된 원인이 된다.

![](/docs//assets/img/2026-01-25-00-05-28.png)

#### 상태 검사 (Health Check)

프로세스가 커널 프로세스 테이블에 존재한다고 해서 해당 서비스가 정상적으로 동작한다고 단정할 수 없다. 예를 들어 웹 서버 프로세스는 살아있지만, 데드락(Deadlock)에 빠져 응답을 주지 못하는 상태가 있을 수 있다. `HEALTHCHECK`은 컨테이너 내부의 프로세스가 실제로 '서비스 가능한 상태'인지 도커 데몬이 주기적으로 검증하는 메커니즘이다.

**1. 검사 파라미터와 상태 머신**
도커는 다음과 같은 정교한 파라미터를 통해 상태 검사를 수행한다.
* **interval**: 검사 간격 (기본 30초).
* **timeout**: 특정 검사가 실패로 간주되기까지의 대기 시간.
* **start-period**: 컨테이너 부팅 초기화 시간을 고려하여 검사를 유예하는 기간.
* **retries**: `unhealthy` 상태로 확정하기까지의 연속 실패 횟수.

**2. 런타임 동작 메커니즘**
상태 검사가 설정된 컨테이너가 실행되면, 도커 데몬은 지정된 주기마다 컨테이너 네임스페이스 내부에서 `exec` 명령을 통해 특정 명령어(예: `curl -f http://localhost/`)를 실행한다. 도커는 이 명령의 **종료 코드(Exit Code)**를 확인한다.
* `0`: Success (Healthy)
* `1`: Failure (Unhealthy)

> **Orchestration과의 연동**
> 
> 컨테이너가 `unhealthy` 상태로 판명되면, 도커 엔진은 해당 컨테이너의 메타데이터를 업데이트한다. Docker Compose나 Swarm 환경에서는 이 신호를 감지하여 해당 컨테이너로의 트래픽 유입을 차단하거나, 컨테이너를 강제로 재시작하는 오토-힐링(Auto-healing) 로직을 트리거한다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-05-34.png)

#### 종료 시그널 (SIGTERM/SIGKILL)

컨테이너의 수명 종료는 호스트 커널과 컨테이너 내부 PID 1 프로세스 간의 시그널 통신을 통해 이루어진다. 이 과정에서 가장 중요한 개념은 **PID 1의 특수성**이다.

리눅스 커널에서 PID 1은 특별한 보호를 받는다. 일반 프로세스는 시그널 핸들러를 등록하지 않아도 시그널 수신 시 커널이 정의한 기본 동작(Default action)을 수행하지만, **PID 1 프로세스는 명시적으로 핸들러를 등록하지 않은 시그널을 모두 무시한다.** 즉, 애플리케이션이 `SIGTERM`을 처리하도록 코딩되지 않았다면, `docker stop` 명령을 내려도 컨테이너는 종료되지 않고 대기 시간(Grace Period)이 지난 후 `SIGKILL`에 의해 강제 파괴된다.

* **STOPSIGNAL**: 도커는 기본적으로 `SIGTERM`을 종료 시그널로 사용하지만, 이미지 빌드 시 `STOPSIGNAL` 지시어를 통해 다른 시그널(예: Nginx의 경우 `SIGQUIT`)로 변경할 수 있다.
* **Zombie Process 문제**: PID 1 프로세스가 자식 프로세스들을 적절히 회수(Wait)하지 않으면, 컨테이너 종료 시점에 소멸되지 않은 좀비 프로세스들이 시스템 자원을 점유하는 문제가 발생할 수 있다. 이를 위해 도커는 `--init` 옵션을 제공하여 가벼운 init 프로세스(`tini`)를 PID 1로 전면에 내세워 시그널 전달과 좀비 회수를 대행하게 할 수 있다.

## 네트워크 아키텍처

도커 네트워크는 복잡한 리눅스 커널의 네트워크 스택을 추상화하여, 컨테이너가 서로 통신하거나 외부 세계와 연결되는 방식을 정의한다. 이는 단순히 IP 주소를 할당하는 것을 넘어, 가상 이더넷 다리(Bridge), 라우팅 테이블, 그리고 iptables 기반의 패킷 필터링 규칙이 얽힌 고도의 시스템 엔지니어링의 결과물이다.

### 네트워크 드라이버

도커는 플러그형 네트워크 아키텍처를 채택하여, 사용자의 요구사항에 따라 다양한 드라이버를 선택할 수 있게 한다. 각 드라이버는 리눅스 커널의 서로 다른 격리 기술과 브릿징 기술을 활용한다.

#### 브리지 네트워크 (Bridge)

브리지 네트워크는 도커의 기본 네트워크 드라이버로, 동일한 호스트 내의 컨테이너들이 서로 통신할 수 있도록 소프트웨어 기반의 가상 스위치를 생성한다.

**1. 물리적 구조: docker0 인터페이스**
도커 엔진이 기동되면 호스트 운영체제에는 `docker0`라는 가상 네트워크 인터페이스가 생성된다. 이는 리눅스 커널의 **L2 가상 브리지** 장치이다. 컨테이너가 생성될 때마다 `veth` (virtual ethernet) 쌍이 만들어지며, 한쪽 끝은 컨테이너 내부의 `eth0`가 되고, 다른 쪽 끝은 호스트의 `docker0` 브리지에 연결된다.

**2. 통신 및 주소 할당 (IPAM)**
도커는 기본적으로 `172.17.0.0/16` 대역의 서브넷을 `docker0`에 할당하고, 컨테이너들에게 이 대역 내의 IP를 순차적으로 부여한다. 서로 다른 브리지에 속한 컨테이너들은 커널의 IP 포워딩 규칙에 의해 격리되며, 통신이 필요한 경우 별도의 라우팅 설정이 필요하다.

#### 호스트 네트워크 (Host)

호스트 네트워크 드라이버는 컨테이너의 네트워크 격리(Network Namespace)를 해제하고, 컨테이너가 호스트 운영체제의 네트워크 스택을 직접 공유하도록 설정한다. 이 모드에서 실행되는 컨테이너는 자신만의 IP 주소를 할당받지 않으며, 컨테이너 내부의 프로세스가 포트를 바인딩하면 호스트의 해당 포트가 즉시 점유된다.

**1. 격리 해제의 물리적 의미**
커널 수준에서 `CLONE_NEWNET` 플래그 없이 프로세스가 생성됨을 의미한다. 결과적으로 컨테이너 내부에서 `ifconfig`나 `ip addr` 명령을 수행하면 호스트의 물리 인터페이스(eth0, wlan0 등)가 그대로 노출된다. 이는 가상화 계층(veth pair, Bridge)을 거치지 않으므로 네이티브 수준의 네트워크 성능을 제공한다.

**2. 성능과 보안의 트레이드오프**
* **성능**: 패킷이 가상 브리지를 통과하거나 포트 포워딩을 위한 NAT(Network Address Translation) 처리를 거칠 필요가 없다. 따라서 초당 수십만 건의 요청을 처리해야 하는 고성능 웹 서버나 실시간 스트리밍 서비스에 적합하다.
* **보안 및 포트 충돌**: 컨테이너가 호스트의 모든 네트워크 자원에 접근할 수 있으므로 격리 보안이 취약해진다. 또한, 동일한 포트를 사용하는 두 개의 컨테이너를 한 호스트에서 '호스트 모드'로 동시에 실행할 수 없다는 관리적 제약이 따른다.

![](/docs//assets/img/2026-01-25-00-05-40.png)

#### 오버레이 네트워크 (Overlay)

오버레이 네트워크는 서로 다른 물리적 호스트에서 실행되는 컨테이너들이 마치 동일한 로컬 네트워크에 있는 것처럼 통신할 수 있게 해주는 분산 네트워크 솔루션이다. 이는 주로 Docker Swarm이나 Kubernetes와 같은 클러스터 환경에서 멀티 호스트 네트워킹을 구현하기 위해 사용된다.

**1. VXLAN (Virtual Extensible LAN) 터널링**
오버레이 네트워크의 기술적 실체는 **VXLAN** 캡슐화이다. 컨테이너가 보내는 L2 이더넷 프레임을 L4 UDP 패킷 내부에 캡슐화하여 물리 네트워크를 가로질러 전송한다.
* 각 호스트에는 **VTEP (VXLAN Tunnel End Point)**라는 가상 인터페이스가 생성된다.
* 패킷이 호스트를 떠날 때 VTEP은 목적지 컨테이너가 위치한 물리 호스트의 IP를 외부 헤더에 붙여 캡슐화한다.
* 수신 측 호스트의 VTEP은 이를 받아 캡슐을 제거하고 내부의 원래 프레임을 대상 컨테이너로 전달한다.

**2. 컨트롤 플레인과 데이터 플레인**
오버레이 네트워크는 분산된 컨테이너들의 IP와 위치 정보를 관리하기 위한 키-값 저장소(Key-Value Store)를 필요로 한다. 도커는 가십 프로토콜(Gossip Protocol)을 사용하여 클러스터 전체에 네트워크 상태 정보를 동기화하며, 이를 통해 컨테이너가 어느 호스트에 있든 이름(Service Discovery)으로 통신할 수 있는 환경을 구축한다.

> **오버레이 네트워크의 MTU 문제**
> 
> VXLAN 헤더가 추가됨에 따라 실제 데이터가 담기는 공간인 MTU(Maximum Transmission Unit)가 작아진다. 일반적인 이더넷 MTU가 1500바이트라면, 오버레이 환경에서는 헤더 공간(약 50바이트)을 제외한 1450바이트 수준으로 조정해야 패킷 단편화(Fragmentation)로 인한 성능 저하를 막을 수 있다.
{: .block-warning }

![](/docs//assets/img/2026-01-25-00-05-45.png)

#### 가상 네트워크 (None)

`none` 드라이버는 컨테이너에 대해 루프백 인터페이스(`lo`)를 제외한 모든 네트워크 인터페이스를 제거한다. 이는 완벽하게 네트워크가 단절된 '에어 갭(Air-gapped)' 환경을 제공한다.

이 모드는 주로 다음과 같은 특수 목적으로 활용된다.
* 외부 통신이 전혀 필요 없는 배치 작업(Batch Job).
* 네트워크를 통한 데이터 유출을 원천 차단해야 하는 고보안 계산 작업.
* 사용자가 직접 커스텀 네트워크 스택을 구성하려는 경우(예: 수동으로 veth pair를 생성하여 외부 툴로 관리).

#### Macvlan 드라이버

Macvlan은 가상 브리지를 거치지 않고 호스트의 물리 인터페이스에 여러 개의 MAC 주소를 직접 할당하여, 컨테이너가 물리 네트워크의 독립적인 노드로 보이게 하는 기술이다.

**1. L2 하위 인터페이스 아키텍처**
커널은 호스트의 물리 NIC(예: eth0) 위에 여러 개의 가상 인터페이스(`eth0.1`, `eth0.2` 등)를 생성한다. 각 인터페이스는 고유한 MAC 주소를 가지며, 물리 스위치는 이를 별개의 물리 서버가 연결된 것으로 인식한다. 

**2. 성능적 우위와 제약**
브리지 모드와 달리 복잡한 포트 포워딩이나 NAT가 필요 없으므로 매우 짧은 지연 시간을 보장한다. 하지만 물리 NIC가 **무차별 모드(Promiscuous Mode)**를 지원해야 하며, 많은 클라우드 환경(AWS, GCP 등)의 가상화 계층에서는 보안상의 이유로 Macvlan 방식의 MAC 주소 위조를 차단하기 때문에 사용이 제한적일 수 있다.

![](/docs//assets/img/2026-01-25-00-05-50.png)

### 네트워크 통신 매커니즘

단순히 드라이버를 정의하는 것을 넘어, 데이터 패킷이 컨테이너의 경계를 넘나드는 물리적인 경로와 이를 제어하는 커널의 규칙 체계를 이해하는 것이 실제 트러블슈팅의 핵심이다.

#### 포트 바인딩 (Port Mapping)

포트 바인딩은 외부 네트워크에서 격리된 컨테이너 서비스에 접근할 수 있도록 특정 호스트 포트를 컨테이너 포트와 연결하는 기술이다. 이 메커니즘은 리눅스 커널의 **Netfilter**와 **iptables**를 통해 구현된다.

**1. DNAT (Destination Network Address Translation)**
사용자가 `docker run -p 8080:80`을 실행하면, 도커 데몬은 호스트의 iptables에 `NAT` 테이블 규칙을 추가한다.
* 외부에서 호스트의 8080번 포트로 패킷이 들어오면, 커널은 `PREROUTING` 체계에서 이 패킷의 목적지 주소를 해당 컨테이너의 내부 IP와 80번 포트로 변환(DNAT)한다.
* 반대로 컨테이너가 응답을 보낼 때는 `POSTROUTING` 단계에서 송신지 주소를 다시 호스트의 IP로 변환(SNAT)하여 외부로 내보낸다.

**2. DOCKER 체인**
도커는 자신의 규칙이 시스템의 다른 규칙과 섞이는 것을 방지하기 위해 `DOCKER`라는 전용 iptables 체인을 생성하여 관리한다. `iptables -t nat -L` 명령을 통해 도커가 자동으로 생성한 복잡한 포워딩 규칙들을 확인할 수 있다.

> **Userland Proxy vs iptables**
> 
> 도커는 과거에 모든 트래픽을 `docker-proxy`라는 프로세스가 직접 중계하는 방식을 사용했으나, 현재는 커널 수준의 iptables 규칙 처리를 기본으로 한다. 프로세스 중계 방식은 높은 CPU 부하를 유발하기 때문이다. 다만, 커널의 IPv6 지원이 미비하거나 특정 환경에서는 여전히 보조적으로 프록시 프로세스가 구동될 수 있다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-05-56.png)

#### 가상 이더넷 (veth pair)

가상 이더넷(Virtual Ethernet, 이하 veth)은 리눅스 커널에서 제공하는 로컬 가상 네트워크 터널이다. veth 장치는 항상 '쌍(pair)'으로 생성되며, 한쪽 인터페이스로 들어온 모든 패킷은 커널 내부 가상 전선(Wire)을 타고 반대쪽 인터페이스로 즉시 전달되는 물리적 특성을 가진다. 도커는 이 veth pair를 사용하여 호스트의 네트워크 네임스페이스와 컨테이너의 격리된 네트워크 네임스페이스 사이를 물리적으로 연결한다.

**1. 커널 내부의 패킷 전달 메커니즘**
커널 소스 코드(`drivers/net/veth.c`) 수준에서 veth 장치의 송신 함수인 `veth_xmit`이 호출되면, 패킷(sk_buff)은 드라이버의 실제 하드웨어 전송 로직을 거치는 대신 반대편 장치의 수신 함수인 `netif_rx`로 직접 전달된다. 이 과정에서 패킷의 메타데이터에 기록된 네임스페이스 정보가 변경되며, 이는 패킷이 마치 물리적인 벽을 뚫고 다른 공간으로 이동한 것과 같은 효과를 낸다.

**2. 컨테이너 네트워크 진입 과정**
도커가 컨테이너를 구동할 때 수행하는 로우 레벨 네트워크 구성 단계는 다음과 같다.
* 호스트 네임스페이스에서 `ip link add veth_host type veth peer name veth_container` 명령과 유사한 시스템 콜을 수행하여 쌍을 생성한다.
* `veth_host`는 호스트의 가상 브리지(`docker0`)에 마운트한다.
* `veth_container`는 컨테이너의 네트워크 네임스페이스 내부로 물리적으로 '밀어 넣는다'(Move).
* 컨테이너 내부로 들어온 `veth_container`의 이름을 표준적인 `eth0`로 변경하고 IP 주소를 할당한다.

이 구조 덕분에 컨테이너 내부의 애플리케이션이 `eth0`로 데이터를 보내면, 패킷은 커널의 가상 전선을 타고 호스트의 `veth_host`로 흘러나오며, 이후 브리지를 통해 호스트의 라우팅 테이블과 iptables 규칙에 따라 외부 망으로 전달된다.

![](/docs//assets/img/2026-01-25-00-06-02.png)

#### 내부 DNS (Service Discovery)

사용자 정의 브리지 네트워크를 사용하는 도커 컨테이너는 고정 IP가 아닌 '컨테이너 이름'이나 '네트워크 별칭'을 통해 서로를 찾아낼 수 있다. 이는 도커 엔진이 내장하고 있는 임베디드 DNS 서버(Embedded DNS Server)를 통해 실현된다.

**1. 리졸버(Resolver) 설정: 127.0.0.11**
도커는 컨테이너 실행 시 `/etc/resolv.conf` 파일에 `nameserver 127.0.0.11`이라는 특수한 IP를 주입한다. 이 주소는 커널 레벨에서 도커 데몬이 관리하는 로컬 DNS 리졸버로 트래픽을 유도하기 위한 루프백 주소다. 컨테이너 내부 프로세스가 DNS 쿼리를 보내면, 도커 데몬 내부의 DNS 엔진이 이를 가로채어 처리한다.

**2. 질의 처리 로직**
* **내부 도메인**: 요청된 이름이 동일한 도커 네트워크에 속한 컨테이너 이름이라면, 도커 데몬이 관리하는 내부 IP 테이블에서 해당 IP를 찾아 반환한다.
* **외부 도메인**: 내부 테이블에 없는 이름(예: google.com)인 경우, 도커 엔진은 해당 쿼리를 컨테이너에 설정된 상위 DNS(호스트의 DNS 혹은 `--dns` 옵션으로 지정된 주소)로 포워딩한다.

> **DNS 캐싱과 TTL**
> 
> 도커의 내부 DNS는 성능 최적화를 위해 매우 짧은 TTL(Time-To-Live)을 가진 캐시를 운영한다. 이는 컨테이너가 잦은 재시작이나 스케일링으로 IP가 수시로 바뀌는 동적 환경에서 서비스 디스커버리의 정합성을 유지하기 위한 엔지니어링적 선택이다.
{: .block-tip }

#### 네트워크 별칭 (Alias)

네트워크 별칭은 특정 컨테이너를 네트워크 상에서 여러 개의 이름으로 식별할 수 있게 하는 기능이다. 이는 마이크로서비스 아키텍처에서 서비스의 역할을 추상화하거나, 레거시 시스템과의 호환성을 유지할 때 강력한 도구가 된다.

예를 들어, `db_v1`이라는 이름의 컨테이너를 실행하면서 별칭으로 `database`를 부여하면, 동일한 네트워크 내의 다른 컨테이너들은 `db_v1`과 `database`라는 두 이름 모두를 통해 해당 컨테이너의 IP에 도달할 수 있다. 도커 DNS 엔진은 쿼리가 들어올 때 별칭 목록을 먼저 검색하며, 하나의 별칭에 여러 컨테이너가 연결되어 있을 경우 DNS 라운드 로빈(Round-robin) 방식으로 IP를 반환하여 기초적인 로드 밸런싱 기능을 수행하기도 한다.

#### IP 주소 관리 (IPAM)

IPAM(IP Address Management)은 도커 네트워크 드라이버가 컨테이너에게 IP 주소를 할당하고 회수하는 체계를 관리하는 서브시스템이다. 도커는 기본적으로 내부 IPAM 드라이버를 사용하지만, 사용자 정의 네트워크 생성 시 서브넷(Subnet)과 게이트웨이(Gateway) 범위를 직접 지정하여 물리 인프라의 주소 체계와 정합성을 맞출 수 있다.

IP 할당 시 도커는 비트맵(Bitmap) 구조를 사용하여 사용 중인 주소를 추적한다. 컨테이너가 생성될 때 가용 IP 대역 중 가장 낮은 숫자의 주소를 선택하여 할당하며, 컨테이너가 삭제되면 해당 주소는 즉시 해제되어 다음 할당을 위해 대기한다.

#### 도커 링크 (Legacy Links)

`--link` 옵션을 통한 도커 링크는 현대적인 사용자 정의 네트워크 기능이 도입되기 이전에 사용되던 유산(Legacy) 방식이다. 이 방식은 DNS 서버를 통하지 않고, 컨테이너의 `/etc/hosts` 파일을 직접 수정하여 상대 컨테이너의 이름을 IP와 하드코딩된 상태로 매핑한다.

링크 방식의 결정적인 단점은 **정적 매핑**이라는 점이다. 연결된 대상 컨테이너가 재시작되어 IP가 바뀌면, 소스 컨테이너의 `/etc/hosts` 파일 정보를 업데이트하기 위해 소스 컨테이너 역시 재시작되어야 하는 강한 결합(Strong Coupling)을 유발한다. 따라서 현대의 아키텍처에서는 이를 지양하고 내장 DNS 기반의 사용자 정의 네트워크 사용을 원칙으로 한다.

### 트래픽 제어

컨테이너 네트워크의 완성은 패킷의 흐름을 통제하고 보안 경계를 세우는 데 있다. 도커는 리눅스 커널의 Netfilter 프레임워크를 활용하여 정교한 트래픽 제어 규칙을 생성한다.

#### 포트 포워딩 (DNAT)

포트 포워딩은 외부 망의 패킷이 호스트의 특정 포트를 통해 격리된 컨테이너의 포트로 도달하게 만드는 주소 변환 기술이다. 앞서 설명한 iptables의 DNAT(Destination NAT) 규칙이 여기서 핵심적인 역할을 수행한다.

호스트의 NIC로 패킷이 들어오면, 커널은 `PREROUTING` 체인에서 해당 패킷의 목적지 IP와 포트를 확인한다. 만약 도커가 예약한 포트라면, 패킷의 헤더 정보를 컨테이너의 내부 IP로 수정하여 라우팅시킨다. 이 과정은 패킷 단위로 커널 내부에서 발생하므로 매우 빠르며, 애플리케이션 입장에서는 마치 자신이 외부 포트와 직접 연결된 것과 같은 환상을 갖게 된다.

#### 네트워크 격리 (Isolation)

도커는 서로 다른 네트워크 간의 통신을 기본적으로 차단하여 보안 경계를 구축한다.

* **네트워크 간 격리**: 도커는 각 사용자 정의 네트워크마다 고유한 iptables 체인을 생성하며, 명시적으로 연결되지 않은 서로 다른 네트워크에 속한 컨테이너 간의 패킷 전달(Forwarding)을 기본적으로 거부(DROP)한다.
* **ICC (Inter-Container Communication) 제어**: 동일한 브리지 네트워크 내에서도 `--icc=false` 옵션을 통해 컨테이너 간의 직접적인 통신을 완전히 차단할 수 있다. 이 경우 컨테이너들은 오직 호스트를 통한 외부 노출 포트로만 서로 통신할 수 있게 되어, 보안 사고 발생 시 인접 컨테이너로의 공격 전파(Lateral Movement)를 효과적으로 방어할 수 있다.

![](/docs//assets/img/2026-01-25-00-06-07.png)

#### 사용자 정의 네트워크

사용자 정의 네트워크(User-defined Network)는 도커의 기본 브리지(`docker0`)가 가진 한계를 극복하고, 서비스 간의 논리적 그룹화와 보안 격리를 달성하기 위해 설계된 전용 네트워크 환경이다. 기본 브리지는 모든 컨테이너가 하나로 묶이는 평면적인 구조인 반면, 사용자 정의 네트워크는 마이크로서비스 간의 통신 경계를 명확히 설정할 수 있는 도구를 제공한다.

**1. 내장 DNS 기반의 서비스 디스커버리**
기본 브리지 네트워크와 사용자 정의 네트워크의 가장 결정적인 엔지니어링적 차이는 **DNS 리졸루션(Resolution)**의 지원 여부다. 기본 브리지에서는 컨테이너 간 통신을 위해 IP 주소를 직접 사용하거나 레거시 `--link` 옵션을 사용해야 하지만, 사용자 정의 네트워크에서는 도커의 임베디드 DNS 서버가 자동으로 활성화되어 '컨테이너 이름'만으로 상호 통신이 가능하다. 이는 IP 주소가 유동적으로 변하는 동적 환경에서 서비스의 결합도를 낮추는 결정적인 역할을 한다.

**2. 자동화된 격리 및 제어**
사용자 정의 네트워크를 생성하면 도커는 호스트 운영체제에 새로운 가상 브리지 인터페이스를 생성한다. 각 네트워크는 고유한 서브넷 대역을 가지며, 커널의 iptables 규칙에 의해 다른 네트워크와 완전히 격리된다. 만약 특정 컨테이너가 두 개의 서로 다른 사용자 정의 네트워크에 동시에 연결되어 있다면, 해당 컨테이너는 두 네트워크 사이를 잇는 '게이트웨이' 역할을 수행할 수 있다.

> **기본 브리지(docker0) 사용 시의 리스크**
> 
> 기본 브리지 네트워크는 보안 설정이 매우 느슨하다. 모든 컨테이너가 하나의 브리지에 물리적으로 연결되어 있어, 특정 컨테이너가 장악될 경우 ARP 스푸핑(Spoofing)이나 스니핑(Sniffing)을 통해 동일 호스트 내의 다른 모든 컨테이너 트래픽을 가로챌 위험이 크다. 운영 환경에서는 반드시 서비스 성격에 맞는 사용자 정의 네트워크를 분리하여 운영하는 것이 보안의 기본 원칙이다.
{: .block-warning }

## 데이터 영속성 및 저장소 전략

컨테이너는 본질적으로 '휘발성(Ephemeral)'을 전제로 설계된 실행 단위다. 컨테이너 내부 파일 시스템에 기록된 모든 데이터는 컨테이너가 삭제되는 순간 쓰기 가능 레이어(Writable Layer)와 함께 물리적으로 소멸한다. 따라서 데이터베이스의 데이터 파일, 사용자 업로드 이미지, 로그 파일 등 보존이 필요한 자산은 컨테이너의 생명 주기와 분리된 외부 저장 공간에 안전하게 적재되어야 한다. 도커는 이를 위해 파일 시스템의 특정 지점을 호스트의 자원과 연결하는 '마운트(Mount)' 모델을 제공한다.

### 스토리지 마운트 모델

도커의 스토리지 모델은 크게 세 가지 방식으로 나뉜다. 이는 데이터가 호스트 운영체제의 어디에 저장되는지, 그리고 도커 엔진이 해당 공간을 얼마나 직접적으로 통제하는지에 따라 구분된다.

#### 볼륨 (Volumes)

볼륨은 도커가 직접 관리하는 호스트 파일 시스템의 특정 영역(`/var/lib/docker/volumes/`)에 데이터를 저장하는 방식이다. 컨테이너 데이터 영속성을 위한 **가장 권장되는 방식**이며, 호스트의 핵심 디렉토리 구조로부터 데이터를 논리적으로 분리하여 안전하게 관리한다.

**1. 호스트 운영체제로부터의 독립성**
볼륨은 호스트의 특정 경로에 의존하지 않는다. 사용자는 단순히 볼륨의 이름만 지정하며, 실제 물리적 저장은 도커 엔진이 담당한다. 이는 컨테이너를 다른 호스트로 이동시키거나 클라우드 환경에서 스토리지 드라이버를 교체(예: 로컬 디스크에서 S3나 NFS로 변경)할 때 소스 코드나 설정을 변경할 필요가 없음을 의미한다.

**2. 고성능 및 동시성 제어**
볼륨은 컨테이너의 쓰기 가능 레이어와 달리 Copy-on-Write(CoW) 오버헤드가 없다. 호스트의 파일 시스템에 직접 쓰기 작업을 수행하므로 네이티브 수준의 I/O 성능을 보장한다. 또한, 하나의 볼륨을 여러 개의 컨테이너가 동시에 마운트하여 데이터를 공유할 수 있으며, 이 과정에서 발생하는 파일 락(Lock)이나 동기화 이슈는 기본적으로 리눅스 커널의 파일 시스템 관리 로직을 그대로 따른다.

#### 바인드 마운트 (Bind Mounts)

바인드 마운트는 호스트 운영체제의 **임의의 절대 경로**를 컨테이너 내부의 디렉토리와 직접 매핑하는 방식이다. 이는 도커 초기부터 존재했던 방식이며, 도커 엔진의 관리 영역 밖에서 물리적 경로가 결정된다는 특징이 있다.

**1. 호스트 자원의 직접 노출**
바인드 마운트를 사용하면 컨테이너가 호스트의 핵심 설정 파일이나 시스템 바이너리에 직접 접근할 수 있다. 예를 들어, 호스트의 `/etc/nginx/conf.d`를 컨테이너 내부로 연결하여 설정 변경을 즉시 반영하거나, 개발 환경에서 호스트의 소스 코드 디렉토리를 마운트하여 코드 수정 시 즉시 컨테이너에 반영(Hot-reload)하는 용도로 매우 유용하다.

**2. 이식성 및 보안 취약점**
바인드 마운트는 특정 호스트의 파일 시스템 구조에 강하게 결합(Strongly Coupled)된다. 특정 경로가 존재하지 않는 호스트에서는 컨테이너 실행이 실패하며, 무엇보다 컨테이너 내부의 프로세스가 호스트의 파일을 삭제하거나 수정할 수 있는 권한을 가지게 되어 보안상 위험을 초래할 수 있다.

> **파일 시스템 마스크(Masking)와 권한 문제**
> 
> 바인드 마운트 시 가장 자주 발생하는 엔지니어링 이슈는 UID/GID 불일치다. 호스트의 사용자가 생성한 파일을 컨테이너 내부의 루트(root) 사용자가 수정하려고 하거나, 반대로 컨테이너가 생성한 파일의 권한이 호스트에서 일반 사용자로 접근이 불가능한 경우가 빈번하다. 이를 해결하기 위해 `--user` 옵션으로 실행 권한을 맞추거나, 컨테이너 실행 시 진입점에서 `chown` 명령을 통해 권한을 보정하는 로직이 필요하다.
{: .block-warning }

#### tmpfs 마운트

`tmpfs` 마운트는 데이터를 호스트의 디스크가 아닌 시스템의 **메인 메모리(RAM)**에 직접 적재하는 특수한 형태의 스토리지 모델이다. 리눅스 커널의 가상 파일 시스템 기능을 활용하며, 데이터의 영속성을 완전히 배제하는 대신 극단적인 입출력 성능과 보안성을 확보하기 위해 설계되었다.

**1. 메모리 기반 저장의 물리적 메커니즘**
`tmpfs`는 리눅스 커널 내부의 페이지 캐시(Page Cache)와 스왑(Swap) 레이어를 기반으로 구동된다. 일반적인 디스크 기반 마운트와 달리, 데이터를 쓰거나 읽을 때 하드웨어 컨트롤러와 통신하는 물리적 I/O 지연 시간이 발생하지 않는다. 커널은 `tmpfs`로 지정된 경로를 마치 일반 파일 시스템처럼 인식하지만, 실제 연산은 CPU와 RAM 사이의 초고속 버스 대역폭 내에서 완결된다.

**2. 휘발성과 보안성**
컨테이너가 정지되거나 호스트 시스템이 재부팅되면 `tmpfs`에 저장된 모든 데이터는 즉시 소멸한다. 이러한 특성은 다음과 같은 엔지니어링 시나리오에서 강력한 이점을 제공한다.
* **민감 정보 보호**: 데이터베이스 비밀번호나 세션 키와 같은 보안 자산을 디스크에 흔적을 남기지 않고 메모리 상에서만 사용하고자 할 때 활용한다.
* **상태 정보의 고속 처리**: 애플리케이션의 임시 파일, PID 파일, 혹은 빈번하게 갱신되는 카운터 정보를 처리할 때 디스크 수명을 보호하고 성능을 극대화한다.

> **tmpfs의 자원 경합 리스크**
> 
> `tmpfs`는 호스트의 RAM 자원을 직접 점유한다. 만약 컨테이너 내부의 프로세스가 `tmpfs` 영역에 대량의 데이터를 무분별하게 기록하면, 호스트 시스템의 가용 메모리가 고갈되어 **OOM(Out of Memory) Killer**가 작동하거나 시스템 전체의 스와핑(Swapping)을 유발할 수 있다. 따라서 실행 시 `--tmpfs-size` 옵션을 통해 사용할 메모리의 최대치를 엄격히 제한하는 설정이 필수적이다.
{: .block-warning }

#### 명명된 볼륨 (Named Volumes)

명명된 볼륨은 도커 엔진에 의해 고유한 이름(ID)을 부여받아 관리되는 볼륨의 형태다. 사용자가 명시적으로 `docker volume create my_data`와 같이 생성하거나, 컨테이너 실행 시 `-v my_data:/app/data`와 같이 이름을 지정하여 마운트할 때 생성된다.

**1. 관리의 가시성과 이식성**
명명된 볼륨은 호스트의 복잡한 절대 경로 대신 추상화된 이름을 식별자로 사용한다. 이는 `docker volume ls` 명령을 통해 시스템 내의 데이터 저장 현황을 한눈에 파악할 수 있게 하며, 백업이나 복구 명령 시 경로 실수로 인한 데이터 유실 가능성을 낮춘다. 도커 데몬은 이 볼륨들을 `/var/lib/docker/volumes/` 하위의 이름별 디렉토리에 격리하여 관리한다.

**2. 수명 주기 분리**
명명된 볼륨의 가장 큰 특징은 컨테이너와의 **느슨한 결합(Loose Coupling)**이다. 컨테이너가 삭제되더라도 명명된 볼륨은 명시적으로 삭제(`docker volume rm`)하지 않는 한 시스템에 영구적으로 보존된다. 이는 애플리케이션의 버전 업데이트를 위해 컨테이너를 교체하더라도, 기존의 데이터 볼륨을 새 컨테이너에 그대로 연결(Re-attach)하여 끊김 없는 서비스를 유지할 수 있게 한다.

#### 익명 볼륨 (Anonymous Volumes)

익명 볼륨은 이름 없이 시스템에서 자동으로 생성된 UUID 형태의 식별자를 갖는 볼륨이다. 주로 `Dockerfile` 내의 `VOLUME` 지시어를 통해 정의되거나, 컨테이너 실행 시 호스트 경로와 볼륨 이름 없이 마운트 지점만 지정(`-v /data`)했을 때 생성된다.

**1. 묵시적 생성과 관리 부담**
사용자가 이름을 지정하지 않았으므로 도커는 `a1b2c3d4...`와 같은 임의의 긴 문자열로 볼륨을 생성한다. 익명 볼륨은 주로 "애플리케이션이 실행되기 위해 반드시 특정 경로의 영속성이 필요하지만, 사용자가 직접 관리할 필요는 없는 경우"에 사용된다. 하지만 이름이 없기 때문에 시간이 지날수록 어떤 볼륨이 어떤 컨테이너와 연결되었는지 파악하기 어려워지는 '볼륨 비대화' 문제를 야기하기 쉽다.

**2. 자동 삭제 조건**
익명 볼륨은 기본적으로 명명된 볼륨과 동일하게 컨테이너 삭제 후에도 남아있지만, 컨테이너 실행 시 `--rm` 옵션을 사용했다면 컨테이너가 종료되는 시점에 연결된 익명 볼륨도 함께 물리적으로 삭제된다.

> **볼륨 데이터 오버라이드(Override) 로직**
> 
> 컨테이너의 특정 디렉토리에 빈 볼륨을 마운트할 때, 만약 이미지 내부의 해당 경로에 이미 데이터가 존재한다면 도커는 해당 데이터를 볼륨으로 복사(Pre-populate)한다. 하지만 바인드 마운트의 경우 호스트의 디렉토리 내용이 컨테이너 내부의 내용을 완전히 덮어씌워 보이지 않게(Masking) 만든다. 이 미세한 동작 차이는 초기 데이터 구성 전략을 세울 때 매우 중요한 고려 요소가 된다.
{: .block-tip }

### 데이터 관리 매커니즘

단순히 공간을 할당하는 것을 넘어, 도커는 저장된 데이터를 어떻게 효율적으로 이동시키고 보호하며 공유할 것인지에 대한 엔지니어링 프레임워크를 제공한다.

#### 볼륨 드라이버 (Volume Driver)

도커의 볼륨 시스템은 드라이버 플러그인 아키텍처를 기반으로 한다. 기본값인 `local` 드라이버는 호스트의 로컬 디스크를 사용하지만, 볼륨 드라이버를 교체함으로써 데이터 저장의 물리적 위치를 네트워크 너머로 확장할 수 있다.

**1. 네트워크 스토리지 추상화**
볼륨 드라이버를 사용하면 컨테이너는 자신이 로컬 디스크에 데이터를 쓴다고 믿지만, 실제로는 클라우드 저장소나 기업용 NAS에 기록될 수 있다.
* **NFS/CIFS 드라이버**: 전통적인 네트워크 파일 시스템을 볼륨으로 마운트하여 여러 호스트의 컨테이너가 동일한 데이터를 공유하게 한다.
* **Cloud-Native 드라이버**: AWS EBS, Google Persistent Disk, Azure File Storage 등을 도커 볼륨 인터페이스로 추상화하여 클라우드 자원의 유연성을 활용한다.

#### 데이터 공유 (Volumes From)

`--volumes-from` 플래그는 한 컨테이너가 다른 컨테이너에 마운트된 모든 볼륨을 그대로 상속받아 공유할 수 있게 하는 메커니즘이다. 이는 호스트의 경로를 직접 명시하지 않고도 컨테이너 간에 데이터를 주고받을 수 있는 논리적 연결 고리를 형성한다.

**1. 데이터 전용 컨테이너(Data-only Container) 패턴**
과거 도커 볼륨 기능이 고도화되기 전, 데이터를 영속화하기 위해 널리 쓰였던 엔지니어링 패턴이다. 실제 애플리케이션을 구동하지 않는 가벼운 컨테이너(예: `busybox`)를 생성하고 여기에 볼륨을 정의한 뒤, 여러 서비스 컨테이너가 이 데이터 전용 컨테이너로부터 볼륨을 공유받는 방식이다. 이는 볼륨의 관리 주체를 특정 서비스로부터 분리하여 데이터의 독립성을 확보하는 전략이다.

**2. 커널 마운트 네임스페이스의 공유**
도커 엔진은 `--volumes-from` 요청을 받으면, 소스 컨테이너의 `Mount` 네임스페이스 정보를 참조하여 동일한 마운트 포인트 객체를 대상 컨테이너의 네임스페이스로 복제한다. 물리적으로는 호스트의 동일한 디렉토리가 두 컨테이너에 각각 마운트되는 형태이지만, 관리 측면에서는 컨테이너 간의 '참조 관계'를 형성하게 된다.

![](/docs//assets/img/2026-01-25-00-10-02.png)

#### 백업 및 복구 (Export/Import)

도커 환경에서 데이터 백업은 크게 '컨테이너 자체의 상태'를 보존하는 방식과 '마운트된 볼륨 데이터'를 추출하는 방식으로 나뉜다.

* **Docker Export/Import**: 실행 중인 컨테이너의 파일 시스템 전체를 하나의 tar 아카이브 파일로 내보낸다. 이 방식은 컨테이너의 쓰기 가능 레이어(Writable Layer)를 포함한 최종 상태를 스냅샷으로 찍는 것과 같으나, 이미지의 레이어 이력(History)은 유실된다는 단점이 있다.
* **Volume Backup 전략**: 볼륨에 저장된 실제 데이터베이스 파일이나 로그를 백업할 때는, 해당 볼륨을 마운트하는 임시 컨테이너를 실행하여 `tar` 명령어로 호스트에 데이터를 아카이빙하는 방식을 취한다.

> **데이터 일관성(Consistency)의 문제**
> 
> 실행 중인 데이터베이스 컨테이너의 볼륨을 실시간으로 백업할 경우, 메모리에만 머물러 있는 더티 페이지(Dirty Page)가 디스크에 기록되지 않아 백업된 데이터가 손상(Corruption)될 위험이 있다. 따라서 엔지니어링 수준에서는 컨테이너를 일시 정지(`pause`)하거나, 애플리케이션 레벨의 덤프(Dump) 도구를 병행하여 원자성(Atomicity)을 확보해야 한다.
{: .block-warning }

#### 고정 파일 시스템 (Read-only Mount)

보안과 데이터 무결성이 극도로 중요한 환경에서는 마운트 옵션에 `:ro` (Read-only) 플래그를 추가하여 컨테이너가 데이터를 수정하지 못하도록 강제한다.

리눅스 커널의 VFS(Virtual File System) 계층에서 이 마운트 지점에 대해 `MS_RDONLY` 플래그를 활성화하면, 컨테이너 내부 프로세스가 `write()` 시스템 콜을 호출할 때 커널은 즉시 `EPERM` (Operation not permitted) 에러를 반환한다. 이는 설정 파일 변조를 통한 침해 사고를 방지하고, 스테이트리스(Stateless) 아키텍처를 강제하여 애플리케이션의 예측 가능성을 높이는 강력한 수단이 된다.

## 멀티 컨테이너 오케스트레이션 (Docker Compose)

단일 컨테이너를 넘어 복잡한 마이크로서비스 생태계를 구축하게 되면, 수십 개의 컨테이너를 개별적으로 관리하는 것은 인지적 과부하와 운영 실수를 유발한다. 도커 컴포즈(Docker Compose)는 다중 컨테이너 애플리케이션을 정의하고 실행하기 위한 오케스트레이션 도구로, 명령형(Imperative) 방식의 컨테이너 관리를 선언적(Declarative) 방식으로 전환하는 패러다임의 변화를 상징한다.

### Compose 아키텍처

도커 컴포즈는 도커 엔진 위에 존재하는 고수준 추상화 계층이다. 사용자가 YAML 형식으로 작성한 서비스 설계도를 읽어 들여, 도커 API가 이해할 수 있는 일련의 명령어로 변환하고 순차적/병렬적으로 실행하는 '조율사' 역할을 수행한다.

#### Compose 규격 (YAML Spec)

컴포즈 파일은 애플리케이션의 최종 상태(Desired State)를 기술하는 기술서다. 도커는 이 YAML 파일을 파싱하여 컨테이너, 네트워크, 볼륨 사이의 유기적인 관계를 정의한다.

**1. 데이터 구조와 스키마 버전**
컴포즈 규격은 버전에 따라 지원하는 기능이 다르다. 초기에는 단순한 링크 위주였으나, 최신 규격(Compose Specification)은 오케스트레이션과 하드웨어 리소스(GPU, 메모리 예약 등) 제어까지 포괄하는 광범위한 스키마를 갖춘다.

**2. 멱등성(Idempotency) 보장**
컴포즈의 가장 큰 기술적 특징은 멱등성이다. `docker-compose up`을 여러 번 실행하더라도, 설정이 바뀌지 않았다면 도커는 기존 컨테이너를 파괴하지 않고 유지한다. 이는 현재 실행 중인 시스템의 상태와 YAML에 기술된 상태를 비교(Diff)하여 변경된 부분만을 선택적으로 업데이트하는 제어 루프(Control Loop) 알고리즘을 기반으로 한다.

![](/docs//assets/img/2026-01-25-00-10-08.png)

#### 서비스 정의 (Services)

도커 컴포즈 아키텍처의 가장 원자적인 단위는 **서비스(Service)**이다. 서비스는 단순히 실행 중인 컨테이너 하나를 의미하는 것이 아니라, 동일한 설정과 이미지를 공유하는 컨테이너들의 '논리적 추상화'를 의미한다. 컴포즈 파일 내에서 정의된 하나의 서비스 섹션은 도커 엔진에게 "이러한 형상(Configuration)을 가진 프로세스 그룹을 유지하라"는 명령과 같다.

**1. 설정의 캡슐화와 이식성**
서비스 정의에는 이미지 이름, 포트 매핑, 환경 변수, 볼륨 마운트 정보가 포함된다. 이는 개별 `docker run` 명령어로 흩어져 있던 파편화된 정보를 하나의 명세서로 캡슐화한다. 엔지니어링 측면에서 서비스 정의는 애플리케이션의 '실행 설계도'가 되며, 동일한 YAML 파일이 개발자의 로컬 머신부터 스테이징, 프로덕션 환경까지 일관된 실행 환경을 보장하는 근거가 된다.

**2. 서비스와 컨테이너의 1:N 관계**
서비스는 복제(Replication)될 수 있는 구조를 전제로 한다. 사용자가 특정 서비스를 '스케일(Scale)'하면, 도커 컴포즈는 동일한 서비스 정의를 기반으로 이름(Suffix)만 다른 여러 개의 컨테이너 인스턴스를 생성한다. 이때 각 컨테이너는 서비스 이름이 부여된 전용 네트워크 별칭(Alias)을 공유하므로, 외부에서는 서비스 이름 하나로 여러 컨테이너에 접근할 수 있는 내부 로드 밸런싱 구조가 형성된다.

> **서비스 정의의 변경과 교체 메커니즘**
> 
> 컴포즈는 서비스 정의가 변경되었음을 감지하면, 기존 컨테이너를 즉시 파괴하고 새로운 설정이 적용된 컨테이너를 생성한다. 이때 도커는 컨테이너의 '이름'과 '설정 해시'를 비교하여 변경 여부를 판단한다. 만약 서비스 이름은 같지만 이미지 태그가 바뀌었다면, 컴포즈는 이를 'Desired State'와의 불일치로 간주하여 교체 작업을 수행한다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-10-14.png)

#### 프로젝트 (Project)

프로젝트(Project)는 도커 컴포즈가 관리하는 가장 상위의 격리 단위다. 기본적으로 컴포즈는 YAML 파일이 위치한 **디렉토리의 이름**을 프로젝트 이름으로 사용하며, 이를 통해 동일한 호스트 내에서 서로 다른 애플리케이션 그룹이 자원을 혼용하지 않도록 격리 경계를 세운다.

**1. 네임스페이스 접두사(Prefixing) 전략**
도커 컴포즈는 프로젝트 내부에서 생성되는 모든 리소스(컨테이너, 네트워크, 볼륨)의 이름 앞에 프로젝트 이름을 접두사로 붙인다. 예를 들어 프로젝트 이름이 `myapp`이고 서비스 이름이 `web`이라면, 실제 생성되는 컨테이너 이름은 `myapp-web-1`이 된다. 이는 호스트 전체의 전역 네임스페이스에서 리소스 이름 충돌을 방지하는 매우 단순하면서도 강력한 메커니즘이다.

**2. 프로젝트 단위의 생명 주기 관리**
`docker-compose up`이나 `down` 명령은 항상 프로젝트 단위로 작동한다. 특정 프로젝트를 종료하면 해당 프로젝트 접두사가 붙은 모든 리소스가 일괄적으로 정리된다. 이는 개발자가 여러 프로젝트를 동시에 진행할 때, 한 프로젝트의 정리가 다른 프로젝트의 컨테이너에 영향을 주지 않도록 보장하는 논리적 안전장치가 된다.

> **프로젝트 이름의 강제 변경과 격리 탈피**
> 
> `--project-name` (또는 `-p`) 옵션을 사용하면 디렉토리 이름과 무관하게 프로젝트 이름을 지정할 수 있다. 이를 통해 동일한 컴포즈 파일을 사용하여 'test', 'dev', 'prod'라는 서로 다른 프로젝트를 한 호스트에 동시에 띄울 수 있다. 하지만 프로젝트 이름이 달라지면 생성되는 네트워크도 달라지므로, 프로젝트 간 통신이 필요한 경우 외부 네트워크(External Network)를 정의하여 연결하는 추가적인 설계가 필요하다.
{: .block-warning }

#### 스택 (Stack)

스택(Stack)은 본래 Docker Swarm 모드에서 다중 노드 클러스터에 배포되는 서비스 그룹을 지칭하는 용어였으나, 현대의 도커 생태계에서는 컴포즈 파일을 통해 배포되는 **'전체 인프라의 계층 구조'**를 의미하는 개념으로 확장되었다. 스택은 서비스, 네트워크, 볼륨이라는 개별 컴포넌트들이 모여 하나의 완성된 시스템(예: 3-Tier Web App)을 이루는 상태를 뜻한다.

**1. 선언적 상태 관리의 정점**
스택 아키텍처의 핵심은 사용자가 리소스의 생성 '순서'를 고민하지 않아도 된다는 것이다. 컴포즈 엔진은 스택 내부의 의존성(depends_on)과 네트워크 구조를 분석하여 최적의 생성 순서를 결정하는 그래프(Graph) 알고리즘을 구동한다. 사용자는 오직 최종적인 시스템의 '모양새'를 정의할 뿐이며, 하부의 복잡한 연결 과정은 스택 관리 엔진에 위임된다.

**2. 고가용성(HA)과 복제 본문(Deploy)**
스택 수준에서는 단일 컨테이너의 실행을 넘어, 서비스의 유지 개수(Replicas), 업데이트 전략(Rolling Update), 리소스 제약 사항(Resource Constraints) 등을 기술한다. 특히 `deploy` 섹션은 스택이 오케스트레이션 엔진(Swarm 등)에 전달하는 핵심 메타데이터를 담고 있으며, 이는 컨테이너 하나가 죽었을 때 자동으로 새 컨테이너를 보충하는 등의 클러스터 레벨 복구 로직의 근거가 된다.

![](/docs//assets/img/2026-01-25-00-10-21.png)

### 서비스 구성 요소

컴포즈 파일 내의 서비스 정의는 컨테이너의 물리적 특성과 논리적 관계를 결정짓는 다양한 속성들로 구성된다. 이 속성들은 단순한 설정값을 넘어, 리눅스 커널의 시스템 콜 파라미터나 도커 엔진의 런타임 옵션으로 직결되는 기술적 명세들이다.

#### 이미지 지정 (image/build)

서비스가 구동될 소스(Source)를 정의하는 방식은 이미 존재하는 이미지를 가져오거나(Pull), 소스 코드로부터 새로 빌드하는(Build) 두 가지 경로로 나뉜다.

**1. image: 외부 이미지의 참조**
레지스트리에 저장된 이미지를 사용하는 방식이다. 태그(`:latest`, `:v1.0`)를 명시하여 버전의 정합성을 유지한다. 엔지니어링 측면에서 태그를 생략하거나 `:latest`를 남용하는 것은 배포의 예측 가능성을 파괴하는 행위이므로, 항상 특정 커밋 해시나 시맨틱 버저닝(SemVer)이 적용된 고유 태그를 사용하는 것이 권장된다.

**2. build: 컨텍스트 기반의 동적 생성**
`build` 지시어는 특정 디렉토리(Context)와 `Dockerfile`을 참조하여 컨테이너 실행 전 이미지를 즉석에서 빌드한다. 
* **멀티 스테이지 빌드 연동**: 컴포즈는 Dockerfile 내부의 특정 타겟 스테이지를 지정하여 빌드할 수 있는 기능을 지원한다.
* **캐시 관리**: 빌드 시 인자(args)를 전달하거나 레이어 캐시를 재사용하기 위한 설정을 포함할 수 있다.

> **Build와 Image의 혼용 전략**
> 
> 컴포즈 파일에 `image`와 `build`를 동시에 적으면, 컴포즈는 지정된 경로에서 이미지를 빌드한 뒤 해당 이미지에 `image` 지시어에 적힌 이름을 태그로 붙인다. 이는 로컬에서 개발한 서비스를 빌드와 동시에 사설 레지스트리 경로로 이름 지어, 이후 `push` 명령 한 번으로 배포 준비를 끝내기 위한 엔지니어링 기법이다.
{: .block-tip }

#### 컨테이너 이름 (container_name)

`container_name` 지시어는 도커 컴포즈가 자동으로 생성하는 컨테이너의 명명 규칙을 무시하고, 사용자가 정의한 고정된 이름을 부여한다. 기본적으로 도커 컴포즈는 `{프로젝트명}_{서비스명}_{인덱스}` 형태의 이름을 사용하여 리소스를 관리하지만, 특정 상황에서는 예측 가능한 이름을 강제해야 할 필요가 있다.

**1. 명명 규칙의 물리적 충돌**
도커 엔진 내에서 컨테이너 이름은 유일성(Uniqueness)을 가져야 한다. `container_name`을 명시하는 순간, 해당 서비스는 호스트 내에서 단 하나의 인스턴스만 존재할 수 있는 **싱글톤(Singleton)** 리소스가 된다. 이는 서비스의 확장성(Scaling)을 원천적으로 차단하는 행위다. 만약 `docker-compose up --scale web=3` 명령을 내리더라도, 이름 충돌로 인해 추가 컨테이너 생성은 실패하게 된다.

**2. 네임스페이스와 서비스 디스커버리**
엔지니어링 측면에서 고정된 컨테이너 이름은 외부 모니터링 시스템이나 레거시 스크립트가 특정 컨테이너를 식별할 때 유용하다. 하지만 도커 컴포즈의 내장 DNS는 기본적으로 '서비스 이름'을 통해 IP 주소를 리졸빙(Resolving)하므로, 통신을 위해 굳이 물리적인 컨테이너 이름을 고정할 필요는 없다. 오히려 고정된 이름은 프로젝트 간의 격리를 모호하게 만들 위험이 크다.

#### 재시작 정책 (restart_policy)

재시작 정책은 컨테이너 내부의 프로세스가 종료되거나 도커 데몬이 재시작될 때, 컨테이너를 어떤 조건에서 다시 깨울 것인지 정의하는 복구 메커니즘이다. 이는 시스템의 자가 치유(Self-healing) 능력을 결정짓는 핵심 설정이다.

**1. 종료 코드와 재시작 로직**
도커 데몬은 컨테이너 내부 PID 1 프로세스의 종료 코드(Exit Code)를 실시간으로 모니터링한다.
* **no**: 어떤 상황에서도 재시작하지 않는다. (기본값)
* **always**: 종료 코드와 상관없이 항상 재시작한다. 수동으로 정지시키지 않는 한 무한 루프를 돌며 가용성을 유지한다.
* **on-failure**: 프로세스가 0이 아닌 코드(에러)로 종료되었을 때만 재시작한다. 정상 종료 시에는 자원을 반납하도록 설계할 때 사용한다.
* **unless-stopped**: `always`와 유사하지만, 사용자가 명시적으로 정지(`docker stop`)시킨 경우에는 데몬이 재시작되어도 컨테이너를 깨우지 않는다.

**2. 지수 백오프(Exponential Backoff) 전략**
프로세스가 실행 직후 계속해서 실패하는 '데드 루프'에 빠질 경우, 도커 엔진은 무분별한 재시작으로 인한 CPU 과부하를 막기 위해 재시작 간격을 점진적으로 늘리는 지수 백오프 알고리즘을 적용한다. 이는 시스템의 안정성을 보호하기 위한 커널 수준의 스케줄링 배려와 맞닿아 있다.

#### 의존성 제어 (depends_on)

`depends_on`은 다중 컨테이너 환경에서 서비스 간의 **실행 순서(Start Order)**를 정의한다. 웹 서버가 실행되기 전에 데이터베이스가 먼저 준비되어야 하는 것과 같은 논리적 선후 관계를 조율한다.

**1. 프로세스 시작과 서비스 준비의 간극**
초기 도커 컴포즈에서 `depends_on`은 단순히 '컨테이너 프로세스가 실행되었는가'만을 판단했다. 하지만 데이터베이스 프로세스가 떴다고 해서 바로 쿼리를 처리할 수 있는 것은 아니다. 내부 초기화(Warm-up) 시간이 필요하기 때문이다. 이 간극을 메우지 못하면 웹 서버는 DB 연결 실패 에러를 내며 종료되는 '부팅 레이스 컨디션(Boot Race Condition)'이 발생한다.

**2. 헬스체크 연동 (Condition-based Dependency)**
현대적인 컴포즈 규격은 `condition` 속성을 통해 이 문제를 해결한다.
* `service_started`: 프로세스가 시작되면 다음 서비스 실행.
* `service_healthy`: 대상 서비스의 `healthcheck`가 성공 판정을 받아야만 다음 서비스 실행.
* `service_completed_successfully`: 일회성 작업(Migration 등)이 성공적으로 종료되어야 다음 단계 진행.

![](/docs//assets/img/2026-01-25-00-10-27.png)

> **의존성 관리의 한계**
> 
> `depends_on`은 오직 `docker-compose up` 시점의 순서만을 제어한다. 실행 도중 데이터베이스가 예기치 않게 죽었을 때 웹 서버를 함께 제어하는 기능은 포함되어 있지 않다. 따라서 애플리케이션 레벨에서 재연결 로직(Retry Logic)을 구현하는 것이 진정한 의미의 탄력적(Resilient) 아키텍처를 완성하는 길이다.
{: .block-warning }

### 실행 및 관리

설계도가 완성되었다면, 이제 이를 실제 물리 자원 위에서 구동하고 유지보수하는 단계로 넘어간다. 도커 컴포즈의 실행 모델은 단순한 컨테이너 묶음을 넘어, 전체 프로젝트의 상태(State)를 관리하는 선언적 워크플로우를 제공한다.

#### 프로젝트 생명 주기 (up/down)

`up`과 `down` 명령은 컴포즈 프로젝트의 전체 수명 주기를 관장하는 가장 강력한 도구이다.

**1. up: 상태 수렴(State Convergence)**
`up` 명령이 실행되면 컴포즈 엔진은 현재 호스트의 상태를 조사하고, YAML 파일에 정의된 '이상적인 상태(Desired State)'가 되도록 차이점(Diff)을 계산한다. 이미지가 없으면 풀(Pull)하거나 빌드하고, 네트워크가 없으면 생성하며, 컨테이너를 순서에 맞춰 기동한다. 이때 `-d` 옵션을 사용하면 백그라운드에서 데몬 형태로 실행되어 터미널 세션과 무관하게 서비스를 유지한다.

**2. down: 자원의 완전한 회수**
`down` 명령은 프로젝트와 관련된 모든 가상 자원을 파괴한다. 컨테이너를 정지 및 삭제하고, 생성된 사용자 정의 네트워크를 제거한다. 중요한 점은 기본적으로 볼륨(Volumes)은 보존된다는 것이다. 만약 데이터까지 완전히 초기화하고 싶다면 `--volumes` (또는 `-v`) 플래그를 추가하여 스토리지 마운트까지 물리적으로 제거해야 한다.

#### 병렬 실행 제어

도커 컴포즈는 다수의 서비스를 기동할 때, 단순히 파일에 기재된 순서대로 하나씩 처리하는 순차적 실행 방식에 머물지 않는다. 컴포즈 엔진은 서비스 간의 의존성(depends_on)을 분석하여 **유향 비순환 그래프(DAG, Directed Acyclic Graph)**를 생성하고, 상호 의존성이 없는 서비스들을 최대한 병렬로 실행하여 전체 시스템의 가동 시간(Wall Time)을 단축한다.

**1. 내부 워커 풀(Worker Pool)과 동시성**
컴포즈는 내부적으로 워커 풀을 사용하여 여러 서비스의 `create` 및 `start` API 요청을 도커 데몬으로 동시에 전송한다. 이는 특히 수십 개의 마이크로서비스로 구성된 복잡한 스택을 배포할 때 큰 성능 이점을 제공한다. 하지만 병렬 실행은 호스트 시스템에 일시적인 리소스 피크(Resource Peak)를 유발할 수 있다.

**2. I/O 스톰(Storm)과 하드웨어 경합**
동시에 여러 컨테이너가 이미지를 풀(Pull)하거나 레이어를 압축 해제하고 파일 시스템을 구성할 때, 호스트의 디스크 I/O 대역폭과 CPU 자원에 극심한 부하가 집중되는 'I/O 스톰' 현상이 발생할 수 있다. 이를 제어하기 위해 컴포즈는 `--parallel` 옵션을 통해 최대 병렬 작업 수를 제한하는 기능을 제공한다. 엔지니어링 측면에서는 무조건적인 병렬화보다는 시스템의 디스크 서브시스템 성능(예: NVMe 여부)에 맞춰 적절한 동시성을 유지하는 것이 부팅 실패를 방지하는 안정적인 전략이다.

#### 환경 변수 확장 (.env)

도커 컴포즈의 강력함은 정적인 YAML 파일을 동적으로 변환하는 환경 변수 확장 메커니즘에서 나온다. 컴포즈는 빌드 시점과 실행 시점에 환경 변수를 주입하고 교체하는 정교한 우선순위 규칙을 따른다.

**1. 변수 치환(Interpolation)의 단계**
컴포즈 엔진은 YAML 파일을 해석하기 전, 텍스트 레벨에서 변수 치환 작업을 먼저 수행한다. `${VARIABLE:-default}`와 같은 쉘 문법을 지원하며, 이를 통해 하나의 컴포즈 파일로 여러 환경(Dev, Staging, Prod)에 대응할 수 있다.

**2. 우선순위 계층 구조 (Precedence)**
변수 값이 중복 정의될 경우, 컴포즈는 다음의 엄격한 순서에 따라 최종값을 결정한다.
1.  **Compose 파일 내부**: `environment` 섹션에 명시된 값.
2.  **쉘 환경 변수**: 실행 중인 터미널 세션에 선언된 값. (호스트 환경 변수가 `.env` 파일보다 우선함)
3.  **환경 변수 파일 (.env)**: 프로젝트 루트 디렉토리에 위치한 파일의 값.
4.  **이미지 정의**: Dockerfile의 `ENV` 지시어로 설정된 기본값.

> **.env 파일의 관리**
> 
> `.env` 파일은 편리하지만 버전 관리 시스템(Git 등)에 포함될 경우 민감한 크리덴셜이 유출되는 치명적인 보안 사고의 근원이 된다. 따라서 실제 운영 환경에서는 `.env`를 템플릿 파일(`.env.example`)로만 관리하고, 실제 값은 배포 파이프라인의 시크릿 관리 도구(Vault, AWS Secrets Manager 등)를 통해 쉘 환경 변수로 주입하는 것이 엔지니어링 표준이다.
{: .block-warning }

#### 컨테이너 스케일링 (scale)

스케일링은 특정 서비스의 컨테이너 인스턴스 개수를 동적으로 조절하여 부하를 분산하고 처리량을 늘리는 기술이다. 컴포즈는 `--scale` 플래그나 `replicas` 설정을 통해 이를 지원한다.

**1. DNS 라운드 로빈(Round-robin) 메커니즘**
서비스가 3개로 스케일링(`web=3`)되면, 도커의 내장 DNS 서버는 `web`이라는 서비스 이름에 대해 3개의 서로 다른 컨테이너 IP 주소를 매핑한다. 외부 서비스가 `web`으로 질의를 보낼 때마다 DNS는 이 주소들의 순서를 바꾸어 응답함으로써, 클라이언트 측 로드 밸런싱을 유도한다.

**2. 호스트 포트 충돌 문제**
스케일링 시 가장 큰 기술적 제약은 호스트 포트 바인딩이다. 만약 `80:80`과 같이 호스트 포트를 고정하여 매핑했다면, 두 번째 컨테이너부터는 호스트의 80번 포트가 이미 점유되어 실행에 실패한다. 이를 해결하기 위해 엔지니어링 수준에서는 호스트 포트를 비워두고(`- 80`) 도커가 임의의 포트를 할당하게 하거나, 앞단에 Nginx나 HAProxy와 같은 전용 로드 밸런서를 배치하여 트래픽을 중계하는 설계를 취해야 한다.

![](/docs//assets/img/2026-01-25-00-10-38.png)

#### 컴포즈 프로파일 (Profiles)

컴포즈 프로파일은 하나의 YAML 파일 내에서 특정 서비스 그룹을 선택적으로 활성화하거나 비활성화할 수 있게 하는 논리적 그룹화 기능이다. 이는 '개발 전용 도구', '모니터링 스택', '디버깅 도구' 등을 메인 애플리케이션과 분리하여 관리할 때 탁월한 효율을 제공한다.

**1. 선별적 기동 로직**
각 서비스 정의에 `profiles` 키를 추가하고 그룹 이름을 지정한다. `docker-compose up` 명령 시 `--profile` 옵션을 주지 않으면, 프로파일이 지정된 서비스들은 무시되고 기본 서비스들만 실행된다. 이는 불필요한 자원 낭비를 막고 로컬 개발 환경의 부하를 최적화한다.

**2. 프로파일 간 의존성 전파**
중요한 점은 의존성 관계에서의 동작이다. 프로파일이 적용된 서비스가 기본 서비스의 `depends_on` 대상이 될 경우, 해당 프로파일을 명시적으로 활성화하지 않으면 기본 서비스의 실행도 보류되거나 에러가 발생할 수 있다. 따라서 프로파일 설계 시에는 서비스 간의 결합도를 면밀히 분석하여 독립적인 운영이 가능하도록 레이아웃을 구성해야 한다.

## 보안 및 시스템 보호 (Protection & Security)

컨테이너 보안의 핵심은 '격리(Isolation)'와 '최소 권한 원칙(Principle of Least Privilege)'의 완벽한 구현에 있습니다. 현대적인 컨테이너 런타임은 호스트 커널을 공유한다는 구조적 한계를 극복하기 위해 다층적인 방어 체계(Defense in Depth)를 구축합니다. 이는 단순한 프로세스 격리를 넘어, 하드웨어 자원 접근 권한부터 커널 시스템 콜의 필터링에 이르기까지 시스템의 모든 접점을 통제하는 것을 의미합니다.

### 권한 및 격리 제어

도커의 권한 관리 모델은 호스트 OS의 루트 권한이 컨테이너 내부로 전이되는 것을 차단하고, 컨테이너가 탈옥(Breakout)하더라도 호스트 시스템에 미치는 영향을 최소화하도록 설계되었습니다. 이를 위해 리눅스 커널의 사용자 네임스페이스와 기능 제어 매커니즘을 적극적으로 활용합니다.

#### 루트리스 모드 (Rootless Mode)

루트리스 모드는 도커 데몬(dockerd)과 컨테이너 프로세스를 호스트의 루트 권한이 아닌 일반 사용자(Non-root user) 권한으로 실행하는 보안 아키텍처입니다. 이는 컨테이너 런타임 자체의 취약점으로 인해 공격자가 데몬의 제어권을 획득하더라도, 호스트 시스템 전체의 루트 권한을 얻지 못하게 차단하는 강력한 격리벽 역할을 수행합니다.

루트리스 모드의 동작을 가능하게 하는 핵심은 `user_namespaces(7)`입니다. 컨테이너 내부의 루트(UID 0)를 호스트의 일반 사용자(예: UID 1000)로 매핑함으로써, 프로세스는 컨테이너 안에서는 관리자 권한을 행사하지만 커널이 바라보는 실제 물리적 권한은 제한된 상태를 유지합니다.

이 모드에서 해결해야 할 가장 큰 기술적 과제는 네트워크와 스토리지 마운트입니다. 일반 사용자는 네트워크 인터페이스를 생성하거나 privileged port(1024 미만)를 바인딩할 수 없기 때문에, `slirp4netns`를 사용하여 사용자 공간 TCP/IP 스택을 에뮬레이션합니다. 이는 커널의 네트워크 스택을 직접 건드리는 대신 TAP 장치를 통해 트래픽을 가공하여 전달하는 방식입니다. 또한, 파일시스템 마운트를 위해 `fuse-overlayfs`를 사용하며, 이는 커널 수준의 OverlayFS가 요구하는 특권 권한 없이도 레이어 구조를 유지할 수 있게 합니다.

> **보안 vs 성능**
> 
> 루트리스 모드는 호스트 보안을 획기적으로 향상시키지만, `slirp4netns`를 통한 네트워크 패킷 처리 시 커널과 사용자 공간 사이의 잦은 컨텍스트 스위칭(Context Switching)으로 인해 네트워크 성능 저하가 발생합니다. 또한, MTU(Maximum Transmission Unit) 설정의 제약과 IP 가상화의 오버헤드는 고성능 I/O가 필요한 애플리케이션에서 치명적인 병목 현상을 유발할 수 있습니다.
{: .block-warning }

![](/docs//assets/img/2026-01-25-00-10-43.png)

#### 리눅스 기능 제어 (Capabilities)

리눅스 커널은 전통적으로 프로세스 권한을 '특권 프로세스(Root)'와 '비특권 프로세스'로 양분했습니다. 하지만 이러한 구조는 작은 권한(예: 시스템 시간 변경)이 필요한 프로세스에게도 모든 시스템 통제권을 부여해야 하는 보안상 허점을 가집니다. 이를 해결하기 위해 등장한 `capabilities(7)`는 루트의 막강한 권한을 약 40여 개의 독립적인 비트로 세분화합니다.

도커는 컨테이너 실행 시 기본적으로 '화이트리스트' 방식을 채택합니다. 즉, 프로세스가 실행될 때 루트 권한으로 구동되더라도 커널 레벨에서 대부분의 위험한 기능을 제거(Drop)합니다. 예를 들어, 커널 모듈을 로드하는 `CAP_SYS_MODULE`이나 호스트를 재부팅하는 `CAP_SYS_BOOT`는 기본적으로 차단됩니다.

컨테이너 런타임은 `prctl(PR_CAPBSET_DROP)` 시스템 콜을 호출하여 자식 프로세스들이 상속받을 수 있는 기능의 최대 범위(Bounding Set)를 제한합니다. 이를 통해 컨테이너 내부의 프로세스는 설령 UID 0으로 실행되더라도 물리적 하드웨어 제어나 민감한 커널 설정 변경이 불가능한 '거세된 루트' 상태가 됩니다.

![](/docs//assets/img/2026-01-25-00-10-55.png)

#### 특권 모드 (Privileged Mode)

`--privileged` 플래그를 통해 활성화되는 특권 모드는 도커의 모든 보안 격리 매커니즘을 무력화하고 컨테이너에게 호스트의 루트와 거의 동일한 권한을 부여합니다. 이 모드에서 컨테이너는 호스트의 모든 장치 노드(`/dev`)에 접근할 수 있으며, AppArmor나 Seccomp에 의한 시스템 콜 제한을 받지 않습니다.

특권 모드의 주요 동작 원리는 커널의 `Capability Bounding Set`을 모두 허용으로 채우고, `cgroups`의 장치 제어기(Device Controller) 제한을 해제하는 것입니다. 이는 주로 'Docker in Docker(DinD)'와 같이 컨테이너 내부에서 다시 컨테이너 런타임을 구동해야 하거나, 커널 수준의 네트워크 드라이버를 직접 조작해야 하는 특수한 시스템 관리 도구에서만 제한적으로 사용되어야 합니다.

엔지니어링 관점에서 특권 모드는 컨테이너 기술의 본질인 '격리'를 스스로 부정하는 선택입니다. 공격자가 특권 컨테이너를 장악할 경우, 간단한 `mount` 명령만으로 호스트의 루트 파일시스템을 컨테이너 내부로 가져와 전체 시스템을 완전히 장악할 수 있는 탈옥 경로를 제공하게 됩니다. 따라서 운영 환경에서는 특권 모드 대신 필요한 최소한의 Capability만 `--cap-add`로 추가하는 방식이 강제되어야 합니다.

#### 사용자 권한 격리 (User Namespace)

사용자 네임스페이스(User Namespace)는 컨테이너 내부의 사용자 및 그룹 ID(UID/GID)를 호스트 시스템의 전혀 다른 ID 범위로 매핑하는 커널 레벨의 가상화 기술입니다. 이 매커니즘은 '컨테이너 내부의 루트가 호스트의 루트와 동일하다'는 전통적인 컨테이너 보안의 가장 치명적인 약점을 원천적으로 봉쇄합니다. 사용자 네임스페이스가 활성화되면, 컨테이너 프로세스는 자신을 UID 0(Root)으로 인식하고 모든 특권 작업을 수행하는 것처럼 보이지만, 실제 호스트 커널이 인식하는 해당 프로세스의 UID는 권한이 없는 높은 번호의 ID(예: 100000)로 치환됩니다.

이 매핑 시스템의 핵심은 `/proc/[pid]/uid_map`과 `/proc/[pid]/gid_map` 파일에 정의된 변환 규칙입니다. 커널은 프로세스가 시스템 콜을 호출할 때마다 이 매핑 테이블을 참조하여 권한을 검증합니다. 예를 들어, 컨테이너 내부 프로세스가 파일에 접근하려고 하면 커널은 해당 파일의 inode에 기록된 UID와 프로세스의 '실제(Real) UID'를 대조합니다. 만약 공격자가 컨테이너를 탈옥하여 호스트의 파일 시스템에 접근하더라도, 커널은 그를 호스트의 루트가 아닌 정체불명의 일반 사용자로 취급하므로 민감한 시스템 파일에 대한 쓰기 권한을 거부하게 됩니다.

> **ID 매핑에 따른 권한 전이 제어**
> 
> 사용자 네임스페이스를 통한 격리는 단순한 권한 제한을 넘어 데이터의 소유권 구조 자체를 가상화합니다. 이는 다중 테넌트(Multi-tenant) 환경에서 각 컨테이너가 서로의 파일을 절대 볼 수 없도록 보장하는 가장 강력한 물리적 격리 수단이 됩니다.
{: .block-tip }

하지만 사용자 네임스페이스의 도입은 엔지니어링 측면에서 파일 시스템 소유권 관리의 복잡성을 가중시킵니다. 호스트의 볼륨을 컨테이너에 마운트할 때, 호스트 상의 파일 UID와 컨테이너 내부 매핑 UID가 일치하지 않아 `Permission Denied` 오류가 빈번하게 발생합니다. 이를 해결하기 위해 최근 커널에서는 `idmapped mounts`와 같은 기술을 통해 마운트 지점 자체에서 ID를 실시간으로 변환하는 기능을 지원하기 시작했습니다.

### 커널 보안 인터페이스 연동

도커는 리눅스 커널이 제공하는 정교한 보안 프레임워크들을 유기적으로 결합하여 컨테이너를 보호합니다. 이는 컨테이너가 시스템의 공유 자원을 요청할 때마다 통과해야 하는 '검문소' 역할을 하며, 악의적인 시스템 콜이나 비정상적인 자원 접근을 실시간으로 차단하는 방어선입니다.

#### Seccomp 프로파일 (Syscall Filtering)

Seccomp(Secure Computing mode)은 프로세스가 호출할 수 있는 시스템 콜(System Call)의 종류를 필터링하는 커널의 샌드박싱 메커니즘입니다. 리눅스 커널은 수백 개의 시스템 콜을 제공하지만, 일반적인 애플리케이션은 그중 극히 일부만을 사용합니다. Seccomp은 '사용하지 않는 시스템 콜은 잠재적인 공격 경로(Attack Surface)'라는 전제하에, 불필요한 시스템 콜을 호출하는 즉시 프로세스를 강제 종료(SIGKILL)하거나 에러를 반환합니다.

도커는 기본적으로 약 300여 개의 시스템 콜 중 보안상 위험하다고 판단되는 약 40여 개를 차단하는 기본 Seccomp 프로파일을 적용합니다. 예를 들어, 커널의 물리적 메모리 영역에 접근하거나 하드웨어를 직접 제어하는 시스템 콜들은 기본적으로 허용 리스트에서 제외됩니다. 이 필터링은 커널 내부에서 BPF(Berkeley Packet Filter) 바이트코드로 변환되어 실행되는데, 이는 컨텍스트 스위칭 오버헤드 없이 시스템 콜 호출 시점에서 극도로 빠르게 실행되는 장점을 가집니다.

![](/docs//assets/img/2026-01-25-00-14-53.png)

> **보안 강도와 애플리케이션 호환성**
> 
> 지나치게 엄격한 Seccomp 프로파일은 특정 언어 런타임이나 디버깅 도구가 사용하는 필수 시스템 콜까지 차단하여 서비스 장애를 유발할 수 있습니다. 예를 들어, 성능 측정을 위한 `perf_event_open`과 같은 호출은 보안상 기본 차단되지만, 모니터링 에이전트 구동을 위해서는 명시적인 허용이 필요합니다.
{: .block-warning }

#### AppArmor 프로파일

AppArmor는 프로그램의 절대 경로를 기반으로 해당 프로그램이 접근할 수 있는 파일, 네트워크, 자원을 제어하는 커널 보안 모듈(LSM, Linux Security Module)입니다. Seccomp이 '무엇을 할 수 있는가(행위)'를 제약한다면, AppArmor는 '어디에 접근할 수 있는가(대상)'를 규정합니다. 도커는 실행 시 `docker-default`라는 이름의 AppArmor 프로파일을 생성하여 모든 컨테이너에 적용합니다.

이 프로파일은 컨테이너가 `/proc/sysrq-trigger`와 같은 민감한 커널 인터페이스에 쓰기 작업을 수행하거나, `/sys/kernel/security`와 같은 보안 설정 영역을 탐색하는 것을 금지합니다. AppArmor의 강점은 '거부(Deny)' 지침이 명확하다는 점입니다. 설령 프로세스가 루트 권한을 가지고 있더라도 AppArmor 정책에 정의되지 않은 파일 시스템 영역에 접근하려고 시도하면 커널 수준에서 즉각 거부됩니다. 이는 컨테이너 내부에 침투한 공격자가 시스템 정보를 수집하거나 다른 프로세스의 메모리를 훔쳐보는 행위를 효과적으로 지연시키거나 차단하는 심층 방어의 핵심 요소입니다.

#### SELinux 보안 레이블

SELinux(Security-Enhanced Linux)는 리눅스 커널 수준에서 구현된 강제 접근 제어(MAC, Mandatory Access Control) 매커니즘입니다. AppArmor가 파일의 경로를 기준으로 권한을 제어한다면, SELinux는 모든 주체(프로세스)와 객체(파일, 네트워크 소켓, 장치 등)에 보안 컨텍스트(Security Context)라 불리는 레이블을 부여하고, 이들 사이의 상호작용을 미리 정의된 정책 데이터베이스와 대조하여 통제합니다.

도커에서 SELinux를 활성화하면, 컨테이너 프로세스는 일반적으로 `container_t`와 같은 특정 유형(Type) 레이블을 부여받습니다. 반면, 컨테이너가 접근해야 하는 파일이나 볼륨은 `container_file_t` 레이블을 가집니다. SELinux 정책은 오직 `container_t` 유형의 프로세스만이 `container_file_t` 유형의 객체에 접근할 수 있도록 허용합니다. 이러한 '유형 강제(Type Enforcement)'는 컨테이너 내부 프로세스가 호스트의 시스템 파일(`etc_t`, `var_t` 등)을 건드리는 것을 원천 차단하는 강력한 논리적 장벽이 됩니다.

특히 다중 컨테이너 환경에서 SELinux는 MCS(Multi-Category Security) 기능을 통해 격리 수준을 한 단계 더 높입니다. 컨테이너마다 고유한 범주 레이블(예: `s0:c123,c456`)을 동적으로 할당하여, 설령 두 컨테이너가 동일한 `container_t` 유형을 가지더라도 서로 다른 범주를 가진 컨테이너의 데이터에는 절대 접근할 수 없게 만듭니다.

> **볼륨 마운트 시의 레이블 충돌 해결**
> 
> 호스트 경로를 컨테이너에 마운트할 때 SELinux 레이블 불일치로 인한 접근 거부가 발생할 수 있습니다. 도커는 볼륨 지정 시 `:z`(공유 가능 레이블) 또는 `:Z`(전용 레이블) 옵션을 통해 마운트된 파일의 SELinux 컨텍스트를 자동으로 재레이블링(Relabeling)하는 기능을 제공합니다.
{: .block-tip }

### 이미지 및 데이터 보안

컨테이너의 실행 시점 보안만큼이나 중요한 것이 정적 자산인 이미지의 무결성과 데이터의 안전성입니다. 공급망 공격(Supply Chain Attack)이 정교해짐에 따라, 신뢰할 수 없는 이미지가 인프라 내부로 유입되는 것을 방지하고 저장된 데이터가 오용되지 않도록 하는 체계적인 보호 전략이 필수적입니다.

#### 이미지 서명 (Docker Content Trust)

도커 콘텐츠 트러스트(DCT, Docker Content Trust)는 이미지의 작성자가 누구인지 확인하고, 이미지가 레지스트리에서 로컬 환경으로 전송되는 과정에서 단 1비트의 변조도 일어나지 않았음을 보증하는 프레임워크입니다. 이는 내부적으로 'The Update Framework(TUF)'를 구현한 Notary 서버를 활용합니다.

DCT를 활성화(`DOCKER_CONTENT_TRUST=1`)하면, 도커 클라이언트는 이미지를 푸시(Push)할 때 작성자의 개인 키로 이미지 매니페스트에 디지털 서명을 생성합니다. 이후 사용자가 이미지를 풀(Pull)할 때, 클라이언트는 해당 이미지를 제공한 레지스트리의 서명을 검증하고 신뢰할 수 있는 서명이 없는 이미지는 실행 자체를 거부합니다. 이 매커니즘은 공격자가 중간에서 이미지를 가로채 악성 코드를 삽입하는 중간자 공격(MITM)이나, 만료된 오래된 이미지를 강제로 주입하는 재생 공격(Replay Attack)으로부터 시스템을 보호합니다.

![](/docs//assets/img/2026-01-25-00-14-59.png)

#### 보안 취약점 스캐닝 (Scanning)

이미지 스캐닝은 컨테이너 이미지 내부에 포함된 운영체제 패키지, 언어별 라이브러리, 바이너리들을 전수 조사하여 알려진 취약점(CVE, Common Vulnerabilities and Exposures)이 존재하는지 확인하는 정적 분석 과정입니다. 이미지는 수많은 레이어로 구성되어 있으므로, 각 레이어의 지문을 추출하여 취약점 데이터베이스와 대조하는 정밀한 분석이 필요합니다.

도커는 `docker scan` 명령(또는 최신 버전의 `docker scout`)을 통해 이미지의 보안 상태를 점검합니다. 이 과정에서 단순히 설치된 패키지 목록을 보는 것을 넘어, 설치된 라이브러리의 버전과 해당 버전에서 발견된 보안 허점의 심각도(CVSS Score)를 리포팅합니다. 특히 상위 베이스 이미지에서 상속된 취약점과 현재 애플리케이션 레이어에서 발생한 취약점을 구분하여 제공함으로써, 엔지니어가 어느 지점에서 보안 패치를 적용해야 할지 명확한 가이드를 제시합니다.

> **취약점 스캐닝의 한계와 능동적 대응**
> 
> 스캐닝 도구는 이미 알려진 취약점(Known Vulnerabilities)을 찾는 데 특화되어 있으므로, 아직 세상에 알려지지 않은 제로데이(Zero-day) 공격을 탐지할 수는 없습니다. 따라서 스캐닝은 일회성 작업이 아닌, CI/CD 파이프라인의 필수 단계로 통합되어 매 빌드 시점마다 자동화되어야 하며, 운영 중인 이미지에 대해서도 주기적인 재검사가 수반되어야 합니다.
{: .block-warning }

#### 도커 시크릿 (Docker Secrets)

컨테이너화된 애플리케이션이 구동되기 위해서는 데이터베이스 비밀번호, API 키, TLS 인증서와 같은 민감한 정보(Secrets)가 반드시 필요합니다. 이러한 정보를 환경 변수(`ENV`)나 이미지 레이어에 직접 포함시키는 것은 보안상 매우 치명적인 행위입니다. 이미지 레이어는 누구나 접근 가능한 읽기 전용 계층이며, 환경 변수는 `docker inspect` 명령이나 컨테이너 내부의 `/proc/self/environ`을 통해 평문으로 노출되기 때문입니다.

도커 시크릿은 이러한 민감 데이터를 안전하게 보관하고 전송하기 위해 설계된 전용 매커니즘입니다. 시크릿은 생성 시 도커 스웜(Swarm) 모드의 매니저 노드에 저장되며, 매니저 노드 간에는 Raft 로그를 통해 강력하게 암호화된 상태로 복제됩니다. 특정 서비스에 시크릿이 할당되면, 도커 엔진은 해당 시크릿을 대상 컨테이너의 메모리 내 파일 시스템인 `tmpfs`에 마운트합니다.

물리적으로 시크릿은 컨테이너 내부의 `/run/secrets/<secret_name>` 경로에 파일 형태로 존재하게 됩니다. 이 방식의 핵심 보안 이점은 데이터가 디스크(Disk)에 절대 기록되지 않는다는 점입니다. 컨테이너가 종료되거나 삭제되면 메모리 상의 데이터는 즉시 소멸하며, 호스트 시스템의 영구 저장소 어디에도 흔적이 남지 않습니다. 또한, 특정 컨테이너는 오직 자신에게 명시적으로 허용된 시크릿에만 접근할 수 있는 '최소 권한의 원칙'이 철저히 지켜집니다.

> **데이터 전송 및 저장의 암호화 매커니즘**
> 
> 도커 시크릿은 전송 시 상호 TLS(mTLS)를 통해 보호되며, 매니저 노드의 디스크에 저장될 때도 AES-256-GCM 등의 알고리즘으로 암호화됩니다. 이는 인프라의 물리적 하드웨어가 탈취되더라도 암호화 키 없이는 민감 정보에 접근할 수 없음을 의미합니다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-15-04.png)

#### 읽기 전용 컨테이너 (Read-only Rootfs)

이미지 레이어 자체는 읽기 전용이지만, 컨테이너가 실행되면 그 위에 '쓰기 가능한 레이어(Writable Layer)'가 추가됩니다. 이는 공격자가 컨테이너 내부의 취약점을 이용해 침투했을 때, 악성 스크립트를 생성하거나 기존 바이너리를 교체하여 시스템을 영구적으로 오염시킬 수 있는 기회를 제공합니다. 읽기 전용 컨테이너 모드(`--read-only`)는 이러한 공격 가능성을 원천적으로 차단하기 위해 컨테이너의 루트 파일 시스템 자체를 읽기 전용으로 마운트합니다.

이 설정이 활성화되면 컨테이너 내부의 모든 경로에 대한 쓰기 시도가 커널 수준에서 거부(`Read-only file system`)됩니다. 이는 애플리케이션이 런타임에 자신의 코드를 수정하거나 민감한 설정 파일을 변경하는 것을 방지하는 강력한 불변성(Immutability)을 강제합니다. 하지만 현대적인 애플리케이션은 로그 기록, 임시 파일 생성(` /tmp`), 세션 관리 등을 위해 최소한의 쓰기 공간을 필요로 합니다.

이를 해결하기 위해 읽기 전용 모드는 보통 `tmpfs` 마운트와 결합하여 사용됩니다. 예를 들어, 루트 파일 시스템은 읽기 전용으로 잠그되, 휘발성 데이터가 필요한 `/tmp`나 `/var/run` 영역만 메모리 기반의 쓰기 가능 공간으로 개방하는 식입니다. 이러한 조합은 공격자가 파일 시스템에 영속적인 백도어를 설치하는 것을 불가능하게 만들며, 재시작 시 모든 변경 사항이 초기화되는 순수 상태를 유지하게 합니다.

> **런타임 불변성과 애플리케이션 설계**
> 
> 애플리케이션이 루트 디렉토리에 로그를 직접 쓰도록 설계되어 있다면 읽기 전용 모드에서 즉시 실행 장애가 발생합니다. 따라서 보안 수준을 높이기 위해서는 로그를 `stdout`으로 스트리밍하거나, 명시적으로 분리된 볼륨 영역에만 쓰도록 애플리케이션 아키텍처를 개선해야 합니다.
{: .block-warning }

## 성능 최적화 및 유지보수

도커의 운영 단계에서 가장 간과하기 쉬운 부분이 시스템 자원의 효율적 관리와 빌드 속도의 최적화입니다. 단순히 컨테이너를 구동하는 것을 넘어, 한정된 컴퓨팅 자원을 어떻게 분배하고 불필요한 데이터 축적을 방지할 것인가는 대규모 인프라 운영의 핵심 역량입니다.

### 빌드 시스템 고도화

이미지 빌드는 개발 주기(Development Cycle)의 병목이 되기 쉬운 지점입니다. 도커는 차세대 빌드 엔진인 BuildKit과 다양한 최적화 기법을 통해 빌드 프로세스를 병렬화하고 결과물의 크기를 최소화하는 방안을 제시합니다.

#### BuildKit 엔진

BuildKit은 도커 18.09 버전부터 도입된 완전히 새로운 이미지 빌드 아키텍처입니다. 기존의 순차적인(Sequential) 빌드 방식과 달리, BuildKit은 `Dockerfile`의 각 인스트럭션 간의 의존성 그래프를 분석하여 연관이 없는 단계들을 동시에 병렬로 실행합니다.

BuildKit의 핵심 혁신 중 하나는 '지능형 캐싱'입니다. 이전 엔진은 하위 레이어가 변경되면 상위 레이어의 캐시를 모두 무효화했지만, BuildKit은 변경되지 않은 파일이 포함된 단계라면 다른 레이어의 변경 여부와 상관없이 캐시를 최대한 활용하려고 시도합니다. 또한, 빌드 컨텍스트 전송 시에도 전체 파일을 압축해서 보내는 대신, 변경된 차이점(Diff)만 스트리밍하여 네트워크 부하를 획기적으로 줄입니다.

![](/docs//assets/img/2026-01-25-00-15-10.png)

#### 멀티 스테이지 빌드 (Multi-stage)

멀티 스테이지 빌드는 단일 `Dockerfile` 내에서 여러 개의 `FROM` 인스트럭션을 사용하여 빌드 프로세스를 논리적으로 분리하는 고도화된 전략입니다. 이 기법의 핵심 목적은 '컴파일 및 빌드 환경'과 '실행 환경'을 물리적으로 격리하여 최종 이미지의 크기를 극한까지 줄이고 보안 표면(Attack Surface)을 최소화하는 데 있습니다.

전통적인 빌드 방식에서는 소스 코드를 컴파일하기 위해 컴파일러, SDK, 빌드 도구(Maven, Go Compiler 등)가 이미지에 포함되어야 했고, 이는 실행 시점에는 전혀 필요 없는 수백 메가바이트의 데이터가 최종 레이어에 잔존하게 만들었습니다. 멀티 스테이지 빌드는 첫 번째 스테이지(예: `build` 스테이지)에서 바이너리를 생성한 후, 두 번째 스테이지(예: `runtime` 스테이지)에서 이전 스테이지의 결과물만을 `COPY --from` 명령으로 추출해 옵니다. 이 과정에서 첫 번째 스테이지에서 생성된 거대한 레이어들과 임시 파일들은 최종 이미지에 포함되지 않고 폐기됩니다.

![](/docs//assets/img/2026-01-25-00-15-15.png)

> **빌드 아티팩트 보존과 레이어 휘발성**
> 
> 멀티 스테이지 빌드는 결과적으로 최종 이미지에 런타임 종속성만을 남기므로, 프로덕션 환경에서의 이미지 전송 속도와 스토리지 효율성을 비약적으로 향상시킵니다. 또한, 빌드 도구에 포함된 보안 취약점이 실행 환경으로 전이되는 것을 원천적으로 차단하는 부수적인 보안 이득을 제공합니다.
{: .block-tip }

#### 빌드 컨텍스트 (Build Context)

빌드 컨텍스트는 `docker build` 명령을 실행할 때 도커 클라이언트가 도커 데몬(Server)으로 전송하는 파일 세트의 집합을 의미합니다. 도커는 클라이언트-서버 아키텍처를 따르므로, 로컬 머신에 파일이 있더라도 데몬이 해당 파일에 접근하여 이미지를 생성하려면 반드시 파일들을 타르볼(tarball) 형태로 묶어 데몬에게 전송하는 과정이 선행되어야 합니다.

엔지니어링 관점에서 빌드 컨텍스트의 크기는 빌드 성능의 결정적인 병목 지점입니다. 컨텍스트가 너무 크면 전송 과정에서 막대한 I/O 대역폭과 CPU 자원이 소모되며, 특히 원격 데몬을 사용하거나 클라우드 빌드 환경에서는 네트워크 지연 시간이 빌드 전체 시간을 지배하게 됩니다. 컨텍스트 전송은 `Dockerfile` 내의 `COPY`나 `ADD` 명령이 실행되기 전, 빌드 프로세스의 최상단에서 발생하기 때문에 불필요한 파일이 포함되지 않도록 관리하는 것이 최우선 과제입니다.

#### .dockerignore 최적화

`.dockerignore` 파일은 빌드 컨텍스트를 구성할 때 전송에서 제외할 파일 패턴을 정의하는 명세서입니다. 이는 Git의 `.gitignore`와 유사한 문법을 공유하지만, 목적은 훨씬 더 하드웨어 지향적입니다. `.dockerignore`를 통해 제외된 파일은 클라이언트가 타르볼을 생성하는 시점부터 배제되므로, 데몬으로의 데이터 전송량을 물리적으로 절감합니다.

최적화의 핵심은 대용량 바이너리, `.git` 디렉토리, 로컬 테스트 로그, 그리고 노드 프로젝트의 `node_modules`와 같은 의존성 폴더를 명확히 제외하는 것입니다. 특히 `.git` 디렉토리는 프로젝트 규모에 따라 수 기가바이트에 달할 수 있는데, 이를 제외하지 않으면 매 빌드마다 거대한 메타데이터를 데몬에게 전송하게 되어 캐시 효율을 떨어뜨리고 빌드 파이프라인을 정체시킵니다.

> **컨텍스트 필터링과 캐시 무효화의 상관관계**
> 
> 컨텍스트에 포함된 파일 중 단 하나라도 변경되면, 해당 파일을 참조하는 `COPY` 인스트럭션 이후의 모든 레이어 캐시는 무효화(Invalidation)됩니다. 따라서 `.dockerignore`를 통해 불필요한 파일의 유입을 차단하는 것은 단순히 전송 속도를 높이는 것을 넘어, 빌드 캐시의 적중률을 극대화하는 전략적 선택입니다.
{: .block-warning }

### 시스템 자원 관리

도커를 장기간 운영하다 보면 'Dangling'이라 불리는 참조되지 않는 이미지 레이어, 중지된 컨테이너의 로그, 사용하지 않는 네트워크 및 볼륨 데이터가 호스트 시스템의 디스크를 잠식하게 됩니다. 이러한 자원 고갈은 시스템 전체의 I/O 성능 저하와 예기치 못한 서비스 중단을 야기할 수 있으므로 능동적인 자원 정리 매커니즘이 필요합니다.

#### 가용 자원 정리 (Pruning)

도커는 시스템 청소를 위해 `prune` 명령 체계를 제공합니다. 이는 도커 엔진의 참조 카운팅(Reference Counting) 메커니즘을 기반으로 동작합니다. 예를 들어, 태그가 유실되어 이름이 없는 이미지(Dangling Image)나 연결된 컨테이너가 없는 익명 볼륨은 엔진 관점에서는 더 이상 유효하지 않은 자산으로 간주되어 삭제 대상이 됩니다.

특히 `docker system prune`은 전체 자원에 대한 일괄 정리를 수행하는데, `-a` 플래그를 사용할 경우 현재 실행 중인 컨테이너와 연결되지 않은 모든 이미지(사용되지 않는 정적 이미지 포함)를 제거합니다. 이는 디스크 공간을 확보하는 데 매우 효과적이지만, 운영 환경에서는 베이스 이미지까지 삭제되어 다음 빌드 시 다시 다운로드해야 하는 오버헤드를 유발할 수 있으므로 주의가 필요합니다.

#### 도커 컨텍스트 (Contexts)

도커 컨텍스트(Docker Contexts)는 단일 CLI 인스턴스에서 서로 다른 도커 엔드포인트(Daemon) 간의 연결 설정을 관리하고 전환하는 논리적 엔티티입니다. 분산 인프라 환경에서 엔지니어는 로컬 개발용 데몬, 원격 스테이징 서버, 그리고 클라우드 네이티브 컨테이너 서비스를 동시에 제어해야 하는 상황에 직면합니다. 과거에는 이를 위해 `DOCKER_HOST` 환경 변수를 수동으로 수정하거나 별도의 별칭(Alias)을 사용해야 했으나, 이는 환경 변수 오염 및 설정의 파편화라는 관리적 리스크를 수반했습니다.

아키텍처 관점에서 컨텍스트는 `~/.docker/contexts/` 경로에 저장되는 메타데이터 세트입니다. 이 데이터는 엔드포인트의 주소(Unix Socket, SSH, TCP 등)와 통신에 필요한 TLS 인증서 경로 정보를 포함합니다. 사용자가 `docker context use` 명령을 실행하면, 도커 클라이언트는 내부 커런트 포인터를 해당 메타데이터로 업데이트합니다. 이후 호출되는 모든 API 요청은 클라이언트 수준에서 가로채어져, 지정된 컨텍스트의 통신 프로토콜에 따라 터널링되거나 직접 전송됩니다.

특히 SSH 엔드포인트 지원은 보안상 큰 이점을 제공합니다. 별도의 TCP 포트를 외부에 노출하지 않고도 기존의 SSH 인프라를 활용하여 원격 데몬을 제어할 수 있기 때문입니다. 클라이언트는 백그라운드에서 SSH 세션을 생성하고 도커 API 트래픽을 해당 세션 내로 캡슐화하여 전달하며, 이는 물리적으로 로컬의 유닉스 소켓을 사용하는 것과 동일한 사용자 경험을 원격지에서도 유지하게 합니다.

#### 로그 드라이버 설정 (Log Rotation)

컨테이너 내부에서 발생하는 모든 표준 출력(`stdout`)과 표준 에러(`stderr`)는 도커 데몬에 의해 인터셉트되어 영구 저장소에 기록됩니다. 도커는 기본적으로 `json-file` 로그 드라이버를 사용하며, 이는 각 로그 라인을 JSON 객체로 직렬화하여 호스트의 디스크(보통 `/var/lib/docker/containers/` 하위)에 저장합니다. 문제는 기본 설정 상태에서 로그 파일의 크기에 제한이 없다는 점입니다. 무한히 증식하는 로그 파일은 호스트의 디스크 가용 공간을 고갈시키며, 이는 결국 시스템 커널의 I/O 블로킹이나 파일 시스템 손상이라는 치명적인 결과를 초래합니다.

로그 로테이션(Log Rotation)은 이러한 자원 고갈을 방지하기 위한 필수적인 데이터 관리 전략입니다. 로테이션 매커니즘은 `max-size`와 `max-file`이라는 두 가지 핵심 파라미터에 의해 제어됩니다. 활성화 시, 현재 기록 중인 로그 파일이 `max-size`에 도달하면 도커 엔진은 해당 파일을 닫고 접미사(예: `.1`)를 붙여 백업한 뒤, 새로운 로그 파일을 생성합니다. 전체 파일 개수가 `max-file`을 초과하면 가장 오래된 로그 세그먼트를 시스템에서 언링크(Unlink)하여 물리적 공간을 확보합니다.

이 프로세스는 파일 시스템 레벨에서 원자적으로 발생하도록 설계되어 있어, 로그 교체 시점에도 애플리케이션의 쓰기 작업은 중단되지 않습니다. 하지만 로테이션이 발생할 때마다 파일 인덱스를 갱신하고 메타데이터를 수정하는 오버헤드가 발생하므로, 초당 수만 건 이상의 로그를 쏟아내는 고부하 환경에서는 적절한 파일 크기 설계가 성능 안정성에 직접적인 영향을 미칩니다.

> **로그 드라이버 선택에 따른 시스템 성능 영향**
> 
> `json-file` 드라이버는 편리한 `docker logs` 조회를 지원하지만, 대규모 환경에서는 로그의 직렬화와 디스크 쓰기 부하가 데몬의 응답 속도를 저하시킵니다. 이를 극복하기 위해 `journald`나 `fluentd`와 같은 외부 드라이버를 사용하면, 로그 처리 로직을 도커 데몬의 주 프로세스에서 분리하여 시스템 전체의 안정성을 높일 수 있습니다.
{: .block-tip }

#### 이벤트 스트림 (Events)

도커 이벤트 스트림(Docker Events)은 도커 데몬 내부에서 발생하는 모든 상태 변화와 객체의 생명 주기 이벤트를 실시간으로 발행하는 발행-구독(Pub-Sub) 시스템입니다. 도커 엔진은 컨테이너의 생성, 실행, 종료뿐만 아니라 이미지의 태그 지정, 볼륨의 마운트, 네트워크 연결 등 시스템 전반에서 발생하는 수십 가지의 세부 동작을 이벤트 형태로 기록하고 이를 외부 API 엔드포인트를 통해 스트리밍합니다.

아키텍처 측면에서 이벤트 스트림은 도커 데몬 내의 메모리 버퍼에 기반한 시계열 데이터 흐름입니다. 외부 클라이언트가 `/events` REST API 엔드포인트에 접속하면, 데몬은 HTTP 응답 본문을 닫지 않고 유지하는 'Streaming Response' 방식으로 데이터를 전송합니다. 각 이벤트는 JSON 객체로 구성되며, 이벤트가 발생한 시점(Timestamp), 이벤트의 종류(Action), 대상 객체의 타입(Type: container, image, volume, network 등), 그리고 해당 객체의 메타데이터를 담은 Actor 속성을 포함합니다.

이 매커니즘은 자동화된 인프라 구축의 핵심 신경망 역할을 수행합니다. 예를 들어, 서비스 디스커버리 도구는 이 스트림을 모니터링하다가 새로운 컨테이너가 'start' 되는 이벤트를 수신하는 즉시 로드 밸런서의 설정을 동적으로 갱신합니다. 또한, 보안 관제 시스템은 컨테이너가 예기치 않게 'die' 하거나 특권 권한으로 실행되는 이벤트를 감지하여 즉각적인 경보를 발생시킵니다.

> **이벤트 필터링과 시스템 부하 최적화**
> 
> 대규모 클러스터 환경에서는 초당 수천 개의 이벤트가 발생할 수 있습니다. 클라이언트 측에서 모든 이벤트를 수신한 뒤 거르는 방식은 네트워크 대역폭과 CPU 자원을 낭비하므로, API 호출 시점에 `filter` 파라미터를 사용하여 필요한 이벤트 타입(예: `type=container`)이나 특정 액션(예: `event=die`)만을 서버 사이드에서 선별적으로 스트리밍받도록 설계해야 합니다.
{: .block-tip }

![](/docs//assets/img/2026-01-25-00-15-37.png)

엔지니어링 트레이드오프 관점에서 이벤트 스트림은 '최선 노력(Best-effort)' 전달 방식을 취합니다. 데몬 내부의 이벤트 버퍼는 크기가 제한되어 있으므로, 클라이언트가 데이터를 충분히 빠르게 읽어가지 못하거나 네트워크 연결이 불안정하여 버퍼가 가득 찰 경우 오래된 이벤트부터 소실될 수 있습니다. 따라서 엄격한 감사(Audit) 기록이 필요한 경우에는 이벤트 스트림에만 의존하기보다, 호스트 OS 수준의 커널 감사 로그(Auditd)나 외부 영구 저장소로 로그를 즉시 전송하는 로깅 드라이버를 병행하여 사용하는 것이 권장됩니다.
